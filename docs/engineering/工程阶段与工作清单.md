# 工程阶段与工作清单

更新日期：2026 年 10 月 26 日。

状态：讨论稿。用于逐项讨论工程落地的顺序、拆分和边界；阶段与工作项尚未逐项确认，也未开始业务代码实现。已有产品决议继续有效，本文不重新定义奖励和资金规则。

建议顺序：工程基础 → 用户鉴权 → 账户与账本 → 任务奖励 → 钱包充提 → 商户支付 → 运营后台完善 → 发布与多端扩展。共 8 个阶段、52 个工作项。

本文作为后续讨论具体工程步骤的主文档。[实施路线](实施路线.md) 保留宏观交付目标；具体工作划分在本文集中修改，确认后的结果再同步对应设计与实施文档，避免维护两套不同的执行顺序。

## 讨论和修改方式

- 先讨论阶段顺序、任务拆分和依赖，再进入某个工作项的详细方案。当前不要求一次确定全部数据库表或接口。
- 使用稳定编号引用，例如「2.1 用户模型增加身份解绑边界」或「5.3 的技术验证提前到工程基础阶段」。调整顺序不随意重编号；拆分可增加子编号，合并保留原编号去向。
- 单个工作项按「讨论 → 确定 → 落地 → 验证」推进。讨论确定后才开始该项实现；已确定的内容不重复确认，实施中发现影响业务行为的变化再说明取舍。
- 状态可记为待讨论、讨论中、已确定、实施中、待验证、已完成或阻塞。每项当前状态以对应讨论记录为准，文档已写入不等于工程已完成。
- 每项包含必要的接口、数据变更、前端接入、权限、错误与恢复，以及对应验证。表中的页面联调项负责串通和体验完善，不意味着前面的模块可以完全不接前端。
- 一个工作项可分多个实现分支，但每次提交围绕明确行为，保留测试证据和遗留问题。

## 第一阶段 建立工程基础

先确定业务代码放在哪里、怎样运行、怎样生成和检查。

| 编号 | 工作项 | 具体实现内容 | 工作边界 |
| --- | --- | --- | --- |
| 1.1 | 工程结构与模块划分 | 确定后端、用户前端、管理前端目录，以及身份、账户、任务、奖励、支付等模块的职责和调用关系 | 明确当前技术选型与依赖；不提前拆成大量微服务 |
| 1.2 | 契约与代码生成 | 建立 API 源定义、数据库 DDL、增量迁移及前端类型生成流程，记录工具版本和命令 | 先建立生成机制和示例；业务表与接口随各模块细化，生成不自动执行迁移 |
| 1.3 | 后端公共基础 | 配置加载、数据库连接、事务入口、统一响应、错误码、日志、请求追踪、健康检查 | 公共层不包含具体业务计算，不提前构造万能业务框架 |
| 1.4 | 前端公共基础 | 路由、API 客户端、错误处理、国际化、页面布局和基础组件 | 提供业务页面接入方式；具体任务、支付等页面随业务实现 |
| 1.5 | 开发与测试环境 | 本地启动配置、测试数据库、构建检查、自动化测试入口和测试环境部署 | 与生产环境分开，形成真实可运行命令，不以文档描述代替运行验证 |

完成条件：从干净环境完成依赖准备、生成、构建、数据库初始化与迁移，一条示例接口前后端贯通。实际使用到的基础组件具备对应验证入口。

讨论重点：工程如何分目录和部署单元；哪些内容生成、哪些手写；前后端共享哪些契约；如何管理环境与工具版本。

## 第二阶段 实现用户与鉴权

解决当前是谁、会话如何恢复、能够操作什么。资金账户在阶段 3 实现。

| 编号 | 工作项 | 具体实现内容 | 工作边界 |
| --- | --- | --- | --- |
| 2.1 | 用户模型 | 产品用户、外部身份映射、用户 idx、状态、创建和查询；明确 Telegram 用户与产品用户关系 | 身份模型与资金账户、钱包地址分开，不因外部平台身份增加而复制业务账户 |
| 2.2 | Telegram 鉴权 | 校验 Mini App 授权材料，首次创建用户，后续返回已有用户 | 服务端验证真实授权，不信任客户端自报身份；登录不绑定邀请关系 |
| 2.3 | 产品会话 | 凭证签发、有效期、失效与续期策略、退出、鉴权中间件 | 会话机制可供后续客户端使用，不在此阶段增加多种未经确定的登录入口 |
| 2.4 | 用户接口与前端接入 | 当前用户查询、资料展示、前端登录状态、失效处理、恢复原业务页面 | 登录恢复后重新检查业务权限，不因恢复页面自动扣款或领奖 |
| 2.5 | 后台登录与权限基础 | 管理账户、后台会话、接口访问控制和操作记录基础 | 主体归属规则随商户模块补齐；不提前做复杂角色矩阵或多级审批 |

完成条件：用户从 Telegram 进入后可靠识别身份，重新打开仍是同一产品账户；过期、伪造材料与未授权访问被正确处理，前端能恢复来源页面。

讨论重点：表结构和唯一约束；会话生命周期；账户禁用影响；普通用户和后台账户的隔离；敏感动作需要怎样的身份校验。

## 第三阶段 实现资金账户与账本

任务奖励、充值、支付和结算都依赖这部分。先实现可信的资金基础，再实现各业务的资金动作。

| 编号 | 工作项 | 具体实现内容 | 工作边界 |
| --- | --- | --- | --- |
| 3.1 | 账户与金额模型 | 美元余额、任务积分、待提现奖励的账户结构、单位、精度和初始化规则 | 链上资产属于外部事实；Pro 为业务进度，不放进可消费余额 |
| 3.2 | 账本与流水 | 凭证、分录、业务关联、余额变更及查询接口 | 业务通过明确记账入口操作，不能直接修改余额字段；各业务保留自己的单据 |
| 3.3 | 占用与释放 | 冻结、核销、释放和关联记录，为出金、组合支付及结算提供基础 | 核销与释放互斥；奖励申请扣减仍遵循原业务规则，不能机械套成同一种余额冻结 |
| 3.4 | 幂等与事务 | 重复请求识别、同键异参冲突、并发余额检查、一次记账与失败回滚 | 不以按钮防重或短期缓存锁代替持久约束 |
| 3.5 | 持久化后台任务 | 任务记录、执行状态、重试、事件持久化与投递基础 | 提供恢复基础，各业务自己定义成功、失败和允许重试条件 |
| 3.6 | 美元余额互转与账单 | 收款账户查找、转账接口、双方账单、确认与结果页、记录列表及详情 | 完成第一个资金功能；链上报价在阶段 5 实现，不为内部互转引入无关依赖 |

完成条件：两个测试账户完成真实数据库记账的互转，双方金额正确；并发不超支，重试不重复扣款，失败不产生单边流水。测试资金通过隔离环境的明确准备方式提供，不增加生产任意改余额入口。

讨论重点：账户类型与单位；记账接口与事务边界；冻结模型；业务单据和账本如何关联；金额精度与舍入；如何查询和恢复原操作。

## 第四阶段 实现任务与奖励

目标是贯通登录 → 真实任务 → 获奖 → 积分抽奖 → 奖励进入美元余额。依赖阶段 2、3，不依赖真实链上收付。

| 编号 | 工作项 | 具体实现内容 | 工作边界 |
| --- | --- | --- | --- |
| 4.1 | 任务基础 | 任务定义、类型、配置、有效期、参与资格、完成记录和验证适配接口 | 每类任务实现自己的资格和验证；不做任意代码上传的任务平台 |
| 4.2 | 任务执行与领奖 | 列表、详情、外部执行入口、主动验证、领奖接口，接入第一种真实任务 | 先贯通执行与验证；完整发奖以 4.3–4.5 整合完成为准，不临时绕过公共结算 |
| 4.3 | 奖励计算与 Pro | 首奖、任务积分、累计进度、自动解锁、翻倍及计算顺序 | 首奖进度与可消费积分分开，计算模块不直接越过账本写余额 |
| 4.4 | 邀请与助力 | 任务链接、受邀上下文、首次完成关系绑定、助力资格、20% 分成及统计 | 不增加通用邀请、改绑或递归分成；资格与本人任务参与保持一致 |
| 4.5 | 奖励事务整合 | 一致结算完成记录、资格消耗、首奖、任务积分、分成及 Pro 变化 | 明确事务和幂等边界，重复验证返回原结果，失败不留下部分奖励 |
| 4.6 | 积分抽奖 | 奖项版本、概率校验、结果计算、扣分与现金入账、记录、动画 | 动画展示已确定结果，不在前端决定奖励，不因断网重新抽取 |
| 4.7 | 奖励转入 | 条件查询、申请、扣奖励、自动处理或人工审核、拒绝退回、美元入账 | 固定本人美元账户，无链上交易；必要审核入口本项完成 |
| 4.8 | 配套页面与后台 | 奖励首页、邀请成果、抽奖、转入，以及任务配置和奖励审核页面联调 | 整合前面接口与页面，不能把必要的可操作入口全部延后到阶段 7 |

完成条件：至少一种真实任务完成全流程；首奖并发、资格消耗、Pro 临界、分成取整、重复领奖、抽奖中断与申请拒绝都有确定结果。

讨论重点：先接入哪种真实任务；任务验证接口；参与和领奖记录如何去重；结算计算顺序；动态提现条件的表达及审核方式。

## 第五阶段 实现钱包与链上通道

首先落实 Mini App 的 TON 与 USDT。用户钱包和平台资金钱包分开，前者由用户授权，后者处理平台实际收付。

| 编号 | 工作项 | 具体实现内容 | 工作边界 |
| --- | --- | --- | --- |
| 5.1 | 用户钱包接入 | 外部连接、会话恢复、切换，内置创建、导入、密钥保护与备份 | 用户密钥留在本地或外部钱包；连接不是扣款授权 |
| 5.2 | 链上资产与直接收发 | 余额、地址、记录、收款码、普通转账、签名和结果查询 | 用户钱包直接转账不产生平台美元入账或商户收入 |
| 5.3 | 平台链上收付基础 | 收款地址、到账归属、监听、事件去重、确认判断、平台签名和出款任务 | 签名与普通业务隔离；实收精确到转账事件，未知执行不重新出一笔 |
| 5.4 | 行情与报价 | 行情获取、资产配置、费用计算、报价记录、有效期、精度和舍入 | 资产估值与实际成交报价分开，不固定假设稳定币等于美元 |
| 5.5 | 本人与代他人充值 | 充值单、受益人、代付、交易请求、实收核验、美元入账及异常处理 | A 付款给 B 充值只给 B 入账；未验证手动转入通道不开放 |
| 5.6 | 美元余额链上转出 | 申请、冻结、风险判断、审核、签名广播、核验与失败恢复 | 审核和拒绝恢复随本项实现；未知出款不可同时退款又重发 |
| 5.7 | 钱包页面联调 | 首页、资产详情、收款、充值、转出，联通账单与状态恢复 | 页面显示权威状态，钱包返回或用户点完成不证明到账 |

完成条件：连接或使用钱包，查询与直接收发资产，充值美元余额，再将美元余额转到确认过的链上目标；TON 与 USDT 的正常和失败恢复分别验证。

讨论重点：密钥保护、外部回跳、充值归属、代付路径、费用承担、确认标准、有效提交证据、冻结时限和晚到账处理。

密钥保护、代付与到账关联先做最小验证，再进入正式实现。若影响阶段 1 的技术选择，验证提前开展；这不意味着提前完整实现钱包业务。结果未知的处理能力不能留到最后联调才补。

## 第六阶段 实现商户与支付结算

依赖用户身份、账本与链上通道。余额、链上和组合支付分别实施、分别验证。

| 编号 | 工作项 | 具体实现内容 | 工作边界 |
| --- | --- | --- | --- |
| 6.1 | 企业与商户 | 主体模型、后台账户归属、申请启用和结算资料 | 明确平台审核与主体权限，不扩展复杂组织系统 |
| 6.2 | 商户接口认证 | API 凭据、请求认证、重放防护、轮换与数据隔离 | 企业后端使用凭据，不下发到用户浏览器 |
| 6.3 | 订单管理 | 后台及 API 开单、商户订单号幂等、有效期、关闭、查询、支付链接和码 | 创建订单不产生收入，商品库存和履约仍归商户系统 |
| 6.4 | 余额支付 | 用户扣款、商户应付款入账、支付记录与结果 | 同事务一致完成，项目链上资产不动 |
| 6.5 | 链上支付 | 付款请求、实收关联、链上核验和商户入账 | 同一实收不再给用户记充值，费用与商品价款分开 |
| 6.6 | 组合支付 | 余额预留、链上差额、分项状态、失败补偿与晚到账 | 限一钱包一网络一资产；全部完成才整单成功 |
| 6.7 | 商户通知 | 回调事件、签名、重试、投递记录、主动查单和接入说明 | 通知失败不改支付事实，乱序和重复不导致重复履约 |
| 6.8 | 退款 | 申请、可退额度、商户占用、余额及链上退款、组合分项 | 按原来源与确定政策处理，不能凭截图退款或虚构可退资金 |
| 6.9 | 商户结算 | 可结算金额、冻结申请、审核、人工触发、到账确认和恢复 | 人工批准不是资金已到，外部可执行提案仍纳入在途 |
| 6.10 | 配套前后台 | 收银台，商户工作台、订单、资金与接入设置，平台处理页面联调 | 联通业务，不把必要失败处理只做成无功能按钮 |

完成条件：商户开单、用户付款、通知与查询确认收款，随后按规则退款或申请结算；每笔资金有明确来源去向且可核对。

讨论重点：企业商户模型、订单和付款尝试关系、商户应付款、支付状态、退款币量与费用、结算执行权及通知契约。

6.4–6.6 可依次在测试环境验证，但实际开放某种付款前必须具备对应退款、异常恢复与通知能力。6.8、6.9 共用出款基础，分别维护自己的额度、占用和业务状态。

## 第七阶段 完善运营后台

把已经随业务实现的处理能力整合成能日常维护的系统。

| 编号 | 工作项 | 具体实现内容 | 工作边界 |
| --- | --- | --- | --- |
| 7.1 | 用户与商户管理 | 检索、详情、交易限制、商户停用恢复、关联业务查询 | 不提供直接改余额、积分或邀请上级入口 |
| 7.2 | 审核工作台 | 汇总奖励转入、用户出金、退款和结算的待办与记录 | 共用展示与处理基础，不抹平各业务不同的资金恢复规则 |
| 7.3 | 异常订单处理 | 少付、多付、重复、晚到、无法归属和未知出款的集中核验入口 | 无证据不改成功，暂挂保留责任和后续处理时间 |
| 7.4 | 对账与平台资金 | 链上、账本、业务单据核对，归集、备付和调拨 | 原币与美元分别核对，内部调拨不能新增用户充值 |
| 7.5 | 配置与审计 | 费用、限额、通道、风险、奖励版本、发布校验和操作记录 | 既有交易保留版本，不以配置回滚撤销历史资金 |
| 7.6 | 运行监测 | 监听停滞、任务失败、未知出款、对账差异、备付不足告警 | 告警需能关联业务和责任，不能只记录无人处理的日志 |

完成条件：运营人员能从发现问题、查看证据到执行处理、反馈结果和核对资金完成全过程，日常操作可追踪。

讨论重点：待办分类与优先级、权限、处理命令、可见信息、超时责任、对账口径及告警条件。

各业务最低必要审核、异常、审计和资金核对在对应阶段完成；本阶段做跨业务整合和运营完善，不是首次补齐所有安全与恢复能力。

## 第八阶段 联调发布与独立 App 扩展

8.1–8.3 完成 Mini App 发布，8.4–8.5 完成独立 App 及其他网络扩展，两者分别验收。

| 编号 | 工作项 | 具体实现内容 | 工作边界 |
| --- | --- | --- | --- |
| 8.1 | 全链路测试 | 登录、任务、充值、支付、退款结算，以及并发、权限、断网和服务重启 | 模块测试随开发完成，本项验证跨模块整体结果，不重复以接口成功代替资金核对 |
| 8.2 | 部署与恢复 | 正式环境配置、迁移、发布流程、备份恢复、监控接入和版本回退 | 回退不能破坏已发生交易，密钥与数据库恢复分别验证 |
| 8.3 | Mini App 发布验证 | Telegram 实际环境、目标设备的鉴权、钱包跳转、页面与资金流程 | 测试通道通过与生产开放分别记录，按确定范围发布 |
| 8.4 | 独立 App 工程 | 客户端框架、接口接入、身份、密钥存储和钱包回跳 | 复用已验证业务契约，平台相关能力单独实现与验证 |
| 8.5 | 其他链适配 | Base、Solana、TRON 的资产、连接、充值、支付、出款和恢复 | 可继续按网络拆分；同名币或钱包品牌支持不等于通道已兼容 |

完成条件：Mini App 可运行、可监测、可恢复；独立 App 与已确定的网络资产分别通过适用场景验证。

讨论重点：发布阻塞标准、环境与资金隔离、部署迁移顺序、故障回退、App 框架、每条链的差异与上线条件。

## 跨阶段边界

1. 产品用户、资金账户和链上钱包分别建模，不能用一个用户表或钱包地址混合承担所有职责。
2. 领域模块对外提供明确能力，优先降低复杂度，不把全部功能塞进公共服务；也不提前拆大量部署单元。
3. 每个业务负责自己的状态和成功条件，共用账本、签名与任务执行能力不代表所有业务共用一张万能状态表。
4. 记录、权限、幂等、事务和恢复与业务一起落地，不能统一推迟到阶段 7 或 8。
5. 页面随业务接入；阶段末的页面联调负责完整体验，不要求先做完所有后端再开始前端。
6. 已确认规则以 [业务规则](../product/02业务规则.md) 为准；待落实通道与参数见 [决议台账](../decisions/决议与待落实事项.md)，不能用原型值冒充生产配置。
7. 每项根据实际范围维护契约源定义、DDL 和迁移、实现及测试；单元测试隔离外部依赖，真实钱包和网络验证单独运行。
8. 实现与验证通过不自动表示已发布。文档、原型、测试环境功能、真实通道验证和生产开放分别标记。
