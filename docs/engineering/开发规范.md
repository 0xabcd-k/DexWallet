# 开发规范

本项目采用用户个人开发习惯中适用的规则。1.1 已确认工程方向并初始化最小 module/workspace；1.2 已建立隔离示例与生成/迁移工具，1.3 已建立后端公共基础与健康接口，不能把这些当作正式业务能力。实际入口、工具版本与命令见 [工程结构](工程结构.md)。

## 文档与需求

- 文档统一在 `docs/`，根 `AGENTS.md` 只保留入口与实际检查命令。
- 当前规范以新版目录为准，历史归档提供来源，不自动覆盖已更新规则。
- `/pre` 请求先在 `docs/design/` 形成具体方案等待确认；已确认方案继续执行，普通任务不增加额外确认关卡。
- 修改规则同步受影响流程、界面、参数与验收。既有用户决议优先于技术偏好，不因规范迁移已有技术栈。

## 成熟能力复用

- 复用以降低项目复杂度为目的，不以库调用数量或统一包名为目标；优先删除重复机制，不引入比原逻辑更重的包装或无实际收益的新依赖。
- 以已确认的产品需求和可观察的运行要求为先。标准库、go-zero 或成熟第三方库已完整覆盖时，直接使用其公开能力；不为同样的行为另建实现，也不增加没有项目职责的透传包装。
- 框架能力先参考 go-zero 的整体设计、默认配置、中间件顺序和生命周期，再选择函数。已有自定义机制、参数、文件划分和测试细节不自动成为不可调整的需求；框架设计更合适且满足需求时，调整项目实现。
- 有差异时先核对锁定版本的配置与扩展点，必要时做隔离实验。只有证实需求未被覆盖，才保留最小适配，并记录具体缺口、适配职责和行为验证；不因局部差异替换整条框架链路，不复制算法或依赖内部 API。
- 复用不限于 go-zero；已使用的 database/sql、go-redis、Apache RocketMQ SDK、golang-migrate 等按能力评估，不为统一包名重复迁移。升级或引入依赖需核对维护、兼容范围和实际收益。
- 验收保持契约、失败语义、资源与退出边界等可观察要求；随合理设计调整测试实现，不让测试固化偶然的 goroutine、缓冲区或锁结构。已确认业务规则及对外契约的变更仍须明确记录影响。

## 契约和生成

本项目已确认 Go/go-zero/goctl + MySQL/InnoDB，采用 SQL-first：仓库 SQL DDL 先定义，再生成基础 model，业务查询与事务保留手写扩展。数据库同时维护完整 DDL、索引及已部署库的增量迁移。1.1 Q07 已确认 `.api` 为 HTTP 唯一权威源，前端类型从同一源派生；如需 OpenAPI，只作为生成的中间产物，不另行手改维护。1.2 已落实直接 TS 类型生成、配置驱动的无缓存 model、手写保护及显式迁移，版本和已验证限制见 [契约生成与迁移](契约生成与迁移.md)。有跨端协议才引入对应 schema，已确认的 Redis 与消息中间件按下述职责接入。

工程已确认单仓库、一个后端 Go module；前端采用 React + TypeScript + Vite、pnpm workspace、Less 与 i18next，用户、商户、平台分别位于 `frontend/apps/user`、`merchant`、`admin`，生成独立构建产物。后端首版采用一个程序/进程承载 API 与后台任务，二者保留代码职责、并发额度和生命周期边界；三个静态站点、MySQL、Redis、RocketMQ 保持各自职责，平台签名保持独立信任边界。需要资源隔离时再拆后台进程，不预先要求独立 worker 部署。多副本不依赖本机业务状态，任务须有持久领取、幂等与退出恢复机制。业务包按已确认职责随实际实现建立。依据见 [1.1 讨论记录](../design/工程工作记录/01-工程基础/1.1-工程结构与模块划分/01讨论记录.md)。

生成器和模板版本可追溯，module、数据库名及路径按项目参数化。模板生成覆盖区与手写扩展分开；首次生成的 logic 骨架不等于以后不能手写。生成不隐式执行数据库迁移。

进入实现阶段先提供真实可执行的准备、生成、类型检查、构建和测试命令，再写入文档；缺工具时明确说明，不能伪造生成产物。

## 业务组织

接入层处理解析、鉴权和响应，业务按领域归档，依赖集中组装。抽象首先降低阅读复杂度，其次考虑复用；不创建没有职责的转发层或万能平台框架。

后端当前共用 `backend/svc.ServiceContext`，直接持有配置、客户端和健康状态；主入口创建并负责最终关闭，各 API 或后续后台任务不重复初始化。API 内的 svc 保留类型别名以兼容 goctl 的导入布局，不建立第二个依赖容器。正式 main/handler/context 的共性由 `backend/template/api/` 承接，其他模板沿用上游；按实际业务提取公共 logic，不提前建立空业务包。未来多个常驻服务可采用原生 ServiceGroup，但它的并发 Stop 不代替“业务排空后再关闭依赖”的顺序约束。

Q04 已确认：业务写入走所属用例，账本、实收分配和出款执行有统一入口；跨模块原子动作由最外层业务用例协调同一显式事务，协作模块不提前提交。按实际复杂度拆包，只读聚合允许在授权范围内编写明确 SQL，不绕过业务入口修改状态。

1.3 Q04 已确认其事务落地方向：基于 TransactCtx 显式传递 session，以手写 WithSession 扩展绑定 model；原子操作不混用默认连接，不引入嵌套事务或公共自动重试。事务内只做同库事务性操作，不执行外部调用或迁移；提交应答丢失保留结果未知，错误和回滚异常保留诊断。具体适配及待验证行为见 [1.3 实施方案](../design/工程工作记录/01-工程基础/1.3-后端公共基础/02实施方案.md)，已建立公共事务入口，具体使用见后端公共基础说明。

枚举贴近领域模型，错误码统一管理，事件 topic 和发送入口集中，Redis key 使用统一命名空间。运营参数进入版本配置，禁止业务魔法值，不要求所有普通字面量都抽成常量。

账务操作通过有幂等和凭证的服务入口，金额使用精确十进制或最小单位整数。API 金额带明确单位，以字符串传递精确值。对外 ID 沿用 idx：参照 dexpoker，以配置密钥和具名业务类型参数将内部数值 id 可逆编码为字符串，输出编码、输入解码后按 id 查询；不另生成 UUID，不增加 idx 持久化列或映射表。编解码复用 FF1 库并统一封装，已使用的编码配置保持稳定，非法输入明确报错；编码不代替鉴权。具体用户模型见 [2.1 实施方案](../design/工程工作记录/02-用户与鉴权/2.1-用户模型/02实施方案.md)，实现与验证见 [用户模型](用户模型.md)。临时有限增长的时序 ID 可用 number，不强制全部 string 或 bigint。

## Redis 与消息中间件

Redis 与消息中间件是已确认架构组件，本地复用现有 Redis、RocketMQ Docker 服务。Redis 承接缓存与明确的临时状态，RocketMQ 承接异步事件分发和业务解耦，MySQL 保留业务事实、资金幂等及恢复依据。引入 MQ 不拆散必须原子完成的记账事务；具体 outbox、消费去重、重试和死信方案在 3.5 落实。

配置、客户端组装与健康诊断归 1.3，本地服务接入和隔离集成测试归 1.5，业务消费者与恢复归所属模块及 3.5。Redis key、topic、消费组按项目/环境集中命名；共享本机服务不共用其他项目业务命名空间，不覆盖现有容器或数据卷。记录实际版本和网络/鉴权配置来源，不把容器 running 当作应用接入通过，不在仓库写凭据。

1.3 Q02/Q03 已确认：YAML 与环境变量提供配置，启动校验，客户端集中管理，首版修改配置后重启生效。MySQL 作为核心依赖；Redis 纯缓存可受控降级，但正确性依赖不得绕过；MQ 故障按实际用途影响对应能力，发送超时保留未知。存活与就绪分开，依赖短暂故障不直接触发进程反复重启。具体边界及尚待实施验证内容见 [1.3 实施方案](../design/工程工作记录/01-工程基础/1.3-后端公共基础/02实施方案.md)。

## 前端与文案

新前端使用 TypeScript/TSX 与明确的 API、props、状态和错误类型。页面与局部样式相邻，接口客户端、鉴权与错误处理集中；不能用 any 或强制断言掩盖业务状态不完整。

按钮、提示、空态和可访问性文案进入 i18next 国际化资源，实际语言集合在实现时确定。文案需表达真实资金状态；协议和内部错误只在确有用户决策价值时出现。

简单状态查询不强制引入 Worker 或长连接框架，复杂持续通信再按需求选型。选择组件时需验证移动端跳转和恢复，不能以组件默认支持扩大业务范围。

## 错误与诊断

1.3 Q01 已确认普通 JSON API 采用 code/message/data/traceId，配合有语义的 HTTP 状态码与稳定字符串业务码；成功 data 使用明确类型，失败省略 data。前端按 code 国际化，原始原因保留在后端错误链与日志，请求成功或超时不等同于资金完成或失败。完整响应纳入 `.api`，不得让运行时包装与生成类型不一致。具体映射与待实施验收见 [1.3 实施方案](../design/工程工作记录/01-工程基础/1.3-后端公共基础/02实施方案.md)；当前公共入口已落实，具体测试见 1.3 验证记录。

区分业务拒绝、鉴权失败、系统失败和未知执行；采用统一类型化结果或异常策略，保留原因，失败不作为普通成功值。日志能关联主体、业务 idx、报价版本、链上事件、重试和执行任务，供有权限的开发运维充分排障。

日志权限边界不等于公开输出凭据；用户密钥和助记词不能进入服务端，管理凭据不进入仓库、公开响应或不相关渠道。

1.3 已落实结构化日志、响应体/响应头/日志 traceId 关联、健康探测与有限停机等待。当前公共入口生成服务端追踪根，不信任客户端追踪头；内部可信传播随部署边界落实。实际配置、命令与限制见 [后端公共基础](后端公共基础.md)。

## 测试与交付

单元测试验证可观察结果，外部数据库、RPC、签名、通知等边界使用 mock/fake，按需控制时间和随机源；不 mock 被测业务本身，不靠随机统计替代确定性正确性检查。真实钱包和依赖放独立集成测试。

1.5 Q02 已确认测试资源隔离，并以生产数据库保持干净为前提：自动化测试、示例迁移、测试数据准备与清理不得连接或操作生产库。使用独立测试配置、凭据和访问边界，目标不明确时拒绝执行，不回退到生产 DSN；资源名前缀不能代替权限隔离。仅清理本次创建且记录归属的资源，开发数据和外部长期库保留。正式迁移仍归显式发布流程。上述保护须以实施与验证记录证明，不能只靠文档宣称已实现。

一个业务逻辑一个分支，保护原有工作区与暂存区。每轮先同步当前远端同名分支，仅快进；新分支从已同步起点创建。验证后仅提交本轮改动并推送，不夹带 IDE 配置、凭据或临时产物；合并按授权执行并优先 squash，不强推改写已发布历史。

当前文档检查为 `python3 scripts/check_docs.py` 与 `git diff --check`。前者检查文档链接、结构、场景追踪、奖励数学参数和历史归档字节完整性，不表示应用或链上集成已通过测试。module/workspace 的实际检查见 [工程结构](工程结构.md)，契约检查使用 `bash scripts/check_contracts.sh`；真实 MySQL 迁移验证使用独立 integration 标签入口，详见 [契约生成与迁移](契约生成与迁移.md)。
