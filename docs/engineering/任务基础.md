# 任务基础与 Telegram 频道样例

4.1 实现任务定义、身份资格、完成记录基础及成员查询边界，并提前接通用于验收的列表、详情和主动检查页面。当前只有 mock 样例，不访问 Telegram，不要求真实频道或 Bot；真实任务执行与奖励整合继续归 4.2–4.5。

## 运行与接口

数据库要求 **business 11**。[完整 DDL](../../backend/manifest/sql/ddl/task/tables.sql)、[约束](../../backend/manifest/sql/ddl/task/constraints.sql) 与 [000011 迁移](../../backend/manifest/sql/diff/business/000011_task_foundation.up.sql) 同步维护；生成入口已登记 task model。迁移不自动执行，现有共享开发库和生产库未升级。

| 入口 | 行为 |
| --- | --- |
| 用户端 `/#/tasks` | 任务列表、参与资格、分页；首页任务按钮及奖励页链接均可进入 |
| 用户端 `/#/tasks/:idx` | 详情、有效期、绑定引导、主动检查；所有样例明确标识，无真实频道跳转 |
| GET `/v1/user/tasks` | 产品 JWT；before 为任务 idx 游标，默认每页 20、最大 100 |
| GET `/v1/user/tasks/:idx` | 当前身份的资格；草稿、其他模式或未开启 mock 返回不存在 |
| POST `/v1/user/tasks/:idx/check` | 无客户端身份或关注参数；只读预检，返回 member/not_member 与检查时间 |

API 权威源为 [platform.api](../../backend/manifest/api/platform/platform.api)。对外任务 ID 继续使用独立业务类型的 idx；响应不返回 Telegram 数字 ID。当前 `claimAvailable=false`，没有领奖接口。检查通过仅显示关注条件满足，刷新页面不自动验证，也不保存可用于以后领奖的验证凭证。

`task_definition` 保存类型、状态、目标频道、配置版本、有效期和基础积分；当前类型为 `telegram_channel_follow`，验证模式仅 mock。基础积分是后续奖励计算的输入，当前页面不把它冒充首奖或最终奖励。配置内容为业务数据，界面固定文案使用中英文国际化资源。当前不开放任务管理 API，样例由受保护工具创建。

`task_completion` 只用于最终已结算事实，唯一键为任务 + Telegram 身份，以及受益用户 + 请求号。基础 model 提供 WithSession；未来由奖励用例在调用方事务内写完成记录与奖励。本轮线上业务代码不写此表，测试中已有完成记录均是明确构造的历史夹具，不表示发奖已实现。

## 资格与外部验证

同一 Telegram 身份在同一任务只能成功一次，已关注者允许参与。更换产品账户不清除该身份已用次数，过去奖励归属不转移；不同任务分别计资格。任务有效区间采用数据库 UTC 的 `[starts_at, ends_at)`，暂停、未开始、到期或身份未绑定不能检查，不提供过期补领。

后端在同一查询中读取最新用户状态、认证版本及当前 TG 绑定，不依赖普通用户缓存或前端参数。外部查询在数据库事务外执行，返回后再次检查身份、绑定版本、任务配置和当前资格。检查期间换绑、回绑、停用或任务变化时不采用旧结果。当前检查是只读快照，不代表锁定后续资格；将来的领奖仍须重新验证并在资金事务内复核。

成员查询接口只接受后端选择的频道 ID 与 Telegram 用户 ID。mock 逐对配置确定结果，无夹具时明确报错；成员为 creator/administrator/member，left/kicked 为非成员。未知状态、身份不匹配和故障为无法核验，不误报未关注或成功；详细原因保留在后端错误链。错误码区分缺身份、不可用、次数已用、绑定变化和验证失败。

不增加任务进行中状态、后台持续关注监听或退订扣回。真实 Bot API 及权限仍按 [方案](../design/工程工作记录/04-任务与奖励/4.1-任务基础/02实施方案.md) 单独接入验收。

## 本地 mock 配置与样例准备

[platform.yaml](../../backend/api/etc/platform.yaml) 默认 `Tasks.Mode: disabled`，任务列表返回空，已存在的样例也不会显示。只有 `Environment: local`、`Mode: dev` 才允许 `Tasks.Mode: mock`；其他组合启动报错。没有切换结果的公开接口，也不通过验证失败自动退回 mock。

在已应用 business 11 的隔离 contract 测试库中运行 [taskdemo](../../backend/tools/taskdemo/main.go)：

```sh
# 在 backend/ 执行；预先加载专用本地测试环境。
# DEXWALLET_MYSQL_DSN 必须指向下方确切 contract 测试库并使用受限测试账号；
# DEXWALLET_ID_SECRET 与访问该库的应用配置一致。不要使用日常开发库或生产凭据。
go run ./tools/taskdemo --database dexwallet_contract_tasks --telegram-user-id 900000001 --member-status member
```

工具使用现有 testenv 目标保护，要求本地显式回环地址、测试账号与同名 `dexwallet_contract_` 库；不创建账户、不伪造已绑定身份、不发奖。每次显式运行创建一条 24 小时有效的独立样例，并输出任务 idx、页面路径和可复制的配置。重复执行会创建新任务，不是覆盖已有配置。实际登录可使用既有 [本地 TG 模拟登录](开发与测试环境.md#在浏览器体验-telegram-登录)，也可使用隔离测试身份；绑定和用户仍来自真实数据库。

```yaml
Tasks:
  Mode: mock
  Fixtures:
    - ChannelID: -100900000001
      TelegramUserID: 900000001
      Status: member
```

同一频道/用户只能有一条夹具。测试未关注时将 Status 改为 left 并重启后端；测试错误时移除 Status，改设 `Failure: timeout`、`rate_limited`、`permission_denied` 或 `invalid_response`。不需要 Bot token；已有本地 TG 登录模拟使用的开发凭据与成员查询 mock 是两个独立边界。
