# 实施路线

具体工程步骤集中在 [工程阶段与工作清单](工程阶段与工作清单.md)，作为后续逐项讨论和修改的主文档，当前为讨论稿。本页保留宏观交付目标；工作拆分和顺序经讨论确定后同步到此，不将下面的阶段标签当作另一套独立工程清单。

实现顺序按依赖组织，不缩减已经确认的资产、组合支付、任务或商户功能。任何对外开放的资金路径必须同时具备异常恢复和资金核对，不能先上线正常支付再补退款与未知交易处理。

## 阶段与交付结果

| 阶段 | 工作 | 完成条件 |
| --- | --- | --- |
| D0 项目定义与原型 | 维护规则和本版方案，绘制用户及后台关键路径 | 六条体验路径覆盖正常、等待和恢复；入口与资金理解问题有记录 |
| D1 身份与账本基础 | 产品身份、外部身份、主体隔离、金额约定、幂等、凭证、冻结、查询与事件 | 余额互转原子完成，重试不重复，对账与审计基础可用 |
| D2 任务与奖励 | 任务类型接口、资格、首奖、关系、分成、Pro、抽奖、奖励转入 | R01–R12 确定性验证，实际任务至少一种完成真实接入 |
| D3 TON 钱包与通道 | Mini App 同设备钱包、密钥保护、资产查询、到账关联、代付、充值与出金 | TON 与 USDT 各自正常及异常路径验证，不能用模拟支付代替通道证据 |
| D4 商户与支付 | 企业商户、手工及 API 开单、三种支付、可靠通知、退款、人工结算 | S14–S30 全部适用路径和并发占用约束通过 |
| D5 运营与发布准备 | 审核、异常、对账、归集、监测、恢复演练和发布参数 | 每个异常有资金结果与责任路径，未落实事项不被当作已开放 |
| D6 独立 App 扩展 | 确定客户端技术栈，扩展 Base、Solana、TRON 与对应资产 | 各客户端、网络、资产逐项验证，不按钱包品牌推断兼容 |

D2 和 D3 的设计可并行，资金能力仍依赖 D1。D4 可以先实现纯余额，再链上和组合，但正式开放的订单必须同时具备对应退款与异常处理。没有具体业务任务时先实现可验证的任务适配结构，不能编造真实任务已上线。

## 原型交付顺序

1. 钱包、奖励、记录三个主要页，明确四类账户及进度。
2. 目标识别与通用确认，贯通账户互转、本人和代充值、链上转出。
3. 首任务、老用户助力、Pro、抽奖和奖励转入。
4. 三种订单支付、外部钱包返回、部分支付和退款。
5. 商户开单与结算、平台审核与集中异常详情。

原型观察用户是否知道实际扣款与到账位置，是否把签名完成当作支付成功，是否在超时后重复付款。原型结果决定界面调整，资金规则不能为了减少步骤被省略。

## 开发前必须具体化的产物

| 范围 | 产物 |
| --- | --- |
| 数据与契约 | 权威 API 源、金额与 idx 表示、DDL 与索引、生成版本和可重复命令 |
| 钱包 | 各客户端密钥存储与备份恢复方案、外部会话与跳转验证记录 |
| 每条资金通道 | 真实资产标识、归属方案、确认和失效证据、费用与代付、替代和回滚处理 |

| 奖励运营 | 实际任务类型、验证策略、到期与参与资格、动态转入条件、抽奖发布版本 |
| 运维 | 监听缺口恢复、未知出款告警、对账差异、签名工具权限、备份恢复和责任分配 |
