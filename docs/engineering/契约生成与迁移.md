生成在临时目录进行，复制 module、源定义及 goctl.yaml，使用固定版本工具的干净内置模板；正式 platform API 再加载仓库内的 [main 模板](../../backend/template/api/main.tpl)、[handler 模板](../../backend/template/api/handler.tpl)和 [context 模板](../../backend/template/api/context.tpl)，其余模板与隔离示例仍沿用上游。显式固定 `GOCTL_EXPERIMENTAL=on` 与临时 GOCTL_HOME/TMPDIR，不读取个人模板。TS 产物只规范化末尾换行，不替换字段或类型。goctl 会格式化输入及创建备份，因此仅向它提供临时副本。缺少配置或 DECIMAL 生成结果退回浮点时失败，实际源文件和产物不变。

正式 handler 模板直接使用 go-zero 的请求解析，并接入项目统一错误与 JSON 输出；context 模板只生成共享 `svc.ServiceContext` 的类型别名；main 模板接入共享上下文、启动取消与原生服务生命周期，避免重新生成入口后退回不兼容的默认构造方式。module 使用 goctl 的 `projectPkg` 参数，API 目录占位符由生成入口的 `PLATFORM_OUT` 派生，不硬编码原项目路径。模板不增加响应包装，成功响应仍须符合 `.api` 的完整类型。新增鉴权或业务中间件时，在共享上下文注册所需依赖和字段，不在别名文件创建第二份客户端。正式 main/context 已直接使用共享配置，生成器丢弃无引用的默认 internal/config 骨架；隔离示例的配置仍由其独立入口使用并保留。

更新前检查整批结果；纯生成区的本地手改会阻止覆盖，旧的纯生成文件按登记清单清理。已有 handler/logic/config/svc/main/model 扩展不覆盖，旧手写骨架须明确处理后再生成。检查包含未跟踪的额外生成文件；不以单次 git diff 代替完整比较。文件写入遇到磁盘异常时应检查差异后重跑，不承诺多个文件的写入是文件系统原子事务。

目前直接 TS 链明确拒绝 `.api` 指针及 interface{}，不假装支持 JSON null。示例可选字段缺省时省略，金额保持字符串，数组输出 []。未来业务若必须区分缺省与显式 null，应补充契约表示和生成能力验证；不能改成 any 或仅依靠类型断言。类型检查不会替代服务端输入校验或权限校验。

## 生成与不依赖数据库的检查

以下命令在仓库根目录执行；检查前应在当前 shell 切换到上述 Node/pnpm 版本：

```sh
python3 scripts/generate.py
python3 scripts/generate.py --check
bash scripts/check_contracts.sh
python3 scripts/check_docs.py
git diff --check
```

generate 仅处理登记的示例源、user/backoffice/account SQL 与正式 platform API 源，不连接 MySQL/Redis/RocketMQ；--check 不修改源码或已提交产物。check_contracts 执行生成差异检查、生成行为测试、Go 编译/单测及共享 TS 严格类型检查。Go 测试不含带 integration 标签的真实数据库用例。

增加业务源时应扩展生成输入与输出归属，保持 module/path 参数化，不将例库清单改成递归扫描所有 SQL。生成产物与源同次提交；数据库变更同时更新完整 DDL 与编号迁移。已执行迁移保持不可变，用新文件修正。

## 显式迁移

迁移入口为 [backend/tools/migrate](../../backend/tools/migrate/main.go)，从 `backend/` 执行。通过本地环境或凭据管理注入 `DEXWALLET_MYSQL_DSN`，使用 MySQL Go driver DSN 格式且包含目标库名；不要把值写入仓库。examples 与 business 均须通过测试目标保护：`DEXWALLET_TEST_ENV=local`、显式回环 `DEXWALLET_TEST_MYSQL_ADDRESS`、`dexwallet_test_admin` 账号及 contract 前缀库；准备见 [开发与测试环境](开发与测试环境.md)。工具同时要求显式目标数据库，两者必须一致。

当前有 examples 与 business 两个显式集合，允许作用于预先建立的 `dexwallet_contract_` 前缀测试库；以下库名只是命令示例，工具不会自动建库：

```sh
go run ./tools/migrate --source examples --database dexwallet_contract_dev --action up
go run ./tools/migrate --source examples --database dexwallet_contract_dev --action version
go run ./tools/migrate --source business --database dexwallet_contract_dev --action up
go run ./tools/migrate --source business --database dexwallet_contract_dev --action version
```

up 无待执行文件时保持成功且显示当前版本；不在生成或应用启动时执行。迁移失败会返回非零并保留 dirty/version 状态；没有自动 force/down。MySQL 的部分 DDL 可能已经提交，应先核对实际结构再修复。数据库连接密码只由环境传入，不作为 CLI 参数打印。business 版本表为 schema_migrations_business，examples 保留 schema_migrations。正式部署入口归 8.2，两个集合的当前 CLI 均不得指向生产库。

## 独立 MySQL 验证

从 `backend/` 执行，先通过环境注入 `DEXWALLET_TEST_MYSQL_DSN`。测试凭据必须使用 [开发与测试环境](开发与测试环境.md) 的受限账号、目标允许地址及 local 环境；只授予 contract 前缀库权限。测试始终创建随机 `dexwallet_contract_` 前缀库，不使用 DSN 原有库作为测试对象：

```sh
go test -tags=integration ./tests/integration -v -count=1
```

测试创建三个专属库，对比空库迁移、带旧数据升级与完整 DDL；验证 decimal 精确往返、NULL/零区分、WithSession 回滚、DDL 部分成功后 dirty 状态与重试阻止。测试正常退出时清理自身创建的库；进程被强杀时需依据该前缀及当次记录核对残留，不能清理其他项目数据库。

本轮复用用户现有 Docker MySQL，服务报告 9.4.0；验证只覆盖该实例，不锁定生产 MySQL 版本。Redis/RocketMQ 未接入或修改。详情见 [实施记录](../design/工程工作记录/01-工程基础/1.2-契约与代码生成/03实施记录.md) 和 [验证记录](../design/工程工作记录/01-工程基础/1.2-契约与代码生成/04验证记录.md)。
