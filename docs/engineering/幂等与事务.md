## 内部入口

[transfer.Service](../../backend/logic/transfer/service.go) 由共享 ServiceContext.Transfers 组装，复用 MySQL、transaction.Runner 和 Accounts。调用者负责先认证，再传入可信 user.Actor；数值用户 ID 本身不代表授权。对外业务 ID 继续通过已有 Transfer 类型编码为 idx。

| 入口 | 行为 |
| --- | --- |
| Submit(ctx, actor, request) | 提交本人美元互转；Request 包含 Key、RecipientID、精确十进制 Amount；返回已提交原单及凭证 |
| FindByRequest(ctx, actor, key) | 查询本人发送的原单；从同一主库读取，不使用 Redis 或只读副本 |

请求号为 16–64 位 ASCII 字母、数字、下划线或短横线，区分大小写；调用方生成足够随机的值，同一次操作始终沿用。发送方与请求号唯一，单据没有短期过期清理。金额为正数且最多两位小数，10 与 10.00 是相同参数；收款人与金额任一变化返回冲突。已有单据只读恢复，不再调用 Post。

本步没有 API 契约、HTTP 错误码映射或自动重发客户端。后续接入必须把认证用户作为 actor，不能接受客户端指定付款人；将领域错误映射到已有响应规范，同时保留“未知”的语义。

## 事务和权限

按用户 ID 升序锁双方用户并复核发送方状态/auth_version，随后查请求号。新单还需收款人存在、启用且不是本人。再插入转账单，调用 [Post](账本与流水.md) 完成双方余额与账本，最后补齐凭证、追加 transfer.completed 事件并一起提交。3.5 起事件与账务不可分离，消息发送在提交后独立进行；事件写入失败回滚整笔转账。顺序为用户 → 单据 → 按既有顺序锁账户；数据库等待受 context 与数据库超时控制。

已提交转账不会因为收款人后来被禁用而改变结果；发送方重新提交和查询仍须满足当前身份授权。首次普通查单未找到不能证明之前的操作未执行。重提时先等待用户行锁，使原事务结束，再查询原单；数据库联合唯一和账本来源唯一继续作为持久约束。

transfer_order.voucher_id 在同一未提交事务中可暂时为空，最终必须补齐；不保存可见的 processing 单据。查询异常的缺凭证单据返回未知，不返回成功。所有 Post/单据错误必须向外传播；不捕获余额不足后继续提交半张凭证或失败回执。

## 错误与恢复

| 结果 | 行为 |
| --- | --- |
| ErrInvalidRequest | 请求号、主体、收款人或金额不合法，未写入 |
| ErrRequestConflict | 已有请求号对应不同收款人或金额，不执行新记账 |
| ErrRecipientUnavailable | 新转账目标不存在或禁用 |
| user.ErrDisabled / ErrStaleSession | 当前发送方无权操作 |
| account.ErrInsufficientBalance | 可用余额不足，整个事务回滚 |
| ErrBusy | 1205 超时或已用完一次 1213 重试；保留原始 MySQL 错误，后续沿用原号 |
| ErrOutcomeUnknown | 提交应答未知且未恢复原单，或发现缺凭证的异常单据；保留原因并继续原号恢复 |
| ErrNotFound | 当前主库没有可见原单，不能据此认定前次失败或生成新请求号 |

业务层最多自动重试一次已确认回滚的死锁 1213，每次完整复核当前授权。锁超时 1205、余额不足、其他系统错误及回滚清理异常均不自动重试。公共事务入口没有增加自动重试；清理异常保留原始 Failure，不降格为普通繁忙。

提交结果未知后尝试原号查主库：已完成且参数相同则返回原单；未找到、读取失败或原 context 已取消则继续返回未知，不自动再次执行资金事务。后续原号重提受到数据库事务与唯一约束保护，即使原事务仍在提交也不会重复扣款。

明确回滚的失败不保存永久回执，后续同键同参可以重新检查余额并成功；参数未落库时没有持久的异参比较依据，调用方仍不得修改原键含义。重试、未知提交恢复日志保留主体/原单与原因，不把基础设施失败伪装为普通成功值。
