# 开发与测试环境

本页是 1.5 的实际运行入口。宿主机运行 Go API 与三个 Vite，复用已有 Docker MySQL/Redis/RocketMQ；本地不需要 Nginx。工程已有健康接口、隔离契约样例及 2.1 用户模型、2.2 内部鉴权、2.3 公开登录与 JWT；启用配置见 [用户鉴权](用户鉴权.md)。3.1 已接入本人余额查询，3.2 已增加内部账本写入与本人流水；尚无公开资金写入或业务消息消费者。

## 工具准备

使用 [工程结构](工程结构.md) 中的锁定版本。当前为 Go 1.26.10、Node 24.22.1、pnpm 10.33.4；Go 可由 module/toolchain 自动选择。先在当前 shell 按 `frontend/.nvmrc` 切换 Node，再执行：

```sh
# 仓库根
python3 scripts/prepare_tools.py
cd frontend
pnpm install --frozen-lockfile
pnpm exec playwright install chromium webkit
```

Linux 浏览器系统库按 Playwright 的明确提示准备。检查脚本不自动升级依赖、修改锁文件或安装系统包。Go 等工具可能下载锁定依赖；复用下载缓存不等于复用旧构建产物。

## 本地数据库与账号

首次准备在仓库根显式执行：

```sh
python3 scripts/prepare_local.py
source .tools/local.env
```

该工具只进入已有本地 `mysql` 容器（要求 host 网络），通过容器内 root socket 显式建库和授权，不输出 root 密码、不重建容器或数据卷。Docker 普通权限不可用时使用 `sudo -n docker`。工具不接受远端参数；本地容器必须是明确的开发服务，不能将生产服务或生产转发伪装成本地目标。

| 用途 | 库/账号 | 权限与生命周期 |
| --- | --- | --- |
| 日常开发 | `dexwallet_dev` | 仅该库 SELECT/INSERT/UPDATE/DELETE；长期保留，不自动建业务表/迁移/清空 |
| HTTP 集成 | `dexwallet_test_http` | 独立账号，仅该库 SELECT；当前健康探测只需连通，长期保留，不被测试清理 |
| 契约/中间件集成准备 | `dexwallet_test_admin` | 仅转义后的 `dexwallet_contract_` 前缀库的 SELECT/INSERT/UPDATE/DELETE/CREATE/DROP/ALTER/INDEX/REFERENCES；无全局管理权限、不允许创建用户 |

凭据随机生成，保存在忽略的 `.tools/local.env`，权限 0600。脚本发现文件或保留账号/库已存在会拒绝重新初始化，不覆盖密码或接管已有库。中断时 `.tools/local.env.pending` 保留本次凭据，需核对本次创建的对象后继续处理，禁止直接批量重置。已有环境也可手动提供同等受限账号；不得使用 root/生产账户冒充测试账户。

配置变量及含义：

| 变量 | 用途 |
| --- | --- |
| `DEXWALLET_TEST_ENV=local` | 明确选择本地测试；其他值在连接前拒绝 |
| `DEXWALLET_TEST_MYSQL_ADDRESS=127.0.0.1:3306` | 显式允许的字面回环 IP/端口，DSN 必须精确匹配；不解析域名，不接受远端目标 |
| `DEXWALLET_TEST_MYSQL_DSN` | 测试准备账号，无默认库；只用于独立后端 integration 和恢复清理 |
| `DEXWALLET_TEST_HTTP_MYSQL_DSN` | HTTP 测试的指定库、受限账号；与准备账号分开 |
| `DEXWALLET_MYSQL_DSN` | 日常 API 的开发库连接；HTTP runner 会仅对本次子进程替换为上述专用连接 |
| `DEXWALLET_ID_SECRET` | 必填的稳定 idx 密钥，16/24/32 字节；prepare_local 首次准备会保存随机值；已有配置需单次补齐，不能每次启动生成 |
| `DEXWALLET_REDIS_PASSWORD` | 本机 Redis 如有认证，由环境显式提供；不扫描其他项目配置 |

2.1 的外键测试需要测试账号在原有转义 `dexwallet_contract_` 库范围内拥有 REFERENCES；本轮已为本机既有测试账号补齐，prepare_local 的新环境授权也已更新，开发/HTTP 账号权限不变。

目标校验也用于直接运行的后端 integration、示例迁移及前端 integration，不只存在于统一脚本。账号/地址/环境字符串是误配置防护，真正隔离来自数据库授权和生产独立访问边界；测试工具不应获得生产凭据。当前入口明确限于本地拓扑，远端 CI/生产网络边界在 8.2 单独配置。

## 日常启动

在已载入开发配置的 shell 中，分别运行：

```sh
# backend/
go run ./api -f api/etc/platform.yaml
# frontend/，分别在独立终端运行
pnpm dev:user
pnpm dev:merchant
pnpm dev:admin
```

API 为 127.0.0.1:8888，三端开发服务监听 0.0.0.0:5173/5174/5175，浏览器使用开发机的局域网 IP 访问（例如 http://172.16.0.102:5173/），不要把 0.0.0.0 当作访问地址。共享 Vite 原生代理精确匹配 `/api` 路径边界、去掉前缀后转发，`DEXWALLET_API_PROXY_TARGET` 可显式指定本地后端。用户端 Hash Router，后台 History Router。启动不隐式迁移；生产构建不包含开发页面。

当前账户、占用、内部互转及后台任务要求 business 数据库版本 9；000004–000009 仅在隔离库验证，共享开发库未升级。部署本版前按显式迁移流程升级，不能通过启动或查询临时创建缺失表。已知种类没有账户行时返回零，与表未迁移导致的数据库错误不同。交付范围见 [账户模型记录](../design/工程工作记录/03-资金账户与账本/3.1-账户与金额模型/03实施记录.md) 、[账本与流水](账本与流水.md) 、[幂等与事务](幂等与事务.md) 与 [持久化后台任务](持久化后台任务.md)。

### 在浏览器体验 Telegram 登录

用户端提供独立的 `pnpm dev:user:tg`：复用已安装 SDK 的 `mockTelegramEnv`，将模拟启动材料注入前端 Telegram 上下文，随后走正式 `/v1/user/auth/telegram/login`。用户、身份、产品 JWT 与昵称修改均来自真实 API 和数据库，不拦截或伪造 API 响应。

先按 [用户鉴权](用户鉴权.md) 配置本地后端，使用已应用 business 迁移的开发数据库、Redis、稳定的 idx/Auth/Session 密钥，并启用 `Session: {}`、`Auth.TelegramEnabled: true`、`Auth.TelegramDevelopment: true`；最后一项只允许在 `Environment: local` 且 `Mode: dev` 时开启。只体验 TG 时可设置 `Auth.EmailEnabled: false`，不需要 SMTP。后端和 Vite 必须使用同一个开发 Bot token；无需真实 Telegram Bot，可在两个启动终端都设置：

```sh
export DEXWALLET_TELEGRAM_BOT_TOKEN='123456:local-telegram-development-only'
# 后端终端：载入其他开发配置后，按上方日常启动命令运行 API。
# 前端终端：
cd frontend
nvm use
pnpm dev:user:tg
```

打开 `http://127.0.0.1:5173/` 或 `http://<开发机局域网 IP>:5173/`，无现有登录态时自动使用 TG ID `900000001`、用户名 `dexwallet_local_dev`、名称“开发体验 用户”、中文语言登录。已有产品登录态按正常流程保留，不强制切换账户；需要重新体验登录时退出后在新标签页打开上述地址。刷新恢复同次启动与原页面；缺少 Web Locks 的局域网 HTTP 环境使用内存登录，刷新可能重新交换凭证。主动退出后刷新不自动登录。开发 TG 授权永久有效、可以重复使用，不做自动刷新授权；缓存很久的启动材料也能直接登录。每次新登录使用新的请求令牌，同一次失败重试保留原令牌和材料。开发界面不再显示授权过期提示。

签名由 Vite Node 进程的开发中间件生成，Bot token 不进入浏览器变量或产物；浏览器只取得签名后的 initData。普通 `pnpm dev:user` 不注入、不启用该中间件；缺少 Bot token 时模拟模式启动直接报错。真实 TG 启动参数优先，不覆盖真实启动。生产 build（包括 `--mode telegram`）不包含注入模块，preview 不提供签名接口。此入口不模拟尚未实现的任务、奖励、钱包或 Telegram 原生交互能力。当前本机后端配置保存在忽略的 `.tools/platform-telegram-dev.yaml`，配合 `.tools/local.env` 与 `.tools/telegram-dev.env` 启动；开发 TG 限流阈值已放宽为 10000/小时，正式默认不变。

局域网 HTTP 开发兼容：认证代次和启动编号复用原生 `crypto.getRandomValues` 生成随机令牌；缺少 `crypto.subtle` 时，仅开发构建动态加载 `@noble/hashes` 2.0.1 的 SHA-256 来计算启动指纹，不自行实现哈希算法。该库按[官方用法](https://github.com/paulmillr/noble-hashes#usage)使用，作为用户应用开发依赖锁定；生产构建保持原生 Web Crypto，模块边界检查阻止开发回退进入产物。

## 检查入口

仓库根执行 `bash scripts/check.sh [范围]`：

| 范围 | 内容 | 真实服务 |
| --- | --- | --- |
| `common`，默认 | 文档/差异、生成漂移与生成行为、Go race/vet、前端类型/单测/构建 | 无 |
| `browser` | 构建后执行 Chromium/WebKit 的既有交互/路由/产物隔离用例 | 无；API fake |
| `integration` | 隔离 MySQL 迁移/事务、账号权限、强杀恢复、Redis 往返、MQ 真正收发和清理 | 本地 MySQL、Redis、RocketMQ |
| `http` | 构建 API 和三端，通过 Vite dev/preview 验证 live/ready、traceId、404、路由刷新与停服恢复 | 专用 HTTP 测试 MySQL；Redis/MQ 在本次 HTTP 配置中关闭，另由 integration 验证 |
| `all` | 顺序执行以上四项 | 完整本地环境 |

原有 Go/pnpm/契约检查仍可独立运行。真实依赖用例不在普通 `go test ./...` 中执行；明确选择真实范围但缺少配置会非零退出，不静默跳过。每次执行输出所选范围、各阶段结果及 `.tools/check-runs/run-*/` 日志/汇总路径；前序失败时后续不计通过。浏览器/HTTP 独立入口总是先构建当前代码。

浏览器占用 5173–5175 和 4173–4175，HTTP 另使用 18888。固定端口的检查串行执行；冲突即失败，不结束或复用日常服务。HTTP 在 `.tools/http-runs/run-*/` 保存 API 二进制、无凭据配置和日志；Playwright 失败证据在 `frontend/test-results/`。API 收到 SIGTERM 正常退出；runner 只回收自己创建的进程组。

## 资源清理与故障恢复

后端真实测试每次生成随机 run ID，并在 `.tools/test-runs/<run-id>/resources.json` 登记确切资源名和 MySQL 目标，先记录意图再创建。数据库、Redis key、MQ topic/消费组均带运行标识；Redis 临时 key 有 TTL。正常结束先关闭客户端再清理本次资源，开发库和长期 HTTP 测试库始终保留。

MQ 使用锁定的 Apache Go SDK 创建 topic、生产和消费消息；其公开 admin API 没有删除消费组操作，因此复用本机 `rmqbroker` 镜像中的官方 `mqadmin deleteSubGroup -r true` 清理组和 offset，并清理确切的 retry/DLQ/topic。入口为 [mqadmin-local.sh](../../scripts/mqadmin-local.sh)，当前适配本机 RocketMQ 5.3.2、127.0.0.1:9876/10911。Redis 固定本机 6379、DB 0；迁移其他拓扑前需明确配置及复验，不能自动猜测远端。

失败/超时/中断保持非零。统一 integration 包装会在子进程结束后依据清单尝试恢复；整组进程被强杀或机器断电不能保证自动收尾。核对清单后，从 `backend/` 执行：

```sh
# RUN_DIRECTORY 替换为输出的确切目录，不使用 glob 或前缀扫描。
go run ./tools/testenv cleanup /absolute/path/.tools/test-runs/RUN_DIRECTORY
```

恢复要求与清单一致的测试地址和凭据，资源名必须属于该 run ID；运行中的 suite 持有文件锁，恢复工具拒绝并发清理。每清理成功一项即持久化剩余项；失败保留清单并返回非零，可针对同一清单再次恢复。日志/空清单作为本地证据保留，不自动删除用户文件。

直接运行后端测试的等价入口为 `backend/` 下的 `go run ./tools/testenv run go test -tags=integration ./tests/integration -v -count=1 -timeout=180s`。直接 `go test -tags=integration ...` 也有目标校验和正常退出清理，但无外层强杀恢复；中断后按清单恢复。
