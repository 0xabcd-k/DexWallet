# 任务领奖与奖励结算

4.2–4.5 已实现本地 mock 任务的完整领奖链路：当前绑定核验、首奖、任务积分、Pro、任务邀请、单层分成、原子入账及原请求恢复。关注成员查询继续使用 mock，正式 Telegram 频道尚未接入；mock 模式只能在 local/dev 启用，不能视为真实频道或生产开放验收。

## 运行准备与迁移

数据库要求 **business 12**，从 11 使用 [000012 增量迁移](../../backend/manifest/sql/diff/business/000012_task_rewards.up.sql)。[完整 DDL](../../backend/manifest/sql/ddl/task/tables.sql) 与 [约束](../../backend/manifest/sql/ddl/task/constraints.sql) 同步维护。迁移不自动执行，本轮只在 testenv 创建的独立数据库验证，未升级共享开发库或生产库。

新增 user_reward_state、task_invitation、user_referral、reward_grant，扩展已有 task_completion。历史完成保留 rule_version=0，不能被解释为新用户或自动补发；存在旧完成却无可证明奖励状态时返回 TASK_HISTORY_UNKNOWN。上线前检查这类记录及历史内部奖励凭证，不用调大业务 ID、清空数据或猜测补账来绕过核对。测试中的旧账本独立夹具与新奖励编号单独隔离。

降级脚本在存在奖励、关系、进度或已分享邀请时拒绝删除数据。与既有迁移一样，拒绝后的 dirty 标记与 guard 表需要按实际结果人工核对；不要直接 force 版本或重跑下迁移。

本地样例准备和成员夹具沿用 [任务基础](任务基础.md)，工具只创建任务，不创建奖励或伪造已验证身份。配置仍为 Tasks.Mode: mock 与明确的频道/TG 用户对；真实 Bot token 不需要提供。邀请链接复用既有 Transfer.WebURL 和可选 Transfer.TelegramURL 作为用户端入口；服务端未配置公开入口时，本地页面使用当前站点的干净地址，不把启动查询参数带入分享链接。

## 已实现接口与页面

全部接口要求产品 JWT，交易用例重新读取当前数据库身份和认证版本。契约源为 [platform.api](../../backend/manifest/api/platform/platform.api)，Go 与 TS 均由它生成。

| 接口 | 行为 |
| --- | --- |
| GET /v1/user/tasks/:idx/claim-preview | 本人/助力资格、阶段、本人收益预估、任务和身份版本；不查询成员、不占次数 |
| POST /v1/user/tasks/:idx/claim | 检查关注并原子结算；请求包含 requestKey、mode、invitationIdx 及预览的 expected 版本/阶段 |
| POST /v1/user/tasks/:idx/invitation | 首任务已完成者创建或返回一条任务专属邀请；同任务同邀请者唯一 |
| GET /v1/user/task-invitations/:idx | 解析有效邀请的任务与公开邀请者资料，不建关系、不领奖 |
| GET /v1/user/task-completions/by-request/:requestKey | 当前用户原请求的已提交结果；404 不证明未执行 |
| GET /v1/user/task-completions | 本人完成历史，taskIdx 可选，before 游标及 limit（默认 20，最大 100） |
| GET /v1/user/task-completions/:idx | 本人历史完成及本人奖励，换绑不改变历史归属 |
| GET /v1/user/reward-grants/:idx | 实际受益人自己的奖励、进度快照与凭证编号；其他人不可查 |
| GET /v1/user/reward-summary | 首任务状态、Pro 进度、直属好友数、有效助力数与两类积分统计 |

既有 /check 保持只读。任务返回 rewardsAvailable 表示服务已接入结算，claimAvailable 表示当前资格允许领奖；不能把后者为 false 一律解释为功能尚未实现。

用户端 /tasks/:idx 提供检查、领奖、邀请与恢复；受邀页显示邀请者并要求明确确认资格消耗，新用户还确认建立关系。登录和绑定返回保留任务及邀请参数；本人邀请由后端归为本人任务。Mini App 的 task_ 加邀请 idx 启动参数先解析到具体任务，与收款码入口分开处理，不凭启动参数登录、绑定上级或自动发奖。

/task-completions 及详情展示历史完成；/reward-grants/:idx 从账单奖励来源进入；奖励首页补充 Pro 与邀请统计。已完成结果只展示当笔事实，不继续把下一次预估收益混在结果下方。全部新增固定文案使用中英文资源。

## 奖励与事务

[奖励计算](../../backend/logic/task/rewards.go) 采用纯函数：首任务 $1 进入 reward_usd，并增加 1000 Pro 进度，不增加可消费积分；老用户任务/助力积分按实际受益人结算前 Pro 翻倍，累计 2000 永久解锁，当笔跨门槛不翻倍。实际任务积分受益人的上级得到向下取整的 20%，不递归、不再翻倍、不增加 Pro。

用户在审阅方案后要求继续实施，以下边界随方案落实：老用户助力者恰好是邀请者上级时，仍得既有关系的分成，不得本人直接任务奖励；禁用上级保留被动分成入账，但不能登录、主动参与或作为新助力的邀请者。

[结算入口](../../backend/logic/task/claim.go) 在事务外查询成员，事务内按用户 ID 升序锁参与者与全部受益人，复查当前会话、阶段、绑定版本、邀请关系与任务有效期。任务定义使用共享读锁；同受益人的 Pro 更新串行化，不设置全局资金锁。完成记录、次数消耗、首奖、关系、全部 reward_grant、公共 account.Post 凭证和 Pro 同一事务提交，失败全回滚。

每份奖励以 BusinessReward 与 reward_grant ID 作为账本来源，按 USD/POINT 分别平衡；进度独立于可消费积分。记录保存任务版本、标题、规则版本、金额及进度快照。旧助力者若没有本人收益，不伪造零金额流水；当前 Pro 从概览另查。

## 幂等与恢复

同用户同请求键比较完整请求语义，一致则返回原完成，不重新发奖；不同参数返回 TASK_REQUEST_CONFLICT。稳定 TG 身份与任务唯一约束阻止换请求键、解绑换绑后重复参与。并发首任务只能有一笔首奖，旧 first 预览不能自动变为 returning 助力。

前端在发起前保存原请求，按 API 服务和用户隔离，以短时 Web Lock 协调多标签。重开后显示查询/重试原请求入口，查询未找到保持原请求。提交结果未知保留原键；服务器仅对确认回滚的死锁最多重试一次。网络、权限或成员查询异常不会被伪装成未关注或已完成。当前不存在“完成后异步补发奖励”队列。

明确上下文变化需先核对原请求再重新展示收益和确认；最终后端仍复查版本。响应中的本人结果与当前任务、本人/助力模式、首任务阶段不匹配时，前端保留请求而不标记成功。
