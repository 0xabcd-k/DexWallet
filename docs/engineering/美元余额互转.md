# 美元余额互转与个人收款码

3.6 已接通个人收款码、扫码/idx 互转、付款确认、原单恢复、双方账单、限额方案和换绑付款限制。用户端使用现有 H5/Mini App 工程；没有新增付款密码或每笔验证码。数据库要求 **business 10**。实现范围和验证见 [3.6 工作记录](../design/工程工作记录/03-资金账户与账本/3.6-美元余额互转与账单/03实施记录.md)。

## 入口与契约

源定义为 [platform.api](../../backend/manifest/api/platform/platform.api)，Go/TS 类型由现有生成链产生。

| 入口 | 行为 |
| --- | --- |
| 用户端 `/#/receive`、GET `/v1/user/receive-code` | 本人摘要、静态签名码、H5 和可配置 Bot 分享链接；无固定金额 |
| 用户端 `/#/pay` | 打开相机扫码，可切换手动 idx 或粘贴收款码/链接；金额由付款人填写 |
| POST `/v1/user/transfer-targets/resolve` | idx/收款码二选一，返回真实目标摘要，不返回邮箱、TG ID 或余额 |
| GET `/v1/user/transfer-policy` | 当前方案、今日用量、剩余额度、UTC 日界和换绑限制到期时间 |
| POST `/v1/user/transfers` | requestKey、recipientIdx、金额字符串；付款人来自产品 JWT |
| GET `/v1/user/transfers/by-request/:requestKey` | 仅付款人按原请求号恢复；查无记录不代表未执行 |
| GET `/v1/user/transfers/:idx` | 仅双方可读，返回本人方向、对方 idx/昵称快照、金额、零费用、完成时间 |
| 既有 `/v1/user/account-entries` | 继续复用双方流水，转账来源可进入详情 |
| POST `/v1/user/identities/impact` | 绑定目标的影响预览；邮箱规范化、TG 服务端验签，不消费 TG proof |
| `/v1/admin/transfer-limit-plans` GET/POST | 平台管理员分页查询、按管理请求号幂等创建不可变方案 |
| `/v1/admin/users/:idx/transfer-limit-plan` GET/PUT | 查看/分配方案；写入须带 expectedPlanIdx 和原因 |

管理端 `/limits` 管理方案，`/users` 查询用户后分配。商户身份及产品 JWT 不能使用管理接口。后台在写事务内复核最新管理员状态、认证版本和改密要求，分配与审计一起提交。

## 资金事务与限额

沿用 [幂等与事务](幂等与事务.md) 的锁顺序和原子记账。锁双方用户后先复核付款权限、查找同键原单；已成功且参数一致的原单优先返回，不重新计算限额、冻结或收款人可用性。新单再检查换绑限制、当前方案、当天成功转出毛额与可用余额。单据、两边余额、凭证分录和完成事件一起提交。

默认种子方案 ID=1：最低 0.01 USD、单笔 100.00 USD、每日 500.00 USD。金额只接受正的十进制字符串，最多两位小数，不接受科学记数或隐式舍入。方案创建后没有原地修改接口；调整通过新方案和用户分配完成。切换方案保留当天已用金额，剩余不得小于零。新单保存采用的方案 ID 与双方昵称快照；旧历史不伪造昵称。

数据库 UTC 时刻在用户锁后读取一次，同时用于当日区间和单据 created_at；查询使用 `(sender_id, created_at)` 索引。正式连接和隔离测试连接均配置 UTC。限额覆盖美元互转，不自动扩展到以后商户或链上业务。

并发分配与付款共用用户行锁。管理端 expectedPlanIdx 变化返回冲突；重复分配当前同一方案不重复记有效变更。方案创建以管理员 ID + requestKey 唯一，同号异参冲突。

## 付款确认与恢复

核对目标、金额、美元余额来源、零费用、限额及限制后才可确认。余额不足标红；登录返回、扫码和打开弹窗不扣款。纯余额互转没有链上钱包抽屉。

提交前将 requestKey/recipientIdx/amount 保存到浏览器本地存储，按会话 issuer 和本人 idx 分隔，不复制登录凭据。短 Web Lock 协调同一来源的多个页面创建待确认请求，锁内不发网络请求；缺少可靠存储、安全上下文或 Web Locks 时拒绝新提交。浏览器清除站点数据会丢失本机恢复信息，因此服务器账单仍是最终事实来源。

断网、超时、协议异常或未知结果保留原号。重开页面先查原号，查无记录继续提示未知；用户核对后可以沿用原号继续。曾经未知的付款不会因为后来查询失败或权限变化而被自动抹掉。成功响应还须匹配原收款人、金额和方向才清理本机恢复记录。金额/目标变化需重新核对；同键不改参数。

## 收款码配置与解析

在 [platform.yaml](../../backend/api/etc/platform.yaml) 配置：

```yaml
Transfer:
  DefaultLimitPlanID: 1
  WebURL: https://wallet.example.com/
  TelegramURL: https://t.me/your_bot/your_app
```

另以环境变量 `DEXWALLET_RECEIVE_CODE_SECRET` 提供独立的至少 32 字节密钥，不复用 JWT、验证码或 idx 密钥。WebURL 必须是准确部署基址，无 query/fragment；HTTPS 为正式入口，本机允许 localhost/127.0.0.1 的 HTTP。TelegramURL 必须准确指向官方 Bot/Mini App。没有配置收款码密钥与 WebURL 时，收款码接口明确返回服务不可用；idx 互转不依赖此配置。默认方案配置仅影响后续新用户，必须指向数据库中已存在的方案。

码为 `base64url(JSON([1,"account",idx,mac]))`，HMAC-SHA256 绑定版本、类型、idx 和环境，MAC 完整保留。原始码最长 512 字符，无 padding。服务器只接受原始签名码或精确匹配配置的链接；拒绝未知类型/版本、多余字段、附加金额、重复参数、篡改、其他域名/路径/Bot，不读取任意 URL。更换密钥使旧码失效。

Telegram startapp 在前端仅作为路由提示，后端仍验证收款码。非收款用途的已有启动参数保留其生命周期，不擅自当付款。有效收款码也可能被替换为另一个人的有效码，所以确认页必须展示实际 idx 和昵称。

二维码生成使用 [node-qrcode](https://github.com/soldair/node-qrcode)，浏览器相机识别使用 [ZXing browser](https://github.com/zxing-js/browser)，均按锁文件固定依赖。相机不可用时保留手动入口；手机真实相机权限和原生 App 扫码仍需设备验收。

## 换绑限制与历史回填

user 保存 identity_revision、最近邮箱/TG 身份 ID、payment_restricted_until。任何实际绑定变化增加 identity_revision；解绑保留最近身份。首次绑定、恢复最近原身份不新增限制；直接 A→B 或解绑 A 后绑 B，均在身份写事务里设为 `max(原限制, 数据库当前时间+24小时)`，并轮换 auth_version。单纯解绑仍沿用已有认证版本轮换，但不新加付款限制。收款/查账不受冻结影响，已有单据仍可恢复。

邮箱/TG 绑定提交新增 expectedRevision 和 expectedReplacement，须先查询影响并展示提醒。事务重新判断目标与基线，不信任前端确认位作为身份凭据。预览只返回本人的换绑影响，不公开目标邮箱是否属于其他账户；归属冲突在验证身份后的写入中检查。预览不替代原邮箱验证码或 TG 签名。返回 token 的可选 restrictedUntil 字段和 policy 接口给出实际限制时间；昵称修改不能改限制。

[000010 迁移](../../backend/manifest/sql/diff/business/000010_public_transfers.up.sql) 回填当前绑定身份。旧数据库已丢失的解绑归属不能可靠推断，因此无法回填的一侧标记 **-1（未知）**，与 **0（已知从未绑定）** 区分。新注册账户明确初始化历史，已知绑定为对应身份行 ID。未知历史下绑定返回 `IDENTITY_HISTORY_UNKNOWN`，不能自动按首次绑定放行。

升级前应核对以下清单，并结合可验证的原始记录为相应用户补充最近身份 ID；只有证实从未绑定才能写 0。缺少依据保持 -1，不能批量清零。回填应在停写窗口或用户锁内执行，同时增加 identity_revision，保留运维变更证据，不缩短已有 payment_restricted_until。

```sql
SELECT id,last_email_identity_id,last_telegram_identity_id
FROM `user`
WHERE last_email_identity_id=-1 OR last_telegram_identity_id=-1;
```

本轮迁移只在隔离测试库运行，未修改共享开发库或生产库。down 在已有转账、额外方案、绑定变更或冻结记录时拒绝回滚，避免移除资金与安全依据；失败后的 dirty/guard 按既有迁移恢复规范处理，不自动 force。

## 当前开放边界

本轮提供 USD 余额互转和只读账单。首页有任务、收款、付款和余额入口；任务仍沿用未开放提示，余额页的链上充值说明属于后续能力。Mini App 的链上入口提示需要 App，下载链接和原生打包随客户端发布落实。

商户固定订单、链上资产、组合付款、Gas 结算和原生钱包签名仍归阶段 5/6；通知订阅及真实邮箱/TG Bot 收发仍按原决定留到 8.2–8.3。当前测试不代表这些通道已接入或已完成生产发布。
