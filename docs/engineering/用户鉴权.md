# 用户鉴权基础

2.2 已建立邮箱验证码、Telegram Mini App 验签、身份绑定/换绑/解绑的内部用例，入口为 [auth.Service](../../backend/logic/auth/service.go)。2.3 已接入产品 JWT 与公开认证契约，2.4 接入前端。App 原生 Telegram 授权方式随 8.4 确定，本项没有把 Mini App initData 宣称为任意客户端授权协议。

## 配置和依赖

共享 ServiceContext 在配置 Auth 时组装鉴权依赖，沿用同一个 MySQL、Redis 和 transaction.Runner。省略 Auth 时不启用该能力；不连接邮件服务或 Telegram 做启动探测。启用示例（加入现有 platform YAML）：

```yaml
Session: {} # 签名密钥由 DEXWALLET_TOKEN_SECRET 注入
Auth:
  EmailEnabled: true
  TelegramEnabled: true
  SendPerEmail: 10
  SendPerSource: 30
  VerifyPerSubject: 30
  VerifyPerSource: 60
  SMTP:
    Host: smtp.example.com
    Port: 587
    From: auth@example.com
    Username: auth@example.com
    ImplicitTLS: false
    Timeout: 10s
```

| 环境变量 | 作用 |
| --- | --- |
| DEXWALLET_TOKEN_SECRET | 至少 32 字节的独立随机签名密钥；必须与 Auth.Secret 不同，所有节点保持一致。变更后现有 token 立即失效 |
| DEXWALLET_AUTH_SECRET | 至少 32 字节的稳定随机密钥，与 idx 密钥分开；用于验证码、请求和材料摘要。变更会使未完成认证材料及恢复令牌失效 |
| DEXWALLET_TELEGRAM_BOT_TOKEN | 启用 Telegram 时必填；只用于服务端验证，不进入客户端或仓库 |
| DEXWALLET_SMTP_PASSWORD | SMTP 账号密码，与 YAML 中 Username 成对配置；SMTP 可使用有 TLS 的受控免认证投递服务 |

现有 Redis 必须启用；不可用时鉴权返回依赖错误，不绕过限流。SMTP 默认强制 STARTTLS，ImplicitTLS=true 使用直接 TLS；不提供跳过证书校验或明文降级选项。邮件适配复用 [go-mail](https://github.com/wneessen/go-mail) v0.8.1，发送有 context/超时；不启用内容调试日志。中英文邮件文案在 `backend/logic/auth/templates/`，未知语言回退英文。

本机未配置真实邮件供应商或 TG Bot，也未发送真实邮件。本轮 fake 仅通过测试依赖注入，应用不会返回固定验证码或把未验证 TG ID 当授权。

## 邮箱挑战与限流

验证码为均匀随机的 6 位数字，5 分钟有效、60 秒后可重发，每挑战最多 5 次错误尝试。按邮箱规范化结果定位一条当前挑战，不合并本地部分大小写、点号或加号别名。重发替换挑战号与摘要，因此旧挑战立即失效；不会清空 Redis 累计额度。

MySQL 只保存验证码 HMAC、随机挑战号、用途、Actor 及会话版本、发送状态、时间和尝试次数。事务先保留 pending 挑战，提交后发信，再以挑战号条件激活；发信失败或未知状态不能消费，要求重发。旧发送结果不能激活已被新挑战替换的记录。错误验证码的计数单独作为拒绝结果提交；正确验证码的消费与用户/身份变更、操作记录一起提交。

限流使用 redis_rate v10.0.1 与现有 go-redis 客户端，集中定义发送、邮箱验证、TG 验证的 key 范围。配置表示 GCRA 均速及同值突发量（如发送每邮箱均速 10/小时、突发 10），不是滑动一小时绝对上限。IP 来源先于邮箱额度检查；TG 验签前按来源限流。来源须是接入层确认的 IP，HTTP 层当前仅使用连接 RemoteAddr，忽略 X-Forwarded-For/X-Real-IP。反向代理部署的可信来源配置归 8.2，当前代理后的客户端会共享代理 IP 限流。

## Telegram 验证

复用 init-data-golang v1.5.0 验证完整原始 initData；项目额外拒绝过长材料、重复查询字段、换行歧义、缺少用户、机器人及非法时间。auth_date 最长 5 分钟，未来最多容差 30 秒。依据为 [Telegram 官方验证说明](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app) 和 [库实现](https://github.com/Telegram-Mini-Apps/init-data-golang)。不使用客户端的 initDataUnsafe。

通过验证后才构造可信 TG 完整资料快照；可选资料缺失保持 NULL 语义，产品昵称头像仍只在首次创建时初始化。材料指纹基于验证后的 hash，因此改变查询参数排列不能绕过重放限制。已使用材料无法换请求令牌再次登录或跨用途绑定，需要取得新的授权材料。

## 内部调用与会话衔接

| 方法 | 前置条件与结果 |
| --- | --- |
| SendEmail | 规范化邮箱、可信来源 IP、用途；绑定/换绑须提供有效 Actor，事务内重新检查 |
| VerifyEmail | 挑战号、验证码、请求令牌和相同用途/Actor；正确时创建或解析用户，或完成绑定变更 |
| VerifyTelegram | 原始 initData、请求令牌、可信来源 IP 和用途/Actor；验签后进入相同事务流程 |
| Unbind | 有效 Actor 与明确身份类型；不需要再验证旧身份，仍须保留其他登录方式 |

Actor 包含内部用户 id 和 auth_version，由 HTTP 层验证 JWT 后构造；公开请求不接收客户端自报的 Actor。普通受保护请求通过用户缓存校验状态和版本，身份变更在事务中直接复核或恢复已提交的原操作。

每次操作使用客户端安全随机生成的 32 字节十六进制请求令牌（64 个小写字符）；网络重试保留该令牌与输入。同令牌不同输入会被拒绝，已提交结果最多恢复 5 分钟；恢复检查用户状态、当前 auth_version 及绑定版本。TG 恢复还须通过原授权的签名与时效检查。新的认证尝试使用新令牌；验证码失败不占用请求令牌。

成功返回 Result，包含用户、身份、稳定 OperationID 和原始 CreatedAt，保留原操作的身份与时间依据，不要求为每次登录建立会话表；换绑/解绑成功但响应丢失时，可按相同输入和请求令牌核对已提交结果，不能重新执行。恢复入口须验证原凭证的签名/主体并匹配已提交操作，不得笼统允许旧版本凭证操作；操作记录本身不能替代有效认证材料，5 分钟操作恢复窗口不变。公开身份操作已接入上述恢复规则，过期或签名无效的 JWT 不能进入恢复。

2026-10-29 用户取消当前范围中的单次登录撤销：普通退出仅清理客户端凭证，退出全部设备、禁用、解绑/换绑仍使用用户级 auth_version 使旧凭证失效。随后确定单 token 有效期 3 天、剩余不足 36 小时通过响应头续签，并明确取消 30 天认证上限；新 token 从签发时起有效 3 天，无累计登录时长上限、独立刷新凭证或刷新接口。2.2 的 auth_operation 是认证材料消费与幂等恢复记录，不是设备会话表，不因该范围调整而删除。后端签发与响应头已实现，客户端接入归 2.4，设计边界见 [2.3 实施方案](../design/工程工作记录/02-用户与鉴权/2.3-产品会话/02实施方案.md)。

绑定目标已属其他用户时拒绝；当前类型已绑定其他身份时必须走换绑；换绑前至少两种身份，解绑后至少一种。实际换绑/解绑递增用户 auth_version 和相关身份 binding_version，添加第二种身份及重复绑定当前身份不撤销其他会话。成功操作记录与身份变更同事务保存，业务失败全部回滚；旧外部身份及历史任务次数保留，奖励不迁移。

## 公开接口与 token

契约源为 [platform.api](../../backend/manifest/api/platform/platform.api)，goctl 同步生成 Go 路由、类型和 TS 契约。以下为 API 服务原始路径；本地前端通过现有 `/api` 代理访问。时间字段 expiresAt 使用 Unix 秒。

| 方法与路径 | 输入与认证 | 结果 |
| --- | --- | --- |
| POST /v1/user/auth/email/code | email、locale（en / zh-CN，默认 en） | challenge、expiresAt |
| POST /v1/user/auth/email/login | requestToken、email、challenge、code | accessToken、userIdx、expiresAt |
| POST /v1/user/auth/telegram/login | requestToken、完整 initData | 同上；首次成功建立产品用户与 TG 身份 |
| GET /v1/user/current | Bearer token | idx、nickname、avatarUrl；复用鉴权读到的用户 |
| POST /v1/user/auth/logout-all | Bearer token | loggedOut=true；事务内复核并递增版本，不签发新 token |
| POST /v1/user/identities/email/code | Bearer token、email、locale、purpose=bind / replace | 为当前用户和用途生成 challenge |
| POST /v1/user/identities/email/verify | Bearer token、邮箱登录输入、purpose=bind / replace | 完成绑定/换绑，返回当前有效 token |
| POST /v1/user/identities/telegram/verify | Bearer token、TG 登录输入、purpose=bind / replace | 同上 |
| POST /v1/user/identities/unbind | Bearer token、requestToken、identity=email / telegram | 解绑并返回新版本 token |

请求使用 `Authorization: Bearer <token>`。登录/身份成功响应同时在 data.accessToken 与 `X-Access-Token` 返回凭证；普通成功响应在剩余不足 36 小时时通过该头续签。错误、全部退出不续签。认证路由设置 `Cache-Control: no-store`。目前使用同源调用，不启用宽泛 CORS；如将来增加跨源访问，需限制来源并暴露该响应头。

JWT 使用固定 HS256，必须包含环境 issuer=`dexwallet_<environment>`、唯一 audience=`product-user`、产品 idx 主体、正数 auth_version、iat 和 exp，签名和有效期均独立校验；exp-iat 固定 72 小时，不接受缺失时间、未来签发或过期 token。商户/管理端需各自认证域，不能直接复用产品用户校验器。时钟应同步，当前 JWT 不设未来时间宽限。普通续签保留所验证版本，不从缓存或数据库的新版本升级旧凭证。

省略 Session 时不启用公开认证路由的能力（返回 503），健康接口仍可用；启用 Session 必须同时配置 Auth 与 Redis。JWT 不增加会话表、刷新凭证、刷新接口或累计登录时长上限。只有三个身份操作接口允许签名和时效有效的旧版本进入事务恢复；新操作必须通过数据库当前版本检查，匹配的旧操作也必须复核结果版本与绑定状态。恢复最多 5 分钟，每次返回的 token 从本次签发起有效 3 天。

复用 `golang-jwt/jwt/v4 v4.5.2`（已有间接依赖改为直接依赖）处理签名与解析，`.api middleware` 由 go-zero 生成挂载。没有直接采用框架默认 Authorize：锁定版本会跳过标准 claims 的上下文传递、未要求 issuer/audience/exp，且鉴权失败会转储请求；项目需要保留到期时间、统一错误及受限操作恢复，因此仅适配这些边界。HTTP 服务、超时、追踪、解析与响应仍使用原有框架能力。

| HTTP / code | 含义 |
| --- | --- |
| 400 / AUTH_PROOF_INVALID | 验证码或 TG 材料无效/过期；不表示当前产品 token 失效 |
| 401 / UNAUTHENTICATED | token 缺失、无效、过期、用户不存在或版本已失效 |
| 403 / PERMISSION_DENIED | 用户被禁用 |
| 409 / IDENTITY_OCCUPIED、IDENTITY_ALREADY_BOUND | 身份属于其他账户，或当前类型已绑定、应走换绑 |
| 422 / ANOTHER_IDENTITY_REQUIRED | 先绑定另一种身份 |
| 409 / CONFLICT | 原操作输入冲突、已消费材料、恢复过期或绑定变化 |
| 429 / RATE_LIMITED | 认证频率限制 |
| 503 / SERVICE_UNAVAILABLE | 功能未配置、用户缓存/认证限流 Redis 或发信不可用 |

普通退出仅在客户端清理；前端 token 存储、并发响应去倒退、退出后的迟到响应丢弃、登录页和身份引导均属 2.4，尚未实现。账户禁用的管理接口及后台登录归 2.5；当前已校验 disabled 状态，但没有新增管理操作。

## SQL 与验证

新增 [auth SQL](../../backend/manifest/sql/ddl/auth/tables.sql) 和 [business/000002](../../backend/manifest/sql/diff/business/000002_create_auth.up.sql)，不修改已发布的 000001。goctl 生成 challenge/operation model，手写扩展只处理锁定、保留记录及条件更新。操作记录保留成功审计与材料指纹，expires_at 限制恢复窗口，不自动删除审计。
