# 用户鉴权基础

2.2 已建立邮箱验证码、Telegram Mini App 验签、身份绑定/换绑/解绑的内部用例，入口为 [auth.Service](../../backend/logic/auth/service.go)。2.3 已接入产品 JWT 与公开认证契约，2.4 已接入用户前端。App 原生 Telegram 授权方式随 8.4 确定，本项没有把 Mini App initData 宣称为任意客户端授权协议。

## 配置和依赖

共享 ServiceContext 在配置 Auth 时组装鉴权依赖，沿用同一个 MySQL、Redis 和 transaction.Runner。省略 Auth 时不启用该能力；不连接邮件服务或 Telegram 做启动探测。启用示例（加入现有 platform YAML）：

```yaml
Session: {} # 签名密钥由 DEXWALLET_TOKEN_SECRET 注入
Auth:
  EmailEnabled: true
  TelegramEnabled: true
  SendPerEmail: 10
  SendPerSource: 30
  VerifyPerSubject: 30
  VerifyPerSource: 60
  SMTP:
    Host: smtp.example.com
    Port: 587
    From: auth@example.com
    Username: auth@example.com
    ImplicitTLS: false
    Timeout: 10s
```

| 环境变量 | 作用 |
| --- | --- |
| DEXWALLET_TOKEN_SECRET | 至少 32 字节的独立随机签名密钥；必须与 Auth.Secret 不同，所有节点保持一致。变更后现有 token 立即失效 |
| DEXWALLET_AUTH_SECRET | 至少 32 字节的稳定随机密钥，与 idx 密钥分开；用于验证码 HMAC。变更会使未完成验证码失效 |
| DEXWALLET_TELEGRAM_BOT_TOKEN | 启用 Telegram 时必填；只用于服务端验证，不进入客户端或仓库 |
| DEXWALLET_SMTP_PASSWORD | SMTP 账号密码，与 YAML 中 Username 成对配置；SMTP 可使用有 TLS 的受控免认证投递服务 |

现有 Redis 必须启用；验证码、TG 防重放、限流不可用时拒绝认证。普通用户查询缓存异常时记录日志并查询 MySQL。SMTP 默认强制 STARTTLS，ImplicitTLS=true 使用直接 TLS；不提供跳过证书校验或明文降级选项。邮件适配复用 [go-mail](https://github.com/wneessen/go-mail) v0.8.1，发送有 context/超时；不启用内容调试日志。中英文邮件文案在 `backend/logic/auth/templates/`，未知语言回退英文。

本机未配置真实邮件供应商或 TG Bot，也未发送真实邮件。后端不会返回固定验证码或把未验证 TG ID 当授权。

前端现提供独立开发模式 `pnpm dev:user:tg`，由本地 Vite 使用同一个开发 Bot token 生成签名材料，再通过原有后端验签、用户落库及 JWT 流程，后端不增加免验签入口。操作方式见 [开发与测试环境](开发与测试环境.md)。

用户确认本地开发以方便体验为先：显式配置 `Auth.TelegramDevelopment: true` 后，TG 材料无过期时间、可重复使用；用户状态、认证版本和绑定归属仍校验。仅 `Environment=local`、`Mode=dev` 可启用，其他环境配置会被拒绝。仍验证 Bot 签名，不影响邮箱验证码或产品 JWT 有效期。以下时效和防重放描述是默认规则；开发 TG 开关是明确例外。

## 邮箱挑战与限流

验证码为均匀随机的 6 位数字，5 分钟有效、60 秒后可重发，每挑战最多 5 次错误尝试。按邮箱规范化结果定位一条当前挑战，不合并本地部分大小写、点号或加号别名。重发替换挑战号与摘要，因此旧挑战立即失效；不会清空 Redis 累计额度。

三端共用 [Proofs](../../backend/logic/auth/proofs.go)：Redis 按认证域和规范化邮箱保存当前挑战号、HMAC 和错误次数，TTL 5 分钟。HMAC 绑定用途/Actor/认证版本，后台绑定账户认证版本；验证码不落 MySQL。发送顺序为占用 60 秒冷却 → 发邮件 → 写入带 TTL 的验证码，没有 pending/active/failed 状态机。发信失败或 Redis 写入失败返回错误，等待冷却后重发；接受邮件已发出但验证码未保存的低频失败，不做跨 SMTP/Redis 的事务补偿。

Lua 将核对、错误计数、成功删除放在一次原子操作内，并发校验只有一个成功。验证码一旦消费，后续业务失败或 SQL 提交结果未知也不恢复；需要获取新验证码。重发不清空累计限流。新发送失败时，上一份仍未过期且未消费的验证码继续有效。

限流使用 redis_rate v10.0.1 与现有 go-redis 客户端，集中定义发送、邮箱验证、TG 验证的 key 范围。配置表示 GCRA 均速及同值突发量（如发送每邮箱均速 10/小时、突发 10），不是滑动一小时绝对上限。IP 来源先于邮箱额度检查；TG 验签前按来源限流。来源须是接入层确认的 IP，HTTP 层当前仅使用连接 RemoteAddr，忽略 X-Forwarded-For/X-Real-IP。反向代理部署的可信来源配置归 8.2，当前代理后的客户端会共享代理 IP 限流。

## Telegram 验证

复用 init-data-golang v1.5.0 验证完整原始 initData；项目额外拒绝过长材料、重复查询字段、换行歧义、缺少用户、机器人及非法时间。auth_date 最长 5 分钟，未来最多容差 30 秒。依据为 [Telegram 官方验证说明](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app) 和 [库实现](https://github.com/Telegram-Mini-Apps/init-data-golang)。不使用客户端的 initDataUnsafe。

通过验证后才构造可信 TG 完整资料快照；可选资料缺失保持 NULL 语义，产品昵称头像仍只在首次创建时初始化。材料指纹基于验证后的 hash，因此改变查询参数排列不能绕过重放限制。验签后用 Redis SET NX 记录 hash，保留 5 分 30 秒覆盖时间容差。已使用材料不能再次登录或跨用途绑定，需要取得新材料；不持久保存认证结果，开发 TG 开关除外。

## 内部调用与会话衔接

| 方法 | 前置条件与结果 |
| --- | --- |
| SendEmail | 规范化邮箱、可信来源 IP、用途；绑定/换绑须提供有效 Actor，发送时普通查询检查，写入时事务内复核 |
| VerifyEmail | 挑战号、验证码和相同用途/Actor；正确时创建或解析用户，或完成绑定变更 |
| VerifyTelegram | 原始 initData、可信来源 IP 和用途/Actor；验签、防重放后进入身份事务 |
| Unbind | 有效 Actor 与明确身份类型；不需要再验证旧身份，仍须保留其他登录方式 |

Actor 包含内部用户 id 和 auth_version，由 HTTP 层验证 JWT 后构造；公开请求不接收客户端自报的 Actor。所有受保护接口使用同一 UserAuth；普通请求按 30 秒缓存检查状态和版本，身份写入在事务中复核最新状态。不再设置允许旧版本凭证进入的特殊恢复中间件。

2026-10-30 按用户确认的可维护性原则删除认证操作回执、摘要对比和成功结果回放。登录/换绑/解绑返回用户和身份信息，由 HTTP 层签发 token；验证码或 TG 材料消费后不承诺重复成功。身份操作响应丢失时，前端清理匹配的旧凭证，使用保留身份重新登录并查看当前状态，不自动重放操作。

单 JWT 有效期 3 天，剩余不足 36 小时通过响应头续签，无累计 30 天上限、独立刷新凭证、会话表或单次登录撤销。普通退出仅清理客户端；禁用、换绑/解绑仍通过 auth_version 使旧凭证失效。

绑定目标已属其他用户时拒绝；当前类型已绑定其他身份时必须走换绑；换绑前至少两种身份，解绑后至少一种。实际换绑/解绑递增用户 auth_version 和相关身份 binding_version，添加第二种身份及重复绑定当前身份不撤销其他会话。身份变更在单个 MySQL 事务内完成，业务失败回滚身份数据；已消费的外部证明不恢复；旧外部身份及历史任务次数保留，奖励不迁移。

## 暂停开放退出全部设备（2026-10-30）

当前没有业务需求，所有用户端移除“退出全部设备”按钮及请求封装，`.api` 不再声明 `POST /v1/user/auth/logout-all`；生成路由不注册该接口，访问返回 HTTP 404（标准文本响应），不修改认证版本或签发 token。专用 handler、接入 logic 和响应类型一并移除，不增加开关或临时拒绝接口。

保留 [user.Service.LogoutAll](../../backend/logic/user/logout.go) 内部用例：事务锁定用户并复核状态和认证版本，递增 auth_version，使旧 token 失效；保留其缓存失效机制及集成验证。该方法只接受可信内部调用者构造的 Actor，不作为新的公开入口。普通退出、用户禁用、换绑/解绑的认证版本变化、3 天 token、36 小时续签阈值及 30 秒缓存规则均保持。

未来确认需要重新开放时，先恢复 `.api` 声明并生成路由和 Go/TS 类型，再补接入层、前端确认交互及国际化；验收事务复核、旧 token 失效、缓存传播和退出响应不续签后再发布。历史 2.3/2.4 记录中的公开全部退出描述仅代表当时已实现范围，以本节当前状态为准。

## 公开接口与 token

契约源为 [platform.api](../../backend/manifest/api/platform/platform.api)，goctl 同步生成 Go 路由、类型和 TS 契约。以下为 API 服务原始路径；本地前端通过现有 `/api` 代理访问。时间字段 expiresAt 使用 Unix 秒。

| 方法与路径 | 输入与认证 | 结果 |
| --- | --- | --- |
| POST /v1/user/auth/email/code | email、locale（en / zh-CN，默认 en） | challenge、expiresAt |
| POST /v1/user/auth/email/login | email、challenge、code | accessToken、userIdx、expiresAt |
| POST /v1/user/auth/telegram/login | 完整 initData | 同上；首次成功建立产品用户与 TG 身份 |
| GET /v1/user/identities | Bearer token；普通查询展示身份 | 当前身份 type、subject、displayName；空列表为 [] |
| PATCH /v1/user/profile | Bearer token、nickname（去首尾空白、1–128 个 Unicode 字符） | 当前产品资料；不修改外部身份快照或认证版本，提交后失效用户缓存 |
| GET /v1/user/current | Bearer token | idx、nickname、avatarUrl；复用鉴权读到的用户 |
| POST /v1/user/identities/email/code | Bearer token、email、locale、purpose=bind / replace | 为当前用户和用途生成 challenge |
| POST /v1/user/identities/email/verify | Bearer token、邮箱登录输入、purpose=bind / replace | 完成绑定/换绑，返回当前有效 token |
| POST /v1/user/identities/telegram/verify | Bearer token、TG 登录输入、purpose=bind / replace | 同上 |
| POST /v1/user/identities/unbind | Bearer token、identity=email / telegram | 解绑并返回新版本 token |

请求使用 `Authorization: Bearer <token>`。登录/身份成功响应同时在 data.accessToken 与 `X-Access-Token` 返回凭证；普通成功响应在剩余不足 36 小时时通过该头续签。错误不续签。认证路由设置 `Cache-Control: no-store`。目前使用同源调用，不启用宽泛 CORS；如将来增加跨源访问，需限制来源并暴露该响应头。

JWT 使用固定 HS256，必须包含环境 issuer=`dexwallet_<environment>`、唯一 audience=`product-user`、产品 idx 主体、正数 auth_version、iat 和 exp，签名和有效期均独立校验；exp-iat 固定 72 小时，不接受缺失时间、未来签发或过期 token。商户/管理端需各自认证域，不能直接复用产品用户校验器。时钟应同步，当前 JWT 不设未来时间宽限。普通续签保留所验证版本，不从缓存或数据库的新版本升级旧凭证。

省略 Session 时不启用公开认证路由的能力（返回 503），健康接口仍可用；启用 Session 必须同时配置 Auth 与 Redis。JWT 不增加会话表、刷新凭证、刷新接口或累计登录时长上限。身份操作同样要求有效的当前登录凭证，并在事务内复核；没有旧凭证恢复例外。

复用 `golang-jwt/jwt/v4 v4.5.2`（已有间接依赖改为直接依赖）处理签名与解析，`.api middleware` 由 go-zero 生成挂载。没有直接采用框架默认 Authorize：锁定版本会跳过标准 claims 的上下文传递、未要求 issuer/audience/exp，且鉴权失败会转储请求；项目需要保留到期时间、统一错误及认证版本检查，因此仅适配这些边界。HTTP 服务、超时、追踪、解析与响应仍使用原有框架能力。

| HTTP / code | 含义 |
| --- | --- |
| 400 / AUTH_PROOF_INVALID | 验证码或 TG 材料无效/过期；不表示当前产品 token 失效 |
| 401 / UNAUTHENTICATED | token 缺失、无效、过期、用户不存在或版本已失效 |
| 403 / PERMISSION_DENIED | 用户被禁用 |
| 409 / IDENTITY_OCCUPIED、IDENTITY_ALREADY_BOUND | 身份属于其他账户，或当前类型已绑定、应走换绑 |
| 422 / ANOTHER_IDENTITY_REQUIRED | 先绑定另一种身份 |
| 409 / CONFLICT | TG 材料重放或身份绑定冲突 |
| 429 / RATE_LIMITED | 认证频率限制 |
| 503 / SERVICE_UNAVAILABLE | 功能未配置、验证码、防重放、限流 Redis 或发信不可用 |

普通退出仅在客户端清理。2.4 已实现用户端 token 存储、并发响应去倒退、退出后的迟到响应丢弃、登录页和身份引导，具体见 [前端公共基础](前端公共基础.md)。账户禁用的管理接口及后台登录已由 2.5 接入，见 [后台鉴权](后台鉴权.md)。
