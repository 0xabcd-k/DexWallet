# 用户鉴权基础

2.2 已建立邮箱验证码、Telegram Mini App 验签、身份绑定/换绑/解绑的内部用例，入口为 [auth.Service](../../backend/logic/auth/service.go)。正式 HTTP 仍仅有健康接口；2.3 接入产品会话和公开认证契约，2.4 接入前端。App 原生 Telegram 授权方式随 8.4 确定，本项没有把 Mini App initData 宣称为任意客户端授权协议。

## 配置和依赖

共享 ServiceContext 在配置 Auth 时组装鉴权依赖，沿用同一个 MySQL、Redis 和 transaction.Runner。省略 Auth 时不启用该能力；不连接邮件服务或 Telegram 做启动探测。启用示例（加入现有 platform YAML）：

```yaml
Auth:
  EmailEnabled: true
  TelegramEnabled: true
  SendPerEmail: 10
  SendPerSource: 30
  VerifyPerSubject: 30
  VerifyPerSource: 60
  SMTP:
    Host: smtp.example.com
    Port: 587
    From: auth@example.com
    Username: auth@example.com
    ImplicitTLS: false
    Timeout: 10s
```

| 环境变量 | 作用 |
| --- | --- |
| DEXWALLET_AUTH_SECRET | 至少 32 字节的稳定随机密钥，与 idx 密钥分开；用于验证码、请求和材料摘要。变更会使未完成认证材料及恢复令牌失效 |
| DEXWALLET_TELEGRAM_BOT_TOKEN | 启用 Telegram 时必填；只用于服务端验证，不进入客户端或仓库 |
| DEXWALLET_SMTP_PASSWORD | SMTP 账号密码，与 YAML 中 Username 成对配置；SMTP 可使用有 TLS 的受控免认证投递服务 |

现有 Redis 必须启用；不可用时鉴权返回依赖错误，不绕过限流。SMTP 默认强制 STARTTLS，ImplicitTLS=true 使用直接 TLS；不提供跳过证书校验或明文降级选项。邮件适配复用 [go-mail](https://github.com/wneessen/go-mail) v0.8.1，发送有 context/超时；不启用内容调试日志。中英文邮件文案在 `backend/logic/auth/templates/`，未知语言回退英文。

本机未配置真实邮件供应商或 TG Bot，也未发送真实邮件。本轮 fake 仅通过测试依赖注入，应用不会返回固定验证码或把未验证 TG ID 当授权。

## 邮箱挑战与限流

验证码为均匀随机的 6 位数字，5 分钟有效、60 秒后可重发，每挑战最多 5 次错误尝试。按邮箱规范化结果定位一条当前挑战，不合并本地部分大小写、点号或加号别名。重发替换挑战号与摘要，因此旧挑战立即失效；不会清空 Redis 累计额度。

MySQL 只保存验证码 HMAC、随机挑战号、用途、Actor 及会话版本、发送状态、时间和尝试次数。事务先保留 pending 挑战，提交后发信，再以挑战号条件激活；发信失败或未知状态不能消费，要求重发。旧发送结果不能激活已被新挑战替换的记录。错误验证码的计数单独作为拒绝结果提交；正确验证码的消费与用户/身份变更、操作记录一起提交。

限流使用 redis_rate v10.0.1 与现有 go-redis 客户端，集中定义发送、邮箱验证、TG 验证的 key 范围。配置表示 GCRA 均速及同值突发量（如发送每邮箱均速 10/小时、突发 10），不是滑动一小时绝对上限。IP 来源先于邮箱额度检查；TG 验签前按来源限流。来源须是接入层确认的 IP，后续 HTTP 层必须明确可信代理范围，不直接信任任意请求头。

## Telegram 验证

复用 init-data-golang v1.5.0 验证完整原始 initData；项目额外拒绝过长材料、重复查询字段、换行歧义、缺少用户、机器人及非法时间。auth_date 最长 5 分钟，未来最多容差 30 秒。依据为 [Telegram 官方验证说明](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app) 和 [库实现](https://github.com/Telegram-Mini-Apps/init-data-golang)。不使用客户端的 initDataUnsafe。

通过验证后才构造可信 TG 完整资料快照；可选资料缺失保持 NULL 语义，产品昵称头像仍只在首次创建时初始化。材料指纹基于验证后的 hash，因此改变查询参数排列不能绕过重放限制。已使用材料无法换请求令牌再次登录或跨用途绑定，需要取得新的授权材料。

## 内部调用与会话衔接

| 方法 | 前置条件与结果 |
| --- | --- |
| SendEmail | 规范化邮箱、可信来源 IP、用途；绑定/换绑须提供有效 Actor，事务内重新检查 |
| VerifyEmail | 挑战号、验证码、请求令牌和相同用途/Actor；正确时创建或解析用户，或完成绑定变更 |
| VerifyTelegram | 原始 initData、请求令牌、可信来源 IP 和用途/Actor；验签后进入相同事务流程 |
| Unbind | 有效 Actor 与明确身份类型；不需要再验证旧身份，仍须保留其他登录方式 |

Actor 包含用户 id 和 auth_version，只能由 2.3 的有效会话产生。这里没有把客户端自报 Actor 当作鉴权；因此当前没有公开这些内部入口。

每次操作使用客户端安全随机生成的 32 字节十六进制请求令牌（64 个小写字符）；网络重试保留该令牌与输入。同令牌不同输入会被拒绝，已提交结果最多恢复 5 分钟；恢复检查用户状态、当前 auth_version 及绑定版本。TG 恢复还须通过原授权的签名与时效检查。新的认证尝试使用新令牌；验证码失败不占用请求令牌。

成功返回 Result，包含用户、身份、稳定 OperationID 和原始 CreatedAt。2.3 应按该操作恢复同一会话；换绑/解绑成功但响应丢失时，可按相同输入和请求令牌核对已提交结果，不能重新执行。恢复入口须验证原会话的签名/主体并匹配已提交操作，不得笼统允许旧版本会话操作。最长 30 天重新认证的起点不能因重试或绑定变更顺延；会话签发与恢复尚待 2.3 实现。

绑定目标已属其他用户时拒绝；当前类型已绑定其他身份时必须走换绑；换绑前至少两种身份，解绑后至少一种。实际换绑/解绑递增用户 auth_version 和相关身份 binding_version，添加第二种身份及重复绑定当前身份不撤销其他会话。成功操作记录与身份变更同事务保存，业务失败全部回滚；旧外部身份及历史任务次数保留，奖励不迁移。

## SQL 与验证

新增 [auth SQL](../../backend/manifest/sql/ddl/auth/tables.sql) 和 [business/000002](../../backend/manifest/sql/diff/business/000002_create_auth.up.sql)，不修改已发布的 000001。goctl 生成 challenge/operation model，手写扩展只处理锁定、保留记录及条件更新。操作记录保留成功审计与材料指纹，expires_at 限制恢复窗口，不自动删除审计。

锁顺序为操作记录 → 邮箱挑战（邮箱流程）→ 用户 → 同类型身份按 id 升序；TG 流程不锁邮箱挑战。复用 2.1 的用户与身份锁定规则。只对明确回滚的竞争/死锁做有限解析重试，提交结果未知或回滚失败立即返回。

```sh
# backend/，普通检查不连接服务
go test -race ./...
go vet ./...
# 已 source .tools/local.env；只创建/清理本轮隔离资源
go run ./tools/testenv run go test -race -tags=integration ./tests/integration -run '^TestAuth' -v -count=1 -timeout=180s
```

真实测试复用 MySQL/Redis，邮件使用 fake，Telegram 使用公开测试密钥构造签名。redis_rate 自带 rate: 前缀，隔离资源清单已支持该库生成的、属于当前 run 的准确 key；其他 run 和任意通配符仍拒绝清理。验收范围与结果见 [2.2 验证记录](../design/工程工作记录/02-用户与鉴权/2.2-Telegram鉴权/04验证记录.md)。
