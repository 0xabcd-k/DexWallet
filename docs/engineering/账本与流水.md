# 账本与流水

3.2 已建立内部完整凭证记账和本人流水查询。方案与验收见 [3.2 工作记录](../design/工程工作记录/03-资金账户与账本/3.2-账本与流水/01讨论记录.md)。本页描述当前代码入口，充值、发奖、转账等真实业务尚未开放。

## 数据与金额

完整定义在 [账户 SQL](../../backend/manifest/sql/ddl/account/tables.sql) 与 [约束](../../backend/manifest/sql/ddl/account/constraints.sql)，增量为 [business/000006](../../backend/manifest/sql/diff/business/000006_ledger.up.sql)。user_account 继续保存可用/占用余额，新增 ledger_voucher 与 ledger_entry；不另建重复的用户流水表。

凭证的 business_type、business_id、action 唯一；一个业务不同动作可分别落账，可分次的动作应使用各自明细单据 ID，不能每次重试临时生成来源。凭证可以通过 original_voucher_id 关联历史凭证。分录以 voucher_id、line_no 唯一，引用用户账户或系统科目，两种目标互斥。

用户账户贷记增加、借记扣减，金额始终为正；每条用户分录保存该余额部分变动后的金额；3.3 增加 available/held 区分，旧分录仍为可用余额。系统分录记录相应借贷，不保存用户余额，也不维护所有请求共同竞争的平台余额行。初始具名科目为美元充值清算、奖励费用和积分发行；这只是记账分类，不能代替链上证据、费用规则或平台备付核对。

全部分录按单位借贷平衡。美元和奖励按 2 位小数，积分为整数，沿用 DECIMAL(36,18) 与精确十进制；输入不自动舍入，账户余额不能为负或溢出，扣款只使用可用余额。金额在 API/前端保持字符串。

## 内部写入契约

[account.Service.Post](../../backend/logic/account/posting.go) 接收 Posting（来源、可选原凭证、完整 Entries）和显式 session。Credit/Debit 是同一次完整记账中的正额增减明细构造函数，不是可独立提交的写入口。已有 ServiceContext.Accounts 与 Tx 可直接用于后续业务接入。

业务调用顺序：

1. 所属业务识别稳定请求与业务单据、校验原参数及权限；关键授权和身份状态在外层数据库事务中复核。
2. 使用已有 transaction.Runner.TransactCtx，把其 callback 的 context 和 session 显式传入 Post；RequireSession 拒绝无事务或其他连接，防止误用默认连接导致部分提交。
3. Post 在写入前核验目标、精度与按单位平衡，登记唯一来源凭证；按 user_id/kind 固定顺序准备和锁定所有用户账户。仅入账目标可按需创建零行，已有余额保持，纯扣款缺行返回余额不足。
4. 在已锁定余额上按明细顺序计算每条变化和变动后余额，检查每一步非负与范围；最终余额和完整分录与业务单据同事务提交。单个凭证对同一账户的多条分录按传入顺序执行，不承诺先扣后加和先加后扣等价。
5. 任一错误必须从外层 callback 原样或包装返回，不允许吞错后继续提交。业务失败、数据库分录写入失败都整笔回滚。事务内不调用邮件、MQ、链 RPC 等外部服务。

ErrInvalidPosting 表示参数/精度非法，ErrUnbalanced 表示单位不平衡，ErrInsufficientBalance 表示可用不足，ErrAlreadyPosted 表示同一来源动作已有凭证；原始 MySQL 原因保留在错误链。账本不会把重复变成成功回执，业务层在识别原单并校验参数后返回原业务结果。可以通过绑定同一 session 的 LedgerVoucherModel.FindOneByBusinessTypeBusinessIdAction 查询来源；提交结果未知时沿用 transaction.Failure.Unknown，不换来源盲重试。

来源类型为 transfer、deposit、reward、withdrawal、payment，独立 idx 类型为 TransferId、DepositId、RewardGrantId、WithdrawalId、PaymentId；后续新增真实业务时扩展具名来源及稳定编码，不能复用旧类型表示另一种单据。代码中的业务授权由未来用例承担，内部 Post 自身不是对客户端的授权入口。

普通业务只追加凭证/分录，不更新或删除已提交历史。工具生成的基础 CRUD 不代表开放历史修改功能；有依据的补记/冲正另建凭证关联原记录，是否允许、资金不足处理和操作审计由所属业务决定。当前没有任意调账或冲正 HTTP API，也没有通用奖励撤销能力。

## 本人查询

实际接口为 GET /v1/user/account-entries，源定义在 [.api](../../backend/manifest/api/platform/platform.api)。沿用产品 JWT、no-store 和响应头续签。

| 参数 | 约束 |
| --- | --- |
| kind | 可选；usd_balance、reward_usd、task_points；省略查询本人所有种类 |
| before | 可选，上一页返回的 nextCursor；使用 LedgerEntryId 编码后的 idx |
| limit | 默认 20，范围 1–100 |

返回 data.entries 和 data.nextCursor。每条包含 idx、voucherIdx、businessType、businessIdx、action、kind、unit、direction（in/out）、amount（正字符串）、balanceAfter（该余额部分变动后金额）、balancePart（available/held）、activity（posted/held/consumed/released）、createdAt（UTC）。nextCursor 为空表示当前读取已无下一页。

所属用户只来自 JWT，附加 userId 参数不能改变所有者。查询直接连接本人账户与分录，不返回系统科目、其他用户分录或对手余额。游标只是位置，不提供任何权限。按分录 id 倒序，额外读取一条判断下一页；不执行总量统计或保证多个请求共享快照，后续提交记录可刷新读取。账户/表故障明确报错，不返回假空列表。

## 用户页面与范围

[记录页](../../frontend/apps/user/src/view/records/index.tsx) 支持种类筛选、加载更多、刷新、空态、错误重试、登录返回原筛选，以及中英文展示。钱包/奖励账户卡可进入相应筛选。已展示的旧页在下一页失败时保留；筛选、刷新或会话变化取消旧请求，未授权时不保留旧记录。金额和变动后余额不转浮点。

当前展示已提交的账户分录；3.3 补充占用明细及占用/释放活动。完整互转、跨业务账单聚合在 3.6，链上记录及具体业务详情随对应工作项实现；业务请求幂等整合在 3.4；后台任务与可靠消息在 3.5。

## 迁移与验证入口

3.2 基线对应 business 版本 6；含 3.3 的当前代码要求 business 版本 7，生成/启动/查询不自动迁移。000006 新增空账本表，保留旧账户；不伪造已有余额的历史来源。当前没有已开放的生产资金写入，测试准备仅限登记的隔离库。共享开发库仍未应用本轮迁移，部署前须显式升级。回滚脚本只供明确的迁移流程，不用于撤销已记账交易。

普通检查：仓库根 bash scripts/check.sh common，包含 Go race/vet、生成、类型、前端单测与三端构建。真实测试使用受限 local.env 与 testenv，见 [开发与测试环境](开发与测试环境.md)。专项命令：

```sh
# backend/；先按测试环境说明载入受限配置

# frontend/；使用锁定 Node，浏览器测试前已构建
pnpm test:e2e --workers=1
```

实际证据、已验证限制及资源清理记录见 [3.2 验证记录](../design/工程工作记录/03-资金账户与账本/3.2-账本与流水/04验证记录.md)。浏览器使用 HTTP fake；真实查询和记账由独立后端 MySQL/Redis HTTP 验证，不把两者合称真实浏览器全链路验收。

## 3.3 占用扩展

当前迁移为 business/000007。Hold/Consume/Release 复用同一记账核心，普通 Post 禁止占用动作与占用部分写入。用户流水增加 balancePart/activity；占用与释放的内部占用侧分录不重复展示，核销展示占用侧扣款。完整内部凭证与分录仍保留。入口、约束和迁移限制见 [占用与释放](占用与释放.md)。
