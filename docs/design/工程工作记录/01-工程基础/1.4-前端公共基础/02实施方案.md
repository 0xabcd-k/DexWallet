## 目标与工作边界

在现有三个应用 workspace 和生成类型之上，建立可独立启动与构建的前端入口，完成路由、请求与错误处理、国际化、页面布局和实际使用的基础组件。沿用 [开发规范](../../../../engineering/开发规范.md)、[工程结构](../../../../engineering/工程结构.md)、[契约生成与迁移](../../../../engineering/契约生成与迁移.md) 和 [后端公共基础](../../../../engineering/后端公共基础.md)。

信息架构遵循 [信息架构与交互原则](../../../01信息架构与交互原则.md) 和 [商户与平台界面](../../../03商户与平台界面.md)。本项验证页面承载能力，不实现登录、钱包连接、权限判断、资金数据、任务、支付、账本和消息订阅。无数据库迁移、服务端业务事务或新增业务 API。

1.4 负责前端本身的开发代理、构建和浏览器验证；1.5 负责干净环境、部署代理、域名及全栈联通。健康接口只用于技术验收，不能表示业务能力已经完成。

## 设计与实现步骤

### 1. 应用与共享模块（Q01）

组件库、布局与复用边界已确认；具体依赖版本在实施时核对。以下目录同时展示 Q04 的建议位置，国际化细节仍待确认。

建议目录如下；仅创建本项实际使用的目录和包，不为未来模块批量建立空壳：

```text
frontend/
  apps/
    user/src/
      main.tsx
      app/                 # 本端 provider、路由与移动布局
      api/                 # 本端客户端实例和手写端点适配
      components/          # 本端基础状态组件
      view/<module>/       # 页面 index.tsx 与 style.less
      locales/             # 本端文案
    merchant/src/          # 同样分层，独立路由和实例
    admin/src/             # 同样分层，独立路由和实例
  packages/
    api-contract/          # 已有生成类型，继续由 .api 生成
    api-client/            # 不依赖 React/UI 的请求、解析与错误类型
    i18n/                  # 初始化工厂、公共文案与错误码翻译
    ui-desktop/            # 商户/管理实际共用的后台布局与状态组件
```

用户端使用 Ant Design Mobile；后台使用 Ant Design。移动端组件留在 user，暂不建立只有一个消费者的移动 UI 包。共享包不反向依赖应用，不持有全局会话，不引入业务路由；user 的依赖树和构建产物不携带桌面组件库。

用户端承接钱包／奖励／记录三个主入口，仅主页面展示底部导航；子页面使用返回入口，并有明确站内回退目的地。未实现页面显示未开放状态，不显示假余额、假订单或把未知值显示为零。商户与管理端各自提供桌面侧栏、标题区和内容区；导航定义留在各自应用，仅注册本项实际提供的入口，其余业务菜单随业务增加。

库组件直接使用；只有形成项目行为或布局约定时才增加封装，不为每个 Button/Input 添加透传包装。加载、空态、筛选无结果、错误和未开放分别表达。配色不作为唯一状态提示，可访问名称也通过国际化资源提供。

### 2. 路由与状态（Q02）

本节路由、状态归属及启动衔接方案已确认，具体实现与实测待完成。用户端内部路径为 `/wallet`、`/rewards`、`/records`，地址表现为 `/#/wallet` 等，根路由转到 `/wallet`。主页面采用底部导航布局，子页面采用返回布局；商户端和管理端分别维护工作台布局、路由和入口。路由按应用集中定义，业务页面随业务交付增加，可按页面延迟加载，不先注册所有未来页面。

用户端使用 createHashRouter，商户端和管理端使用 createBrowserRouter；各端独立创建路由并交给 RouterProvider，采用客户端 Data Mode，保留现有 Vite SPA 构建。选择 Data Mode 是为了集中定义嵌套布局、路由错误边界和后续表单离开保护；本项不强制把所有请求迁入 loader/action，不增加 SSR 或 Node 线上服务。

各端提供根路由跳转、未知路由页、受控的站内返回入口。两个后台使用 History 路由，生产部署必须将页面路径回退到所属应用的 index.html，但 API 与静态资源错误不能被改写为 HTML；此部署规则进入 1.5。用户端 Hash 路由不会将 `#/wallet` 等片段发送给服务器，页面刷新仍请求原入口路径。

用户端必须先完成 Telegram 启动参数读取与会话内恢复准备，再规范化应用 hash 并创建路由。官方脚本会解析初始 location.hash，并通过 sessionStorage 保存/恢复 initParams；具体 SDK 选定后核对其初始化顺序和缓存机制，不先清空启动 hash，不重复开发另一套同用途缓存。1.4 使用合成启动参数验证此顺序及刷新边界，覆盖普通浏览器无 Telegram 参数、首次参数 hash、已有应用路由 hash 和存储不可用的场景；恢复失败应明确报告启动上下文缺失，不伪造身份。此适配只负责启动上下文，不做登录、服务端验签或认证会话恢复。

Telegram 分享入口采用 startapp 参数，经允许的目标映射进入内部页面；业务目标解析、鉴权、Telegram BackButton 订阅及宿主恢复由对应接入项实施。宿主返回需复用应用站内返回规则，不能假设浏览器路由会自动绑定。真实 Telegram 的 iOS、Android、Desktop/Web 启动、刷新、重开及返回要另行验收，本项浏览器/合成参数测试不能代替客户端实测。

启动适配建议位于 `apps/user/src/app/telegram/`，由应用入口在路由创建前调用，分别提取原始初始化数据、业务入口候选值及来源信息。`tgWebAppStartParam` 来自页面原始 search；Hash 路由中的 search 属于应用导航，不混用两者。保存类型明确的启动上下文，向应用 provider 提供只读数据；原始 initData 不写入日志、业务链接或路由状态。共用 api-client 不导入 Telegram SDK，两个后台不承担此启动流程。

完整目标流程为：Telegram 链接 → 读取启动上下文 → 建立待处理目标 → 创建路由并展示启动状态 → 2.2/2.3 的验签与产品会话 → 2.4 恢复允许的来源页面 → 所属业务校验对象与权限。1.4 只建立启动上下文、路由衔接和可测试的待处理目标生命周期；不增加鉴权 API、正式任务/付款目标协议或业务副作用。

启动目标生命周期需区分待处理、已处理及无效：同次启动的刷新保留当前路由，避免残留 GET 参数使页面反复跳回入口；鉴权失败不丢目标；明确的新启动替换旧上下文，新启动无参数不继承旧邀请。相同参数的新启动仍可打开，不永久按参数去重。检测新启动须保留 SDK 缓存合并前的来源证据，不能仅以缓存后的 start_param 或 activated 事件判断；无新证据时不得假称收到新参数。所选 SDK 对缺失字段的旧值回填要覆盖测试，避免混合不同启动的数据。

GET 候选值可预选加载界面，业务可信值须来自后续服务端验证与解析结果；候选值不一致、未知类型、无效/过期目标均有明确失败状态及站内出口，不回退到旧业务目标。进入页面不自动绑定邀请、领奖或扣款；登录与邀请关系的边界沿用阶段 2 及任务规则。

可分享的筛选、分页状态归 URL；表单草稿和弹层状态归所属页面；语言等少量应用设置通过 provider 传递。默认不引入全局状态库或 TanStack Query；后续出现服务端数据缓存、失效和轮询需求时按实际页面引入，避免在本项另造查询缓存。刷新不承诺恢复未提交表单，不把敏感草稿默认存入 localStorage。

URL 只承载适合分享的非敏感条件，路径参数和 query 必须解析、校验并对无效值做明确处理。返回列表保留原筛选和分页；跨步骤草稿在后续所属流程的共同父级保留内存状态，不依赖全局页面保活。未提交表单的离开保护随真实表单落实，刷新、关闭标签页和外部钱包跳转的恢复需单独验证，不由路由库自动保证。

应用内返回使用可识别的站内来源，否则回所属模块入口；不以 history.length 作为来源可信的依据，也不接受任意外站 return URL。未知路径显示未找到页面，运行异常进入可恢复的错误页，不暴露原始堆栈。若后续使用 loader 获取数据，页面不再对同一数据重复发请求；路由权限与真实认证留给后续工作项。

### 3. 请求与错误边界（Q03）

本节已确认，具体实现与验证待完成。首版使用 fetch 完成所需 JSON 请求，不额外引入 Axios 或通用拦截器框架；上传、流式接口等按实际业务另行设计。

调用关系为：页面／后续业务 hook → 应用 api 适配 → 共享 api-client → HTTP；api-contract 为客户端和应用提供生成类型。路由与 UI 不进入共享请求库。各应用通过工厂创建独立客户端，配置 base URL、有限超时及调用方取消信号；会话和认证回调以后由所属应用注入。本项不增加 token 存储、自动刷新或登录跳转。

基于 fetch 实现；必须同时检查 HTTP 状态与响应协议，不能把收到 HTTP 响应等同于成功。成功需符合 HTTP 成功状态及 code=OK，失败保留 status、code、traceId 和诊断原因。返回 JSON 首先作为 unknown 处理，校验公共 envelope；端点适配负责具体 data 校验，不能通过泛型断言把未检查的数据当作生成类型。手写校验不修改生成文件，接口字段变化仍先改 .api。

错误区分有结构的业务拒绝、无标准响应的 HTTP 错误、网络不可达、超时、调用方取消和协议不符。未知业务码保留原字符串及 traceId，显示通用本地化提示；不将未知码强制转换为生成的已知错误码联合类型。即使 HTTP 成功，错误 envelope 或损坏数据也不能成为正常 data。

成功返回与契约一致的已校验响应，保留 data 与 traceId；不在多层反复拆包或重新包装。错误使用明确的分类与字段表达，避免所有失败都变成一个字符串。请求库只返回结果或抛出明确错误，不弹 Toast、不路由跳转。页面决定内联错误、页面错误或一次性提示；主动取消不提示失败。公开界面按 code 映射文案，不直接展示服务端原始诊断 message；开发诊断保留足够上下文且不输出凭据。traceId 可用于问题定位。

默认超时为 10 秒，可按端点覆盖；客户端配置校验拒绝无效时长，计时覆盖请求和响应体读取。合并调用方取消与客户端超时信号，按先触发的原因分类，并在所有结束路径清理计时器和监听。网络错误只记录浏览器能提供的原因，不凭通用异常区分 DNS、CORS 和实际断网。

认证失败由应用后续会话层处理：401/UNAUTHENTICATED 与 403/PERMISSION_DENIED 分开，前者允许会话层保留目标后发起恢复，后者不得触发反复登录。并发失效通知与登录去重在会话接入项实现，恢复成功也不由公共客户端自动重放原写请求。Telegram initData 只在后续规定的鉴权交换中使用，不默认附加到所有 API；本项不确定凭证存储或自动续期策略。

首版不自动重试请求，尤其不自动重复提交写操作。超时不表示服务端已撤销；后续资金页面依据原请求标识查询状态，由所属业务项落实幂等与恢复。并发查询应取消或忽略过期结果，不能让旧响应覆盖新选择。

开发时建议每端默认请求同源 `/api`，Vite 代理去掉该前缀后转发到本地后端，因此 `/api/health/live` 对应现有 `/health/live`。三个应用采用独立开发端口并启用 strictPort。公开的 `VITE_API_BASE_URL` 只配置地址，不存放凭据；生产 `/api` 代理由 1.5 配置，不把本项开发代理当作已完成的线上部署。

### 4. 国际化与展示（Q04）

i18next 已确认；本项建议使用 react-i18next，首版资源为 zh-CN 和 en。Mini App 选择顺序为本端已保存的用户偏好、启动上下文中的受支持 Telegram language_code、浏览器语言列表中首个支持项、英文；普通浏览器和两个后台跳过 Telegram 来源。只将明确的简体中文变体映射到 zh-CN，不把繁体语言自动当成已支持。语言偏好建议存入 localStorage，使用带应用名称的具名 key，读写失败时保留内存选择，不阻塞启动；本项不创建用户设置接口或跨设备同步。共享初始化工厂接受应用传入的候选语言，不直接读取 Telegram 全局对象；language_code 仅用于显示，不触发身份确认。

语言映射先检查脚本，再检查地区：en 及其地区变体归 en，zh-Hans 及其地区变体归 zh-CN；无显式脚本的 zh-CN、zh-SG 归 zh-CN，zh-Hant 等繁体标签不归简体，无地区/脚本的 zh 继续下一来源。语言检测仅在初始化且没有手动偏好时生效，不用后续检测覆盖用户选择。初始化资源准备好后再呈现主体界面，减少首屏文案切换。

本项只提供实际使用的基础资源，公共命名空间建议为 common、errors，各应用维护自己的 app 命名空间。稳定 key 配合插值/复数机制，避免拼接句子；错误码本身作为映射依据，不要求后端根据语言重新定义 code。

公共命名空间维护通用操作和错误，应用命名空间维护导航和本端文案。分别创建 i18n 实例，语言切换同时更新组件库 locale、文档 lang、日期等展示；缺失翻译有明确回退，测试检查两种语言 key 一致。静态文案、错误提示、占位符和可访问标签均使用资源。语言切换通过现有实例更新，不以语言作为根组件 key，不重建路由或清空表单和待打开目标；资源检查同时覆盖 key 和插值参数，缺失翻译回退英文，未知错误码使用通用文案。

金额沿用 API 十进制字符串及单位，禁止统一转成 Number 后计算；本项仅按实际组件需求提供展示，不提前建立金融计算库。金额展示带 USD、USDT 等明确单位，币量不统一固定两位小数；API 精确值与展示格式分开，不在本项确定业务舍入规则。时间按设备时区显示，详情和后台查询标明所用时区；仅接受契约明确单位/时区的时间值，不通过数字长度猜秒或毫秒，不默认将英文显示等同于 UTC。语言切换只改变格式，不改变时间点或统计区间；报表统计时区归对应业务项。未知金额、空列表和零值保持区别。语言集合与兜底语言仍待确认，不沿用归档原型作为新增决议。

### 5. 验证与实施顺序（Q05）

确认 Q01–Q05 后再安装依赖。实施时核对 React、React DOM、Vite、路由、组件库和测试工具的兼容范围，固定可复现版本及 pnpm lockfile；保留已经确认的 Node/pnpm 工具链，必要升级单独说明依据。

依次补齐三个入口及构建配置、布局路由、国际化、请求与错误处理，最后补充验收。基础组件只在实际用到时引入。采用 Vitest 与 React Testing Library 验证客户端和组件的可观察行为，网络边界用 fake；少量 Playwright 浏览器用例验证路由、语言与布局，真实后端联通单独运行。

开发样例用于验证健康接口、加载、故障和恢复，不放在产品导航中；采用独立开发入口或仅开发环境加载的模块，并检查生产构建不能访问该样例。生产骨架只展示明确的页面状态，不暴露内部工具、技术诊断面板或虚构业务数据。健康接口成功仅证明请求链可达。

## 验收条件

以下是确认后的目标，不代表本轮已经通过：

| 范围 | 可观察的通过标准 |
| --- | --- |
| 工程 | 三端可分别启动、类型检查和构建，lockfile 安装可复现；生成契约检查无手改漂移 |
| 路由 | 主入口、子路由、返回、未知路由可用；验证底栏与子页面区别、无站内来源的深链接回退、query 校验与返回保留、页面异常恢复；Hash 路由创建前保留启动上下文、刷新及存储失败边界；两个后台的路径回退要求明确移交 1.5 |
| 布局 | 用户端在窄屏可操作，桌面两端布局可用；键盘焦点、可访问名称、空态与错误态有实际验证 |
| 类型与协议 | 合法健康响应可消费；缺失字段、损坏 JSON、HTML 错误页、非成功 HTTP、未知业务码均不能伪装成正常结果 |
| 请求生命周期 | 超时与取消可区分；不自动重试写操作；响应体读取也受超时/取消控制，结束后清理监听；区分 401 与 403；过期请求结果不覆盖新状态；失败可在显式操作后恢复 |
| 国际化 | 中文和英文切换覆盖导航、公共错误与组件文案；手动选择优先，Telegram 可选语言与浏览器语言按约定回退，存储失败仍可用；切换不重置路由/输入/启动目标；key 与插值一致，不显示裸 key |
| 隔离 | 三端路由、客户端、语言实例独立；用户构建不带桌面 UI；生产入口不能访问开发样例 |
| 范围 | 不新增业务鉴权、余额、订单或任务 API；未实现状态与真实空数据有区别；真实健康联通与模拟网络测试分别记录 |
