### Q01：为什么建议两套组件库

用户端首先服务移动端和 Telegram Mini App，后续还需适配安全区、窄屏、软键盘与返回操作。商户和管理端主要是桌面工作台，长表格、筛选和复杂表单更常见。让所有端使用一套桌面组件，会增加用户端的适配工作；全部自研基础组件则会增加键盘交互、焦点管理、加载态和错误态的维护负担。

建议使用库提供的基础交互组件，项目负责页面结构、业务组合和视觉主题。用户端不依赖桌面 UI 包；商户和管理端共用确实相同的后台布局及基础状态组件，不共享路由、权限清单或会话。主题使用各组件库公开能力；页面局部样式继续使用 Less，不依赖覆盖内部 DOM 的方式统一两套库。

本项只实现会实际使用的导航、布局、按钮、输入、加载、空态、错误态等。表格业务、支付弹窗、钱包连接、权限菜单及 Telegram 登录随对应工作项实现。组件库不能替代真实设备上的可访问性和交互验证。

备选为“用户端自研轻量组件、后台用 Ant Design”：用户端视觉自由度更大，但需要自行维护更多基础交互。建议先采用成熟移动组件，只对具体不适用的组件做局部替换。具体版本在确认后核对 React、Vite、TypeScript 与两个组件库的兼容范围，再固定依赖和锁文件；当前没有新增依赖。

### Q02：路由与状态如何组织（待确认）

建议每端使用 React Router 的 createBrowserRouter，集中维护本端路由表、嵌套布局、错误页和按页面加载的模块；继续以 Vite 构建静态 SPA。Data Mode 提供后续 loader/action、路由错误边界和表单离开保护的接入能力，不要求本项同时实现这些业务流程。

用户端建议以 `/wallet`、`/rewards`、`/records` 对应三个主入口，根路径转到钱包；详情等子页面使用不带底栏的布局。商户端和管理端各有自己的工作台及详情布局，不用一个巨大路由表按身份切换三个系统。未实现的业务路由不批量注册。

| 状态 | 建议归属 | 示例与边界 |
| --- | --- | --- |
| 可分享、可恢复的页面位置 | URL path 与 query | 详情 idx 放 path；非敏感的筛选、分页放 query，返回列表保留条件；路由输入仍需校验 |
| 临时交互 | 页面或组件的 useState/useReducer | 输入、选中项、弹层开关；无需全局 store |
| 跨步骤的未提交草稿 | 所属流程共同父级的内存状态 | 后续业务流程按需建立 provider，内部步骤切换不丢输入；不默认落盘，不承诺刷新后恢复 |
| 少量应用设置 | 本端 provider | 语言等设置；持久化方式由 Q04 确定，不共用三端会话 |
| 服务端数据 | 请求结果与所属页面/业务 hook | 余额、订单状态以后来自 API；不能另复制到全局 store 并当成权威事实 |

本项暂不增加 Redux/Zustand，也不建立自研查询缓存。等真实页面需要请求去重、缓存失效或轮询时，再评估 TanStack Query；如果采用 loader，同一数据不能再由页面 effect 重复请求。这里主要避免同时维护 URL、页面 state、全局 store 三份相同状态。

返回操作保留可识别的站内来源与 query；没有可靠站内来源时转到所属模块入口，不能仅凭 history.length 推断可以安全返回。深链接打开子页也应有可用出口。后续登录恢复和 Telegram 返回按钮由接入项实施，页面隐藏与路由守卫都不替代后端权限校验。

History 路由需要部署层支持页面路径回退，API 和资源请求不能被误回退为 HTML；列入 1.5 验收。备选 Hash 路由能减少部署回退要求，但在当前可管理部署环境的前提下，建议使用标准路径。首版不增加 SSR、路由服务端或通用页面保活框架。
