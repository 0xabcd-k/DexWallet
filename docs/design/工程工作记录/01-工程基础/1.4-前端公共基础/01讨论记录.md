### Q01：为什么建议两套组件库

用户端首先服务移动端和 Telegram Mini App，后续还需适配安全区、窄屏、软键盘与返回操作。商户和管理端主要是桌面工作台，长表格、筛选和复杂表单更常见。让所有端使用一套桌面组件，会增加用户端的适配工作；全部自研基础组件则会增加键盘交互、焦点管理、加载态和错误态的维护负担。

建议使用库提供的基础交互组件，项目负责页面结构、业务组合和视觉主题。用户端不依赖桌面 UI 包；商户和管理端共用确实相同的后台布局及基础状态组件，不共享路由、权限清单或会话。主题使用各组件库公开能力；页面局部样式继续使用 Less，不依赖覆盖内部 DOM 的方式统一两套库。

本项只实现会实际使用的导航、布局、按钮、输入、加载、空态、错误态等。表格业务、支付弹窗、钱包连接、权限菜单及 Telegram 登录随对应工作项实现。组件库不能替代真实设备上的可访问性和交互验证。

备选为“用户端自研轻量组件、后台用 Ant Design”：用户端视觉自由度更大，但需要自行维护更多基础交互。建议先采用成熟移动组件，只对具体不适用的组件做局部替换。具体版本在确认后核对 React、Vite、TypeScript 与两个组件库的兼容范围，再固定依赖和锁文件；当前没有新增依赖。

### Q02：路由与状态如何组织（已确认）

已确认的修订方案：用户端使用 React Router 的 createHashRouter，商户端和管理端使用 createBrowserRouter；各端集中维护本端路由表、嵌套布局、错误页和按页面加载的模块；继续以 Vite 构建静态 SPA。Data Mode 提供后续 loader/action、路由错误边界和表单离开保护的接入能力，不要求本项同时实现这些业务流程。

用户端建议以 `/wallet`、`/rewards`、`/records` 对应三个主入口，地址表现为 `/#/wallet`、`/#/rewards`、`/#/records`；根路径转到钱包；详情等子页面使用不带底栏的布局。商户端和管理端各有自己的工作台及详情布局，不用一个巨大路由表按身份切换三个系统。未实现的业务路由不批量注册。

| 状态 | 建议归属 | 示例与边界 |
| --- | --- | --- |
| 可分享、可恢复的页面位置 | URL path 与 query | 详情 idx 放 path；非敏感的筛选、分页放 query，返回列表保留条件；路由输入仍需校验 |
| 临时交互 | 页面或组件的 useState/useReducer | 输入、选中项、弹层开关；无需全局 store |
| 跨步骤的未提交草稿 | 所属流程共同父级的内存状态 | 后续业务流程按需建立 provider，内部步骤切换不丢输入；不默认落盘，不承诺刷新后恢复 |
| 少量应用设置 | 本端 provider | 语言等设置；持久化方式由 Q04 确定，不共用三端会话 |
| 服务端数据 | 请求结果与所属页面/业务 hook | 余额、订单状态以后来自 API；不能另复制到全局 store 并当成权威事实 |

本项暂不增加 Redux/Zustand，也不建立自研查询缓存。等真实页面需要请求去重、缓存失效或轮询时，再评估 TanStack Query；如果采用 loader，同一数据不能再由页面 effect 重复请求。这里主要避免同时维护 URL、页面 state、全局 store 三份相同状态。

返回操作保留可识别的站内来源与 query；没有可靠站内来源时转到所属模块入口，不能仅凭 history.length 推断可以安全返回。深链接打开子页也应有可用出口。后续登录恢复和 Telegram 返回按钮由接入项实施，页面隐藏与路由守卫都不替代后端权限校验。

两个后台的 History 路由需要部署层支持页面路径回退，API 和资源请求不能被误回退为 HTML；列入 1.5 验收。用户端使用 Hash 路由，导航不改变服务器收到的页面路径，减少刷新时的子路径回退配置要求。首版不增加 SSR、路由服务端或通用页面保活框架。

#### Mini App 路由补充核对

用户提醒此前 Mini App 使用 Hash 路由。Telegram 官方文档未规定必须使用 Hash；History 原理上可以使用，但不能把普通浏览器中的可用性当成 Telegram 各客户端已经验证。此前统一推荐三端 History，未充分说明启动参数、刷新恢复和宿主返回按钮边界，已修订并确认采用用户端 Hash、两个后台 History。用户此前项目必须用 Hash 的具体原因没有证据，不推断为 Telegram 的统一限制。

Hash 的代价是与 Telegram 启动参数共用 URL fragment。核对官方 telegram-web-app.js，启动时先解析 location.hash，并通过 sessionStorage 保存及恢复 initParams。因此需要在创建 Hash Router 前完成启动参数读取和会话内恢复准备，再将 hash 规范化为应用路由；不能先重写 hash 再初始化 SDK，也不能把 tgWebAppData 当成页面路径。优先复用所选 SDK 的能力，存储不可用或启动数据缺失时明确处理；缓存数据不是已鉴权凭证，不延长其有效期，服务端校验仍属后续鉴权项。

Telegram 内分享的任务或付款入口应使用 t.me 的 startapp 参数，再映射到允许的内部路由；直接分享 `/#/...` 不能代替 Mini App 启动链接。Telegram BackButton 也需要显式订阅并调用应用的返回逻辑，Hash Router 不会自动接管宿主按钮。

1.4 应设计并验证路由创建前的启动适配顺序、首次启动与刷新时的参数恢复边界，不提前实现登录或业务 startapp 跳转。真实 Telegram 的 iOS、Android、Desktop/Web 启动、刷新、重开及返回表现，在 Mini App 接入项单独验证；当前没有实机验证证据。

#### 启动参数与现有架构的衔接

启动参数分三层：外部 t.me 链接的 `startapp` 表达业务入口；Telegram 将其传为 `initData` 内的 `start_param` 和页面 GET 参数 `tgWebAppStartParam`；平台初始化数据还包含用户、auth_date、签名等，经 SDK 暴露为原始 `initData` 与未验证的 `initDataUnsafe`。不能把这三层都当成 React Router 的 query，也不能认为 startapp 就是应用 hash。

例如 `https://t.me/<bot>/<app>?startapp=task_<opaqueRef>` 表示带任务上下文打开应用；此处仅说明参数用途，不确认正式编码协议。前端先读取上下文，后续由允许的业务目标映射为内部任务页。任务邀请还要保留邀请上下文；登录本身不绑定邀请关系，不自动领取奖励或付款。

现有三端独立应用、Vite 静态产物及 Go API 足以承接该流程：在 user 增加启动适配入口，保存类型明确的启动上下文和待处理目标；后台不依赖 Telegram 模块，共享请求库也不直接读取 Telegram 全局对象。后续 2.2–2.4 接入服务端验签、产品会话与来源页恢复。无需为此新增部署单元或改变业务分层。

GET 参数及 initDataUnsafe 可用于预选界面，不能作为已验证身份或授权依据；后端只信任通过验签及有效期检查的原始 initData，并另行检查任务、订单等业务权限。两处业务参数不一致时，不拼接、不静默覆盖已验证值；保留待处理状态或显示入口无效。签名验证成功也不代表参数指定的业务动作已获授权。

刷新同次启动时，保留当前有效内部路由，已处理的初始目标不再次强制跳转；鉴权失败重试仍保留未处理目标。明确的新启动上下文优先于旧的待处理目标，新启动无业务参数时也不能继承旧邀请。相同 startapp 在新的启动中仍可再次打开，不能永久按参数去重；Telegram 的 activated 事件本身也不能被当作收到新启动参数。新启动与刷新判定及 SDK 缓存合并行为必须单独验证，不假设 sessionStorage 自动解决全部问题。

结论是架构兼容、启动适配仍待实现，尚不能声称当前已有代码能完成真实 Mini App 启动与鉴权。Q02 已确认，具体实现及实测仍待完成。

### Q03：API 客户端与错误处理（已确认）

已确认使用原生 fetch，加一个职责有限的共享客户端工厂。当前只需要 JSON 请求、超时、取消与统一协议解析，fetch 可以满足；额外库也仍需实现项目错误语义和数据校验，因此首版不增加 Axios，不自建大型拦截器框架。待真实需求出现上传进度或特殊传输能力时再评估，不因此预先扩展 1.4。

职责分三层：`packages/api-client` 负责 HTTP 与公共错误；各应用 `src/api` 持有独立实例、端点调用和具体 data 校验；页面或业务 hook 负责加载、提示和恢复。类型继续从 .api 生成，运行时封装和校验保留在手写文件。共享包不读取 Telegram 全局变量，也不持有三端共用的认证状态。

| 情况 | 客户端行为 | 展示及恢复归属 |
| --- | --- | --- |
| HTTP 成功、code=OK、数据有效 | 返回已校验的响应，保留 data 与 traceId | 页面使用 data，后续业务状态以字段含义为准 |
| 标准业务失败响应 | 抛出含 code、HTTP status、traceId 的类型化错误 | 已知 code 映射本地文案；未知 code 通用兜底，保留原码 |
| 401/UNAUTHENTICATED | 明确返回认证失败，不自动刷新或重发 | 后续应用会话层统一处理失效，并保留 Q02 的待打开目标 |
| 403/PERMISSION_DENIED | 保留无权限错误 | 显示无权限，不当成会话过期反复登录 |
| HTTP 错误且不是标准 JSON | 保留 status，标为 HTTP 错误 | 通用错误提示，不把代理 HTML 当成业务数据 |
| HTTP 成功但 JSON 或数据不符契约 | 协议错误 | 明确失败，不能补成空列表或零余额 |
| 网络失败或超时 | 区分网络不可达与客户端超时 | 展示适当提示；超时不表示服务端已撤销操作 |
| 调用方主动取消 | 明确取消类型 | 页面退出等场景不弹失败提示；不承诺撤销已送达服务端的请求 |

默认采用 10 秒超时，可按端点覆盖，计时覆盖响应头与响应体读取，并在结束后清理计时器及取消监听。浏览器未提供原因时，不把网络错误武断归因为断网、DNS 或 CORS。后端和代理的超时配置分别管理，不以客户端计时代替服务端执行期限。

首版不自动重试请求。查询失败可由页面提供重试；写操作不能在网络超时或恢复登录后自动重发。后续支付等流程先查询原业务状态，幂等规则随所属业务项落实。请求库不弹 Toast、不跳转；避免一条错误既被公共层提示又被页面重复提示。

开发继续采用同源 `/api` 及 Vite 代理，三个应用分别创建客户端实例。生产的代理规则交 1.5；真实认证、续期、凭证存储和 Cookie 策略交 2.2–2.5，不在本项提前确定或实现。

### Q04：国际化、语言选择与展示（已确认）

已确认通过 react-i18next 将 i18next 接入 React，首版提供简体中文（zh-CN）和英文（en）。中文便于当前产品核对，英文作为跨地区用户的兜底；本项只维护实际出现的基础文案，不提前翻译全部未来业务页面。

| 场景 | 语言选择顺序 |
| --- | --- |
| Telegram 用户端 | 本端用户明确选择 → 启动上下文中受支持的 Telegram language_code → 浏览器语言列表中首个支持项 → 英文 |
| 普通浏览器用户端、商户端、管理端 | 本端用户明确选择 → 浏览器语言列表中首个支持项 → 英文 |

language_code 是可选的显示偏好，不作为身份或权限依据，也不因字段缺失阻塞启动。由已确认的用户端启动适配读取后注入国际化初始化；共享 i18n 包不访问 Telegram 全局对象。用户手动选择后，后续启动检测不能覆盖它。三端分别保存偏好，存储不可用时保留当前内存选择，不因此使页面不可用。

语言标签采用明确映射：en 及其地区变体映射到 en；明确简体标签（如 zh-CN、zh-SG、zh-Hans）映射到 zh-CN，显式繁体脚本不因地区字段被映射为简体。无脚本/地区的 zh 暂按未明确支持处理，继续检查下一来源；不声称已支持繁体中文。标签缺失、损坏或不支持时采用上述回退顺序。

公共资源只放通用操作、加载/空态和公共错误，应用维护自己的导航及后续业务文案。使用稳定语义 key、插值和复数机制；不拼接半句，不翻译 API 错误码、idx 或资产代码。切换语言同时更新组件库 locale、document.lang 和格式化结果，不重新挂载整棵应用，不清空输入、路由或待打开目标。两种语言的 key 和插值参数需一致；缺失中文优先显示英文，未知错误码用通用提示，产品界面不展示裸 key。

金额与时间沿用已有精度和时区边界：API 金额保留十进制字符串，展示明确资产/币种单位，语言切换不改变金额或计算规则；未知值不能写成 0，不把所有资产固定为两位小数。时间按用户设备时区展示，详情和后台查询明确时区，语言切换不改变时间点或统计区间。暂不增加汇率转换、账务舍入、跨设备偏好同步或完整金融格式化库；业务精度和报表统计时区随对应业务项落实。

备选为只提供一种语言，但会推迟第二语言下的长度、错误文案及组件适配验证。已确认本项即用两种语言验证完整基础链路，保留后续按资源扩展的能力。

### Q05：验收深度、样例与实施边界（待确认）

建议 1.4 交付三个可启动、可独立构建的真实前端骨架，并给已使用的基础能力留下可重复验证入口。用户端承接钱包／奖励／记录，两个后台各有工作台布局；业务尚未实现时明确显示未开放，不能用假用户、零余额或假订单填满页面。

| 验收层次 | 本项通过标准 | 证据边界 |
| --- | --- | --- |
| 工程与构建 | 固定版本及锁文件，三端分别启动、类型检查、构建通过；契约生成无漂移 | 记录实际命令与工具版本，不能只以开发服务器可打开为通过 |
| 自动化行为 | 请求解析、超时/取消、不自动重试、语言选择与回退、启动参数保留和目标生命周期可重复验证 | Vitest/React Testing Library；只在外部依赖边界 fake，不验证组件库内部实现，不以测试数量或覆盖率数字替代行为 |
| 浏览器交互与产物 | 导航、返回、未知路径、切换语言保留输入、移动/桌面布局可用；生产构建排除开发样例，用户端不带桌面 UI | 少量 Playwright 用例及必要截图；检查实际产物，不能只隐藏菜单 |
| 真实 HTTP 联通 | 开发样例经本端代理和共享客户端访问真实后端健康接口，收到并展示合法响应；失败后可明确重试恢复 | 独立集成入口，记录所用后端和响应；模拟错误场景另标为 fake，不混称真实联通 |

Mini App 是重点：用合成启动参数验证先读取再建路由、刷新不重复消费目标、新启动替换旧目标、无参数不继承旧邀请、存储不可用和语言回退。浏览器模拟不能证明 Telegram 宿主兼容；真实 Telegram 的启动、验签、返回与来源页恢复在 2.2–2.4 接入时验证，完整发布矩阵归 8.3，不拖到发布才首次检查基础接入。

浏览器建议先覆盖 Chromium 与 WebKit，用户端用窄屏触控视口，后台用桌面视口；这仅为 Web 浏览器证据，不等同于 Android/iOS Telegram 实机。测试以可见文案、可访问名称和用户操作判断结果，失败保存可定位的记录，不用固定等待时间掩盖异步问题。

开发样例放在独立入口或仅开发环境加载的模块，提供健康请求、加载/错误/恢复和基础交互演示；不进入产品导航，生产构建不能访问。认证错误等未有真实接口的场景使用明确标记的合成响应，不提前新增业务接口或假登录。

本项完成后再进入 1.5：从干净环境重放依赖准备、生成、构建和迁移，验证部署代理与 Redis/RocketMQ 隔离。1.4 不将这些环境工作或真实 Telegram 鉴权计为已完成，也不为验收提前实现账本、支付等业务。若检查失败，应修复或如实记录阻塞，不能将未执行项标为通过。

Q05 是本项最后一个待确认问题。确认后按现有方案实施 Q01–Q05，依赖版本核对、必要测试、记录更新、提交推送一并完成；已确认内容不重复讨论。
