# 1.3 后端公共基础 实施方案

[阶段目录](../README.md) · [全部工作记录](../../README.md) · [工作范围清单](../../../../engineering/工程阶段与工作清单.md)

方案确认范围：Q01 统一响应与错误码、Q02 配置与客户端生命周期、Q03 依赖故障与健康检查策略、Q04 事务入口、Q05 日志追踪与验收已确认。确认依据记录在 [讨论记录](01讨论记录.md)。本文保留已确认设计；实际实现、适配与验证结果分别见实施记录和验证记录。

## 目标与工作边界

在 1.1 工程结构和 1.2 契约生成基础上，建立 API 启动、配置、MySQL/Redis/RocketMQ 客户端边界、事务入口、统一响应、错误码、日志、追踪和健康检查。

不实现登录权限、业务表与资金操作，不建立业务缓存策略、消费者或可靠投递机制。前端请求运行时和国际化接入归 1.4，本地服务隔离联通及整体验收归 1.5，持久事件与消费恢复归 3.5。公共错误分类可定义鉴权失败，但不因此实现鉴权。

## 设计与实现步骤

### Q01 统一响应与错误码（已确认）

普通 JSON 业务 API 采用以下结构；成功与错误类型分别在 `.api` 中明确声明，接口成功 data 使用具体类型，不以 interface{} 或手写 TS 掩盖契约差异。统一写出响应时不得重复包装。

成功示意（HTTP 200）：

```json
{
  "code": "OK",
  "message": "",
  "data": { "items": [] },
  "traceId": "7bca..."
}
```

失败示意（HTTP 422，余额不足仅作未来业务示例）：

```json
{
  "code": "ACCOUNT_INSUFFICIENT_BALANCE",
  "message": "Insufficient balance",
  "traceId": "7bca..."
}
```

| 字段 | 规则 |
| --- | --- |
| code | 稳定字符串码，统一登记并使用具名常量；发布后不复用含义，前端不解析 message 判断结果 |
| message | 成功为空字符串，失败为安全简短的兜底说明；不直接输出 SQL、堆栈、凭据或原始依赖错误 |
| data | 成功为该接口明确类型；无业务数据时为 {}，空列表为 []；失败省略，不强制填 null |
| traceId | 关联本次请求及后端日志；生成、传播和入站校验细节随 Q05 确定 |

需要字段级错误时再定义明确类型的 fieldErrors，不先放任意结构 details。当前生成链不支持的指针/null 表达仍按 1.2 规则显式拒绝，不通过类型断言绕过。普通响应规则不强行套用到未来下载、流式协议或外部回调；健康检查契约随 Q03 明确。

| 场景 | HTTP 状态 | code 示例 |
| --- | --- | --- |
| 请求成功、资源创建 | 200 / 201 | OK |
| 已受理并异步处理 | 202 | OK |
| 参数缺失、格式或取值不合法 | 400 | INVALID_ARGUMENT |
| 未登录或凭证失效 | 401 | UNAUTHENTICATED |
| 无权限 | 403 | PERMISSION_DENIED |
| 资源不存在 | 404 | NOT_FOUND |
| 当前状态冲突 | 409 | PAYMENT_QUOTE_EXPIRED（未来业务示例） |
| 业务条件不满足 | 422 | ACCOUNT_INSUFFICIENT_BALANCE（未来业务示例） |
| 请求过于频繁 | 429 | RATE_LIMITED |
| 未预期内部异常 | 500 | INTERNAL_ERROR |
| 服务暂时不可用 | 503 | SERVICE_UNAVAILABLE |

HTTP 表达类别，code 表达具体原因。每类出口仍需遵守对应 HTTP 头及语义；具体接口逐项决定映射，不凭错误文本分类。HTTP 语义依据见 [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html)，429 见 [RFC 6585](https://www.rfc-editor.org/rfc/rfc6585.html)。

前端按 code 映射 i18next 文案，未知码采用通用本地化提示并保留 traceId；message 可作为安全兜底，不作为稳定协议。后端类型化错误保留原始 cause，日志为开发运维提供必要上下文，公开响应只返回安全内容。业务层不负责写 HTTP 响应。

请求成功与业务对象状态分开：查询成功可返回失败或处理中对象；202 仅表示受理。网络中断、超时或 500/503 不证明资金操作未执行，不自动重发资金写入。后续以幂等键、业务 idx、状态查询恢复结果；公共响应不提供一个通用 retryable 标志驱动盲目重试。这一规则不提前实现幂等或业务状态机。

go-zero 可通过 httpx 统一处理错误，但注册处理器只覆盖经过该错误出口的响应，见 [官方错误处理说明](https://go-zero.dev/guides/http/server/error/)。落实时检查参数解析、路由不存在、方法不匹配、panic、限流和超时等实际出口，统一由应用控制的 JSON 错误；已经写出的响应不能保证重新包装。网络断开或代理非 JSON 响应由 1.4 客户端单独处理。

实施顺序为：先改 `.api` 源及生成输入清单，验证成功/公共错误类型可派生到 Go 和 TS；再实现公共类型化错误与 HTTP 映射；最后验证实际服务出口。生成产物与源同次提交，保留手写扩展，不能仅在运行时包装却让 TS 仍描述未包装结构。

### Q02 配置与客户端生命周期（已确认）

- 使用显式选择的 YAML 配置文件，提交无凭据样例；环境变量注入连接凭据及部署差异。建议敏感字段通过 go-zero 的 env tag 注入，避免把任意密码直接拼进 YAML 文本；不混用多套覆盖规则。框架能力见 [配置说明](https://go-zero.dev/reference/configuration/overview/)，实际优先级与空值行为须通过锁定版本验证。
- 启动时校验环境名、地址、端口、超时、命名空间及必填项；配置错误明确退出，不悄悄使用另一个库或其他项目资源。首版不引入配置中心或热更新，修改后重启生效。
- MySQL、Redis、RocketMQ 在组装入口集中创建、共享并关闭，生命周期有明确所有者；业务模块通过实际需要的依赖访问，不每个请求重建客户端。连接凭据不进入仓库或公开响应，诊断保留不含凭据的目标和原因。
- 复用已有 Docker 服务；具体地址、协议、SDK 版本、鉴权来源与超时参数须在实施前核对，当前不声称已经兼容或连接成功。

### Q03 依赖故障与健康检查（已确认）

| 依赖或情况 | 启动与运行建议 | 边界 |
| --- | --- | --- |
| MySQL | 核心依赖；启动在有限时间内检查，失败明确退出；运行中故障使就绪失败并拒绝受影响请求，恢复后重新检查就绪 | 不自动迁移、不以空数据伪装查询成功；运行中保留诊断能力，不因依赖短暂故障立即退出 |
| Redis 只用于可丢失缓存 | 故障可降级为受控回源，并记录降级状态 | 具体缓存随使用方实现，必须考虑数据库负载；不是所有请求无上限回源 |
| Redis 承担会话、限流或正确性条件 | 使用该能力的请求在依赖不可用时明确拒绝，不能绕过校验 | 实际用途随业务确定，不能现在笼统承诺 Redis 故障都可忽略 |
| RocketMQ | 不使用 MQ 的能力可继续；尚未发送的操作可明确拒绝，已发送但应答超时须保留结果未知，不能伪装投递成功或断言未发送 | 只有后续可靠事件已经持久化并验证恢复时，才可承诺暂存后补发；1.3 不具备这项能力 |
| 未启用的能力 | 配置明确标为未启用，诊断反映真实状态 | 关闭依赖不等于把依赖它的业务接口伪装成可用 |

存活检查只反映进程是否能服务探测，不因依赖短暂故障反复重启；就绪检查反映当前服务承诺的核心能力。依赖检查有超时和合理频率，不让每次探测都触发业务写入或消息投递。详细诊断保留给开发运维，公开探测不暴露凭据。

如果 Redis/MQ 故障只影响部分能力，保留无关能力，同时由受影响接口返回明确错误；若它们已成为所有请求的必要前提，则纳入全局就绪条件。不要单凭“组件已纳入架构”推导每个组件都是全站硬依赖。具体端点与探测参数在 Q05 和实施中细化，业务能力加入时同步维护就绪条件，不重新讨论已确认原则。

### Q04 事务入口（已确认）

沿用 1.1 Q04：跨模块原子动作由最外层业务用例协调同一显式事务，协作模块不提前提交。以下工程落地方向已确认，不提前实现资金用例。

1. **使用 go-zero 的事务能力，保持入口小而明确。** 采用 `TransactCtx(ctx, func(ctx context.Context, session sqlx.Session) error)` 形态，由用例调用；依赖注入仅暴露所需事务能力，不建设通用仓储框架或事务传播框架。底层以 `sqlx.SqlConn.TransactCtx` 为基础，必要适配只补足错误与诊断要求。框架用法见 [go-zero MySQL 文档](https://go-zero.dev/guides/database/mysql/)。
2. **事务显式传递。** 用例把同一个 session 传给参与事务的模块方法，model 通过手写 `WithSession(session)` 扩展绑定；沿用 1.2 已验证的样例方式，不修改生成区。事务内相关读写必须走绑定后的 model/session，不能混用默认连接；不把事务藏入 context，也不临时替换共享 model 的连接。
3. **只有外层结束事务。** 回调成功才尝试提交；回调返回错误则回滚；panic 走回滚和内部异常诊断。子模块参与已有事务，不另开独立事务、不提前提交，不引入嵌套事务或保存点；需要独立调用时由独立的外层用例建立边界。
4. **失败保留原因，提交错误不伪装成确定回滚。** 记录开始、执行、提交或回滚阶段及原始原因；回滚失败须同时保留原始操作错误和回滚异常，不能把清理失败当正常业务拒绝。提交时断线或应答丢失可能无法确认结果，不返回成功，也不承诺未执行或已回滚，后续由业务幂等与查询恢复。锁定的 go-zero v1.10.3 在回滚失败时会把原始错误格式化为文本、包装回滚错误，panic 也转为 error；实施时须验证错误链和分类，必要时做最小适配，不假定默认行为已满足全部约定。
5. **事务保持短小，只协调同一 MySQL 库内的事务性操作。** 事务中不调用链上节点、第三方接口、MQ 发送或 Redis 写入；不在事务内执行迁移/DDL。必须原子持久化的事件随业务在同一数据库事务写入，之后由 3.5 投递。简单地“提交后立即发消息”不能替代可靠事件机制。
6. **公共层不自动重试。** 不统一重试整个回调、提交失败或超时；未来遇到死锁等场景，由具备幂等和确定回滚依据的具体用例制定有限重试策略。并发锁定顺序、隔离级别及资金不变量随所属业务确定，不把“有事务”当作并发正确性已得到保证。

概念示意：外层用例开启事务 → 模块 A 和模块 B 使用同一 session → 两者成功后统一提交；中途失败则回滚。这只验证公共机制，不在 1.3 创建账户、账本或转账接口。现有 [model 样例扩展](../../../../../backend/model/example/contract_sample_model.go) 可作为绑定方式依据，公共层自身尚未实现。

### Q05 日志、追踪与公共入口验收（已确认）

#### 日志与追踪

复用 go-zero 的 logx/logc 和 OpenTelemetry 追踪基础，首版结构化 JSON 输出到标准输出，便于本地和容器统一收集。暂不部署 ELK、Loki、Jaeger 或追踪收集器；不把外部日志/追踪服务作为启动依赖。参考 [go-zero 组件说明](https://go-zero.dev/components/) 与 [追踪说明](https://go-zero.dev/components/observability/tracing/)，实际行为以锁定版本及测试为准。

| 内容 | 建议 |
| --- | --- |
| 请求摘要 | 时间、级别、服务、环境、traceId、方法、路由模板、HTTP 状态、业务 code、耗时；已有业务上下文时增加主体和业务 idx，不为日志提前创建业务模型 |
| 级别 | 正常请求和预期业务拒绝记 info；降级、慢请求和异常取消等记 warning/slow 或等价结构化事件；系统错误、panic、事务提交/回滚异常记 error。普通 4xx 不一律升级为系统告警 |
| 原始原因 | 错误链、必要堆栈、失败阶段、依赖目标和关键业务参数保留给开发运维；同一次异常在明确责任出口记录，避免每层重复打印同一堆栈 |
| 凭据边界 | 不批量输出 Authorization、Cookie、连接密码或完整请求体；按需记录诊断字段，保留非凭据上下文。需核对框架默认访问日志的请求转储路径，不能只限制自定义 logger 却让内置日志旁路输出 |
| 高频探测 | 正常健康探测降低日志噪声；就绪变化、依赖失败和恢复必须留记录，仍能按需诊断 |

HTTP 入口建立有效 traceId，返回体 traceId 与上下文日志一致，并建议在响应头提供 `X-Trace-Id`。公共客户端请求由服务端建立追踪；仅在明确可信的内部调用或网关边界继续合法的 W3C traceparent。缺失、无效或不可信来源不直接采信任意客户端 traceId 字符串；可信入口配置在实际部署时落实。前端跨域读取响应头的暴露配置交 1.4/1.5，不以放开任意来源代替。

同一请求只维护一套有效追踪上下文；不在响应、日志和框架中分别生成不同 ID。不启用外部导出或不采样时仍须具有有效关联 ID；404/405、参数错误、panic、限流、超时和健康路由同样验证覆盖。当前版本的 trace handler 会提取入站头并创建 span，实际入口顺序、无 exporter 时的 ID 生成与框架路由外错误都需验证，不能仅依赖配置默认开启即宣称满足要求。

#### 公共路由与运行行为

建议正式 API 初期只加入 `GET /health/live` 和 `GET /health/ready` 两个公共探测路由，沿用 `.api` 权威源与完整响应生成。1.2 的回显示例继续隔离在测试区域；故意触发异常的入口只存在于测试服务，不注册到正式 API。

- `/health/live`：进程可响应探测时返回 HTTP 200、code OK、data.status 为 live，不查询数据库或消息中间件。
- `/health/ready`：初始化完成、未进入停机且核心依赖检查有效时，返回 HTTP 200、code OK、data.status 为 ready；未就绪返回 HTTP 503、code SERVICE_UNAVAILABLE，按 Q01 省略 data。只公开最小结果，依赖地址和详细原因进入开发运维日志。
- 就绪检查采用有时限的依赖检查与状态快照；检查尚未完成、过期或失败时不报告就绪。健康路由不能被业务依赖门禁一起挡住，否则无法判断恢复。Redis/MQ 是否影响整体就绪严格沿用 Q03，而非自动加入全部必需依赖。
- 普通请求、依赖调用和探测都设置有限超时，依赖调用预算不超过请求剩余时间，传播取消信号。开发起始建议为普通请求 5 秒、单次依赖调用上限 3 秒、探测 1 秒、探测间隔 5 秒、结果有效期 15 秒、停机宽限期 30 秒；均可配置，是起始工程参数，不是业务 SLA。MQ 启动等 SDK 特殊超时在兼容性核对后单独配置，不能套入不适用的请求预算。
- 超时响应不证明数据库或外部操作未执行，仍遵守 Q01/Q04 的结果未知与不自动重试规则；测试需证明取消被传递，不声称超时能强制中止所有外部副作用。
- 收到停机信号后先使就绪失败并停止接收新业务请求，在有限宽限期内等待进行中的请求，再关闭依赖客户端并刷新日志。超出期限记录未完成请求及阶段后结束；后续资金恢复依靠持久业务记录，不依赖进程无限等待或日志本身。

#### 实施与验收顺序

Q05 确认后直接实施已确认的 1.3 范围：先建立正式 API 源和公共响应/错误出口，再组装配置与客户端，补事务基础，最后接入日志、追踪、健康检查和关闭流程。同步扩展生成清单和检查入口，不覆盖 1.2 的手写边界。客户端 SDK、现有 Docker 服务协议和鉴权来源先核对，版本与实际验证证据写入实施记录。

单测以 fake 验证不可靠依赖，HTTP 测试通过真实 handler/server 验证行为；真实 MySQL/Redis/RocketMQ 连接测试独立运行并使用项目隔离资源，不停止或修改用户共享容器来制造故障。1.3 验证本项运行机制，1.5 继续承担干净环境准备与全栈联通。没有接入证据的组件如实记录，不能以 fake 测试声称真实服务已通过。

## 验收条件

以下为验收基线，执行结果见 [验证记录](04验证记录.md)：

1. `.api` 生成的成功和公共错误类型与真实 JSON 一致；成功 data 的明确类型、空对象、空数组、失败省略 data 均有验证。
2. 公共错误码与 HTTP 映射稳定；类型化错误保留 cause，未知异常映射为安全的内部错误；不直接暴露原始依赖错误。
3. 对参数解析、404/405、panic、限流和超时出口做真实 HTTP 行为测试；验证状态码、响应结构和 traceId，明确已写出响应及代理错误的边界。
4. 请求受理和业务完成语义分离；错误响应不暗示资金未执行，不引入盲目重试机制。使用无业务副作用测试对象，不建业务表验证这些公共规则。
