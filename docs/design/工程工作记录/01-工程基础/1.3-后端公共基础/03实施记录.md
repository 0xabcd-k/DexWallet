## 原交付适配与原因（2026-10-27）

1. **生成保持源优先。** 新增 platform.api，成功与错误类型直接生成 Go/TS；错误码常量从同一 `.api` 枚举派生，未另手写一份编号。生成清单扩为 8 个纯生成文件和 16 个受保护骨架，增加正式源变更及手写 main 保留测试。
2. **凭据在解析后注入。** 原 env tag 方案在重复加载/空环境变量用例中出现旧值沿用，改为 YAML 解析后显式读取环境并校验；同时避开 conf 自动调用 Validate 导致先于注入校验的问题。特殊字符不会拼入 YAML；未提供 DSN 必须失败。此调整保留 YAML + 环境变量的确认方向。
3. **事务采用小型适配。** go-zero v1.10.3 的默认事务路径使用 Begin，回滚失败把原始错误格式化为文本，panic 转为 error。适配器使用同一 sql.DB 的 BeginTx 与 sqlx.NewSessionFromTx，保留请求取消、失败阶段、原始/回滚错误和 panic 堆栈；调用仍为 TransactCtx + 显式 session。提交错误按未知处理，不自动重试。context 只保存嵌套拒绝标记，不隐藏事务对象。
4. **统一处理真实 HTTP 出口。** go-zero 生成路由 + Serverless 适配保留路由机制，net/http 负责监听与退出；统一外围处理追踪、错误、并发准入与缓冲超时，覆盖 404/405。替换默认中间件链及 404 包装，避免双 trace、请求转储和文本错误。不是重新实现路由或声明已有鉴权。
5. **生命周期明确。** 请求超时后响应缓冲不再写给客户端，实际 handler 仍计入退出等待；有诊断错误的迟到完成继续留日志。停机使就绪失败并禁止新业务准入；框架自己的强退时限延长到应用宽限之后。客户端最后关闭，关闭异常不吞掉。
6. **复用本地服务。** MySQL 9.4.0、Redis 8.2.1（两者 host 网络），RocketMQ 5.3.2（NameServer 9876、Broker 10911，brokerIP1 为本机地址）。仅记录非凭据元数据。采用 rocketmq-client-go/v2 v2.1.2 remoting 客户端；Redis SDK v9.21.0 与 go-zero v1.10.3 依赖保持兼容，版本在 go.mod/go.sum 固定。

## 验证中发现与修正

- 正式 `.api` 经 goctl 格式化后列间空格变化，错误码提取改为匹配空白，不依赖单个空格。
- 依赖选择时出现 Go MVS 将 go-zero 降级的提示，立即恢复既定 v1.10.3 并采用其要求的 go-redis v9.21.0，最终未迁移框架版本。
- 环境注入与自动校验顺序问题由配置测试暴露并修复；缺失、重复加载和特殊字符用例已通过。
- 额外检查了 go-zero 进程信号处理的默认强退预算，使其不早于应用设置的退出宽限。

## 遗留与工作边界

- MQ 已验证 NameServer 协议访问和 Broker TCP 连接，未发送/消费消息。1.5 进行隔离 topic 收发，3.5 建立可靠事件、重试、去重与恢复。
- Redis 只有客户端、命名空间与故障分类，缓存回源、会话和权限逻辑随业务建立；不宣称已实现业务降级机制。
- 原交付 HTTP 使用 4 MiB 缓冲上限；2026-10-28 已由原生超时缓冲替换，当前资源边界见下方补充，不包含流式下载。公共入口建立新的追踪根，可信网关透传/跨服务追踪待实际部署边界确定。
- 现有无认证 Redis/MQ 路径验证通过；有认证部署、生产版本与容量参数仍需在对应环境验收。SDK 内部连接阶段超时不等同于应用探测预算。
- 1.3 没有登录、账本、资金接口、worker 或消息消费者，也没有启动三个前端应用。

## 2026-10-29：原生启动与全项目复用复核

用户已授权修复，目标是降低维护复杂度。分支 `fix/native-gozero-runtime`，起点 `27235df`。以下取代上轮保留自建 HTTP 生命周期的判断；历史记录保留当时事实。

| 复核范围 | 处理与具体依据 |
| --- | --- |
| HTTP server、监听、信号、关闭与网络期限 | 删除自建 Server/Serve、生产 Serverless 及 signal.NotifyContext，返回原生 rest.Server 并使用 StartWithOpts；沿用框架网络超时，不手设另一组参数。测试适配器才使用 Serverless |
| 关闭顺序 | 使用 proc 的 wrap-up 停止准入，shutdown 钩子等待实际 handler。钩子并行不等于无法协调：starter 等全部 shutdown listener 后才返回，再由主函数关闭依赖；工作超时诊断、HTTP 卡住时原生强退分别验证 |
| 前端请求取消/超时 | 删除手写 timer、监听器转发和 reason 状态，采用 AbortSignal.timeout/any/throwIfAborted；只保留首个中断来源到项目错误的映射。活动时间遵循浏览器标准；无需增加依赖 |
| HTTP 错误、请求日志 | 保留。httpx 负责写出；RecoverHandler 等直接 WriteHeader 不走 SetErrorHandlerCtx，LogHandler 在 5xx 转储请求，不能直接满足统一 JSON、错误原因关联及凭据边界；不为套用原生中间件增加通用响应缓存/拦截器 |
| 追踪、指标、请求超时 | 已使用框架 TraceHandler/Telemetry/TimeoutHandler/Metrics/Prometheus。外围追踪为覆盖 404/405 并建立服务端根，路由装饰只记录匹配模板；不自建追踪 provider 或响应超时缓冲 |
| 并发与请求体 | 保留使用 syncx.Limit/http.MaxBytesReader 的薄适配。原生 MaxConns 按路由且位于超时外侧，超时响应返回就释放；项目需要实际工作结束才释放及探测豁免。MaxBytesHandler 只检查 ContentLength，不能覆盖未知长度流；两者默认拒绝出口均不返回项目 JSON |
| 配置及依赖 | conf.Load/RestConf、database/sql、go-redis、RocketMQ SDK 已负责配置解析、连接池和协议。剩余代码为环境凭据注入、项目预算/资源校验、客户端组装与关闭，不另建配置中心、连接池或为了统一包名迁移 SDK |
| SQL 事务 | 保留现有薄适配。锁定版本 sqlx 的事务失败与回滚双错只对回滚错误使用 %w，提交错误没有阶段标记，无法完整保留已确认的错误链和提交结果未知语义；当前仍使用标准库事务及原生 sqlx.Session |
| 健康 | 保留必需/可选依赖、探测结果有效期和业务准入策略；框架监听器健康不等于这些应用需求，未引入另一套探测服务 |
| 路由、国际化、Telegram | 已复用 React Router、i18next、Intl.Locale/DateTimeFormat、SDK 启动参数缓存及 URLSearchParams/Web Crypto。剩余是语言来源优先级、站内返回白名单和启动目标消费状态，不改成通用插件层。金额展示仅做精确字符串校验/分组，保留原小数位，不引入金额计算或浮点转换 |
| 生成、迁移、隔离测试工具 | Go/TS/model 生成已交 goctl，迁移已交 golang-migrate；脚本保留版本锁、手写文件保护、错误码派生和隔离资源归属/精确清理。进程组清理是测试子进程树收尾，不能用只杀直接子进程的默认 timeout 等价替代 |

框架证据为锁定版本 [starter](https://github.com/zeromicro/go-zero/blob/v1.10.3/rest/internal/starter.go)、[engine](https://github.com/zeromicro/go-zero/blob/v1.10.3/rest/engine.go)、[proc](https://github.com/zeromicro/go-zero/blob/v1.10.3/core/proc/shutdown.go) 和 [事务实现](https://github.com/zeromicro/go-zero/blob/v1.10.3/core/stores/sqlx/tx.go)，均核对本地 module cache。前端采用 [DOM AbortSignal 标准](https://dom.spec.whatwg.org/#interface-abortsignal)，通过真实 Chromium/WebKit 复核运行兼容性。未新增运行时依赖、业务接口或数据库迁移。


### 2026-10-29 再审：能力对照与启动取消修复

用户要求重新阅读代码，并确认框架能力有无丢失。对照 `27235df` 与 `7248f0f`：路由及生成注册、Timeout、Metrics/Prometheus、TraceHandler、JSON 错误、并发计数、请求体限制、事务和健康策略保留；原先关闭的 Breaker/Shedding/Gunzip 未在本轮删除。网络超时变为框架默认推导，前端计时改为浏览器活动时间，是上一轮已记录的行为差异。

发现并修复一处确定回归：删除旧 signal.NotifyContext 时移除了依赖初始化的取消来源，而运行期退出钩子注册在依赖打开之后。现在于初始化之前使用原生 SetTimeToForceQuit 和 AddWrapUpListener，传递可取消的启动 context，并在首次探测及监听前检查取消；没有恢复第二套信号处理。主函数不再因错误链包含取消而整体忽略退出错误，避免同时发生的清理失败被当成成功。

本轮修复仅涉及启动入口；没有改 HTTP 中间件、业务契约、前端实现或运行时依赖。
