## 原交付适配与原因（2026-10-27）

1. **生成保持源优先。** 新增 platform.api，成功与错误类型直接生成 Go/TS；错误码常量从同一 `.api` 枚举派生，未另手写一份编号。生成清单扩为 8 个纯生成文件和 16 个受保护骨架，增加正式源变更及手写 main 保留测试。
2. **凭据在解析后注入。** 原 env tag 方案在重复加载/空环境变量用例中出现旧值沿用，改为 YAML 解析后显式读取环境并校验；同时避开 conf 自动调用 Validate 导致先于注入校验的问题。特殊字符不会拼入 YAML；未提供 DSN 必须失败。此调整保留 YAML + 环境变量的确认方向。
3. **事务采用小型适配。** go-zero v1.10.3 的默认事务路径使用 Begin，回滚失败把原始错误格式化为文本，panic 转为 error。适配器使用同一 sql.DB 的 BeginTx 与 sqlx.NewSessionFromTx，保留请求取消、失败阶段、原始/回滚错误和 panic 堆栈；调用仍为 TransactCtx + 显式 session。提交错误按未知处理，不自动重试。context 只保存嵌套拒绝标记，不隐藏事务对象。
4. **统一处理真实 HTTP 出口。** go-zero 生成路由 + Serverless 适配保留路由机制，net/http 负责监听与退出；统一外围处理追踪、错误、并发准入与缓冲超时，覆盖 404/405。替换默认中间件链及 404 包装，避免双 trace、请求转储和文本错误。不是重新实现路由或声明已有鉴权。
5. **生命周期明确。** 请求超时后响应缓冲不再写给客户端，实际 handler 仍计入退出等待；有诊断错误的迟到完成继续留日志。停机使就绪失败并禁止新业务准入；框架自己的强退时限延长到应用宽限之后。客户端最后关闭，关闭异常不吞掉。
6. **复用本地服务。** MySQL 9.4.0、Redis 8.2.1（两者 host 网络），RocketMQ 5.3.2（NameServer 9876、Broker 10911，brokerIP1 为本机地址）。仅记录非凭据元数据。采用 rocketmq-client-go/v2 v2.1.2 remoting 客户端；Redis SDK v9.21.0 与 go-zero v1.10.3 依赖保持兼容，版本在 go.mod/go.sum 固定。

## 验证中发现与修正

- 正式 `.api` 经 goctl 格式化后列间空格变化，错误码提取改为匹配空白，不依赖单个空格。
- 依赖选择时出现 Go MVS 将 go-zero 降级的提示，立即恢复既定 v1.10.3 并采用其要求的 go-redis v9.21.0，最终未迁移框架版本。
- 环境注入与自动校验顺序问题由配置测试暴露并修复；缺失、重复加载和特殊字符用例已通过。
- 额外检查了 go-zero 进程信号处理的默认强退预算，使其不早于应用设置的退出宽限。

## 遗留与工作边界

- MQ 已验证 NameServer 协议访问和 Broker TCP 连接，未发送/消费消息。1.5 进行隔离 topic 收发，3.5 建立可靠事件、重试、去重与恢复。
- Redis 只有客户端、命名空间与故障分类，缓存回源、会话和权限逻辑随业务建立；不宣称已实现业务降级机制。
- 原交付 HTTP 使用 4 MiB 缓冲上限；2026-10-28 已由原生超时缓冲替换，当前资源边界见下方补充，不包含流式下载。公共入口建立新的追踪根，可信网关透传/跨服务追踪待实际部署边界确定。
- 现有无认证 Redis/MQ 路径验证通过；有认证部署、生产版本与容量参数仍需在对应环境验收。SDK 内部连接阶段超时不等同于应用探测预算。
- 1.3 没有登录、账本、资金接口、worker 或消息消费者，也没有启动三个前端应用。

## 2026-10-28：成熟库能力替换

用户明确授权后在已同步的 `docs/backend-library-reuse` 上实施，起点 `6ec30ec`；改造与本段同次提交，无业务表、迁移或服务配置变更。

| 范围 | 已落实内容 |
| --- | --- |
| 配置 | 嵌入 RestConf，复用框架默认值、Mode/Telemetry/Shutdown；原 RequestTimeout/MaxInFlight/MaxBodyBytes 改为 Timeout/MaxConns/MaxBytes；增加单位和配置组合校验 |
| 输出 | 使用 httpx.WriteJsonCtx、SetErrorHandlerCtx、ErrorCtx；类型契约和 HTTP 错误映射不变，JSON 预序列化保证失败仍返回安全 JSON |
| 超时 | 默认链启用 TimeoutHandler；删除自建计时、goroutine 和响应缓冲；取消后空返回、迟到写入与异常有行为测试；写入后 panic 中止连接并保留诊断，不拼接错误或返回假成功 |
| 追踪/指标 | 框架共享 provider 与 TraceHandler 覆盖路由及 404/405；动态模板通过 Router 公共接口记录；保留原生 Metrics/Prometheus 节点，未部署采集平台 |
| 准入/诊断 | 用 syncx.Limit 管理全局实际任务名额；结构化日志从 runtime 分离；超时响应和迟到异常使用同一 traceId，无请求凭据转储 |
| 保留边界 | 标准库 MaxBytesReader、有序 Shutdown/worker 排空、事务失败阶段/错误链、依赖健康策略；依据见方案补充 |

框架原生超时允许 SSE/WebSocket 跳过，JSON 入口对此返回 400；Breaker/Shedding/Gunzip 尚未适配统一契约，配置误开会报错。测试验证 401 的认证挑战与 403 的区分，不代表实现鉴权。旧 4 MiB 响应上限删除，当前健康响应固定大小；后续列表必须按接口限制规模。版本保持 go-zero v1.10.3，go.mod 仅将 OTel API/SDK 的直接与间接依赖关系调整到实际使用。

完整检查和真实进程信号证据见 [验证记录](04验证记录.md)。1.5 全栈环境、MQ 消息收发及业务可靠性仍按原工作边界推进。
