## 已确认前提

- 单 Go module、Go/go-zero、MySQL SQL-first、三个独立 React/Vite 应用及构建产物继续沿用。
- 本地直接复用已有 MySQL、Redis、RocketMQ，不覆盖其容器、网络、配置或数据卷。资源按项目/环境隔离；不重新讨论是否引入 Redis/MQ。
- 配置采用 YAML 与环境变量，迁移显式执行，生成与应用启动不隐式迁移。现阶段只有隔离示例迁移，没有正式业务表。
- 用户端 Hash Router、后台 History Router、同源 `/api` 客户端、独立会话边界和开发样例生产隔离继续有效。
- 复用成熟工具，不额外建立通用环境管理框架；普通检查与真实依赖测试分开。鉴权、账本、worker 和可靠投递留给所属工作项。

### Q01：建议与理由

建议按用途区分运行方式，沿用现有开发入口：

| 用途 | 运行方式 | 原因 |
| --- | --- | --- |
| 日常开发 | 宿主机运行 Go API 和三个 Vite；连接现有 Docker 中间件 | 直接使用当前工具链、热更新和调试，不增加容器内外源码/网络映射 |
| 自动化集成 | 独立配置、测试资源和进程；端口冲突即退出；只结束自己启动的进程 | 避免影响正在开发的 API 和其他项目服务，重复执行结果可追溯 |
| 构建产物部署验收 | 宿主机运行编译后的 API，项目独立 Nginx 容器提供三端静态站点和代理；只绑定本机回环地址 | 验证静态资源、实际代理与 History 刷新，覆盖 Vite 开发/preview 未证明的部署行为 |

本轮只读核对：已有 mysql/redis 容器使用 host 网络，rmqnamesrv/rmqbroker 使用 rocketmq 网络；RocketMQ 镜像标签为 5.3.2。`docker compose version` 返回子命令不可用。因此建议当前不将 Compose 作为必装前提，后续用标准 Docker 命令启动项目自己的 Nginx。该方式以当前 Linux 环境为基线；迁移到其他宿主系统时重新验证宿主机访问方式。

对比选项：全容器化可以统一应用运行环境，但当前需要额外处理 Go/Vite 调试、宿主机依赖地址及网络；先不采用。只使用 Vite/preview 虽方便，却无法验收正式静态服务与代理配置，也不作为本项交付。

这不改变最终一个 API、一个 worker、三个站点的架构；当前没有 worker 业务，1.5 不创建空 worker 进程。也不要求现在购买域名或部署到公网。
