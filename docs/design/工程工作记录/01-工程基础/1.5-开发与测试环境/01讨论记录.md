### Q01：建议与理由（按后续 Q03 讨论调整）

建议按用途区分运行方式，沿用现有开发入口：

| 用途 | 运行方式 | 原因 |
| --- | --- | --- |
| 日常开发 | 宿主机运行 Go API 和三个 Vite；连接现有 Docker 中间件 | 直接使用当前工具链、热更新和调试，不增加容器内外源码/网络映射 |
| 自动化集成 | 独立配置、测试资源和进程；端口冲突即退出；只结束自己启动的进程 | 避免影响正在开发的 API 和其他项目服务，重复执行结果可追溯 |
| 构建产物本地检查 | 三端 build 后用 Vite preview，按需代理到独立测试 API | 验证产物、路由和联通；Nginx 部署行为留到 8.2 验收 |

本轮只读核对：已有 mysql/redis 容器使用 host 网络，rmqnamesrv/rmqbroker 使用 rocketmq 网络；RocketMQ 镜像标签为 5.3.2。`docker compose version` 返回子命令不可用。后续用户提出本地直接使用前端代理，因此本项不要求安装 Compose 或新建 Nginx 容器。

对比选项：全容器化可以统一应用运行环境，但当前需要额外处理 Go/Vite 调试、宿主机依赖地址及网络；先不采用。本地采用 Vite/preview；正式静态服务与代理配置由 8.2 单独验收，不作为 1.5 完成前提。

2026-10-28 后续讨论取消强制独立 worker 部署：首版一个后端进程承载 HTTP 与后台任务，三个站点保持独立产物和域名方向。当前尚无后台业务，1.5 不创建空 worker。正式环境拓扑、无状态条件、发布与恢复建议统一记录在 [8.2 实施方案](../../08-发布与多端扩展/8.2-部署与恢复/02实施方案.md)，不以本机验收替代生产验收。

本地用例优先自动收尾；强杀或清理失败时，保留不含凭据的运行标识与资源清单，恢复清理只针对清单中的确切资源，并核对归属，不扫描前缀批量删库或删 topic。共享 MySQL、Redis、MQ 容器一直保留。
