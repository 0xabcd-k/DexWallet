### Q01：建议与理由

建议按用途区分运行方式，沿用现有开发入口：

| 用途 | 运行方式 | 原因 |
| --- | --- | --- |
| 日常开发 | 宿主机运行 Go API 和三个 Vite；连接现有 Docker 中间件 | 直接使用当前工具链、热更新和调试，不增加容器内外源码/网络映射 |
| 自动化集成 | 独立配置、测试资源和进程；端口冲突即退出；只结束自己启动的进程 | 避免影响正在开发的 API 和其他项目服务，重复执行结果可追溯 |
| 构建产物部署验收 | 宿主机运行编译后的 API，项目独立 Nginx 容器提供三端静态站点和代理；只绑定本机回环地址 | 验证静态资源、实际代理与 History 刷新，覆盖 Vite 开发/preview 未证明的部署行为 |

本轮只读核对：已有 mysql/redis 容器使用 host 网络，rmqnamesrv/rmqbroker 使用 rocketmq 网络；RocketMQ 镜像标签为 5.3.2。`docker compose version` 返回子命令不可用。因此建议当前不将 Compose 作为必装前提，后续用标准 Docker 命令启动项目自己的 Nginx。该方式以当前 Linux 环境为基线；迁移到其他宿主系统时重新验证宿主机访问方式。

对比选项：全容器化可以统一应用运行环境，但当前需要额外处理 Go/Vite 调试、宿主机依赖地址及网络；先不采用。只使用 Vite/preview 虽方便，却无法验收正式静态服务与代理配置，也不作为本项交付。

2026-10-28 后续讨论取消强制独立 worker 部署：首版一个后端进程承载 HTTP 与后台任务，三个站点保持独立产物和域名方向。当前尚无后台业务，1.5 不创建空 worker。正式环境拓扑、无状态条件、发布与恢复建议统一记录在 [8.2 实施方案](../../08-发布与多端扩展/8.2-部署与恢复/02实施方案.md)，不以本机验收替代生产验收。

## 2026-10-28：确认部署方向，细化 Q02

用户回复“采纳你的意见”，确认上一轮正式部署建议。已同步 8.2 及决议台账；本项仍按逐项讨论推进，生产确认不自动扩大为本地测试资源创建、购买云资源或执行生产发布。

Q02 建议采用“开发数据长期保留、自动化测试资源按次分配”的方式：

| 用途 | 建议资源 | 生命周期 |
| --- | --- | --- |
| 日常开发 | 独立开发库（示例名 `dexwallet_dev`）；沿用 local 环境的 Redis/MQ 命名空间 | 明确初始化一次，日常启动不清库、不隐式迁移；开发数据保留 |
| MySQL 自动化测试 | 保留已有随机 `dexwallet_contract_` 库机制；HTTP/部署联通分配自己的专用测试库 | 运行前分配，正常结束删除本次创建的库；examples 仅作用于隔离契约库 |
| Redis 自动化测试 | 使用现有 RedisKey/Namespace 方法，在测试环境中附加本次运行标识，记录完整 key | 先设置 TTL，再按完整 key 清理；不清整个 DB |
| RocketMQ 自动化测试 | 每次独立 topic、消费组和客户端实例标识，消息带本次运行标识 | 结束先关闭客户端，再清理本次资源；未能清理的元数据如实记录 |

建议将资源准备权限和应用运行权限分开：准备入口可建测试库/账户，应用只使用指定库。当前后端 integration 测试会创建随机库，前端 integration 则要求调用者先提供专用库，两者权限要求不同；继续保留独立入口，通过明确的外层准备/清理流程衔接，不把日常 API 提升为建库工具。

本地用例优先自动收尾；强杀或清理失败时，保留不含凭据的运行标识与资源清单，恢复清理只针对清单中的确切资源，并核对归属，不扫描前缀批量删库或删 topic。共享 MySQL、Redis、MQ 容器一直保留。

本轮只形成 Q02 建议，尚未创建库、账户、key/topic 或实现清理脚本。更具体的命名与验收见 [实施方案](02实施方案.md#q02资源隔离与清理)。

## 2026-10-28：Q02 确认，进入 Q03

用户以保持生产数据库干净为前提采纳 Q02。测试只使用明确的开发/测试目标、专用凭据和隔离资源；不从生产复制数据作为默认样例，不使用生产账户运行集成用例、清理脚本或 examples 迁移。仅改库名前缀、环境标签不构成生产隔离，具体保护措施须实施验证。

Q03 建议用一个项目专用 Nginx 容器提供三个独立静态站点，后端仍是一个测试进程；不为三端建立三个 API：

| 应用 | 本机部署验收入口（建议） | 路由行为 |
| --- | --- | --- |
| 用户端 | `http://127.0.0.1:18080/#/wallet` | 沿用 Hash Router |
| 商户端 | `http://127.0.0.1:18081/overview` | History 路由直接访问/刷新正常 |
| 平台端 | `http://127.0.0.1:18082/overview` | History 路由直接访问/刷新正常 |

三个站点各自的 `/api/health/live` 均转到本次测试 API 的 `/health/live`；保留状态、JSON 和 traceId。三端 dist 分别只读挂载。HTML 页面、静态资源、API 使用不同匹配规则：后台页面导航可以回入口，缺失资源仍返回 404，API 失败不能回一个成功的 HTML 页面。代理不缓存 API，也不为失败请求自动重试。

本机先验证构建产物、代理、刷新与停服恢复，端口可配置且冲突即退出；不要求现在绑定公网域名或证书。正式环境已确认三个 HTTPS 域名，地址/TLS 属环境参数；本机不同端口不等同于完成真实域名、会话隔离或 Telegram 客户端验收。
