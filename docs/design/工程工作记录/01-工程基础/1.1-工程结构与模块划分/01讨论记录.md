## Q04：需要拿捏的边界

用户已确认按 Q04 的细化建议推进：保留明确的事实所有权和写入入口，相关模块在一个 Go module 中直接协作，包与文件只随真实业务增长。以下保留选择理由，详细场景和实现约束见 [实施方案的 Q04 细化](02实施方案.md#q04-细化拆分尺度与具体顾虑)。

| 顾虑 | 具体后果 | 推荐处理 |
| --- | --- | --- |
| 按表生成 CRUD 后直接拼业务 | 领奖、支付、后台各自更新余额，遗漏凭证、幂等或余额约束 | SQL-first 决定数据定义来源；业务按行为组织，资金变动只经 ledger，SQL 扩展留在所属 model |
| 模块分别提交事务 | 任务已完成但未到账，用户已扣款但商户未记应付款 | 所属业务用例开启一个事务，传给协作模块；模块参与事务，不自行提前提交 |
| 充值、支付各认一份链上到账 | 同一实收被重复使用，给用户和商户各入一次账 | chain 统一保存实收与受约束分配；不同业务分别决定自己的完成条件 |
| 退款、结算各写一套打款恢复 | 广播超时被误当失败，释放占用后又发第二笔 | payout 统一执行身份和链上恢复；业务分别拥有额度、审核、占用及终态 |
| 抽象粒度过细 | 阅读一次领奖要跨许多包，规则分散，循环依赖或接口仅做转发 | 上一版职责表作为所有权清单，先按协作业务理解；邀请、Pro、抽奖等保持局部职责，不单独做服务或通用规则引擎 |
| 模块隔离过于机械 | 后台列表一次查询拆成大量服务调用，SQL-first 的查询表达能力被削弱 | 授权后的只读聚合允许明确的 JOIN/查询模型；业务写入仍走所属模块，查询不得偷带状态修改 |

其中统一账务、同一实收不重复入账、未知出款不重复执行沿用现有要求；本项确认的是职责、调用及共同事务边界，具体锁算法和函数签名随业务落地。部署单元及中间件分别按 Q05、Q06 执行。

## Q06：本地服务与后续落点

用户要求 Redis 与消息中间件现在进入架构，并授权直接复用本地 Docker 已有服务。本轮只读检查发现：`redis` 运行于 host 网络；`rmqnamesrv`、`rmqbroker` 使用 `apache/rocketmq:5.3.2` 镜像，运行于 `rocketmq` Docker 网络。NameServer 映射宿主机 9876，Broker 映射 10909、10911、10912、8080、8081。容器运行与端口映射不表示 SDK、鉴权、Proxy 或消息生产消费已验证。

消息中间件在当前方案中按现有服务落为 RocketMQ；不另选并新建一套队列。本轮未修改容器、读取凭据、创建 topic、写入 Redis 或发送消息。详细本地接入证据及待验证项见 [实施方案](02实施方案.md#q06redisrocketmq-与持久任务的关系)。

Redis 承接缓存，RocketMQ 承接异步事件；MySQL 保留业务与账务事实。建议以同事务持久事件（outbox）衔接 MySQL 提交与消息发送，由 worker 的发布/消费角色处理，具体表、协议、重试及失效策略交 3.5 确定。Q04 中要求原子完成的奖励与记账不拆成两个最终一致的消息步骤。
