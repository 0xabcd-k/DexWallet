## 目标、依据与范围

确定技术栈、目录、模块职责、调用关系和部署单元，为 1.2–1.5 及后续业务提供一致入口。详细建议集中在 [实施方案](02实施方案.md)，此处维护选项、确认依据和后续动作。

本轮已阅读 [项目入口](../../../../README.md)、[开发规范](../../../../engineering/开发规范.md)、[决议台账](../../../../decisions/决议与待落实事项.md)、[系统架构与契约](../../../04系统架构与契约.md)、[工程阶段与工作清单](../../../../engineering/工程阶段与工作清单.md)、本项四份工作记录，并结合产品总览、钱包支付、任务奖励和商户平台需求。个人开发习惯中的契约生成、业务分层、国际化及测试原则沿用，不能将技能中的默认栈当成用户已确认选型。

本轮只修改方案文档与必要的索引措辞。后续 1.1 确认后也只建立约定范围内的工程结构；鉴权、账本、奖励、签名、监听、支付、数据库业务表等仍由所属工作项实现。完整工程基础可运行是 1.1–1.5 的联合目标，不是本轮文档已完成的能力。

## 待逐项确定的问题

以下 Q 编号仅属于 1.1，不替代决议台账的 C、D、O 编号。所有推荐均为待确认建议；可以逐项决定，不需要一次回答全部内容。

| 编号 | 需要确定的问题 | 推荐与理由 | 备选及代价 | 确认影响 |
| --- | --- | --- | --- | --- |
| Q01 | 后端与主数据库 | Go + go-zero/goctl，MySQL/InnoDB；契约生成与个人习惯相符，同库事务支撑业务单据与账本一致 | Go 标准库 HTTP 可减少框架约束，但需自行补齐生成和接入约定；PostgreSQL 也能满足事务需求，但应另验模型生成及迁移工具 | 后端依赖、数据访问和 1.2 生成方向 |
| Q02 | 前端基础栈 | React + TypeScript + Vite，pnpm workspace，Less、i18next；适配 H5 与后台，独立 Go API 暂无 SSR 需求 | 需要 SSR 时再评估 React 全栈框架；当前引入会增加另一套服务运行职责 | 前端包组织与构建方式；UI 库、语言集合在 1.4 细化 |
| Q03 | 工程及管理前端拆分 | 单仓库，一个后端 Go module；`frontend/apps/user`、`merchant`、`admin` 三个独立应用 | 一个管理应用包含商户与平台两套路由可少一个构建，但共享发布、会话与资源隔离更难核查 | 推荐三个应用、独立产物及域名；仍由后端执行权限隔离 |
| Q04 | 业务模块与依赖 | 按方案职责表划分；账本统一入口，任务与奖励分责并由任务领奖用例编排共同事务；独立支付、充值、退款、结算业务 | 将所有资金业务合为一个大模块初期文件少，但状态归属与恢复责任容易混淆 | 确认模块所有权、事务方向及禁止的依赖；不是一次生成全部空目录 |
| Q05 | 运行与部署单元 | 一个 API 进程、一个后台 worker 进程、三个静态站点、一套业务数据库；平台签名单独信任边界 | 业务逐个拆服务增加分布式事务和运维；worker 后续可按监听/出款/通知负载拆进程 | 1.1 只定部署图；worker 在 3.5、链任务及签名在 5.3 实现 |
| Q06 | 中间件与异步机制 | 首版以关系库持久任务及事务事件为基础，暂不把 Redis、MQ、服务发现设为必需 | 有实际缓存、限流或吞吐需求时引入 Redis/MQ，但不能替代资金幂等和持久事实 | 1.3、1.5 基础依赖；3.5 讨论任务领取、重试和恢复细节 |
| Q07 | 契约组织方向 | `.api` 作为 HTTP 权威源，SQL DDL + 增量迁移为数据库源；前端类型从同一 API 源派生 | OpenAPI 先行也可行，但需替换或适配后端生成路线；不能两套源并行手改 | 这里只确定方向和目录；1.2 验证 TS 生成链、工具版本与覆盖规则 |
| Q08 | 1.1 落地深度与后续交接 | 确认后只初始化必要工程清单和依赖边界，维护结构说明；1.2 生成、1.3/1.4 公共基础、1.5 环境各自推进 | 一次在 1.1 做完可运行全栈会吞并后续工作项，难以逐项讨论和验收 | 明确 1.1 完成条件；不预先创建业务接口、表、状态机或签名假实现 |

建议先讨论 Q01，再讨论 Q02–Q03，随后 Q04–Q07，最后核定 Q08 的执行范围。目录名称可随结构决议一起调整，不把命名另设成阻塞事项。
