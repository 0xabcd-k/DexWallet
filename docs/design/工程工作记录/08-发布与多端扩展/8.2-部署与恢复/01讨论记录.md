## 已有约束与本次调整

沿用 Go/go-zero、MySQL SQL-first、Redis、RocketMQ、三个独立前端产物及平台签名信任边界。2026-10-28 用户指出 worker 与 API 不必物理分开、独立部署增加麻烦，当前方案据此采用一个后端程序/进程同时承载 HTTP 与后台任务；后台任务仍需持久化、有限并发、可恢复。当前代码只有公共基础，尚无业务后台任务。

“无状态”指业务正确性和恢复不依赖某个进程的内存或本机文件，不代表程序不能有连接池、健康快照或缓存，也不代表任意数量副本都安全高效。多副本领取、幂等、会话与资金并发分别随阶段 2、3、5 落实。

## 待讨论问题

| 编号 | 事项 | 当前建议与待定内容 |
| --- | --- | --- |
| P01 | 应用拓扑 | 一个后端部署单元，首版同进程运行 API/后台任务；生产建议两个完整副本分布于不同故障域。两副本是建议，数量/规格待容量与预算确定 |
| P02 | 数据基础设施 | 优先评估托管高可用 MySQL、Redis 及兼容现有 SDK 的 RocketMQ；自建时分别设计集群、备份和运维，不与应用发布绑定 |
| P03 | 流量、域名与密钥 | 三个独立 HTTPS 域名，同源 /api 代理；数据库/MQ/Redis 私网访问，管理端限制入口；签名能力继续隔离 |
| P04 | 发布与恢复 | 固定镜像摘要、兼容性迁移、分节点摘流发布、应用回退；完整备份与增量恢复、恢复后业务核对 |
| P05 | 验收与成本 | 云/机房、地区、域名、预算、并发/任务规模、可接受停机与恢复目标、运维责任待明确；不据此虚构报价或可用性承诺 |
