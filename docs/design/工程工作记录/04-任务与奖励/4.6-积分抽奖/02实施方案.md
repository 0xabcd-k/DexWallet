# 4.6 积分抽奖 实施方案

[阶段目录](../README.md) · [全部工作记录](../../README.md) · [工作范围清单](../../../../engineering/工程阶段与工作清单.md)

方案依据：用户要求继续下一项与既有 C17/R09–R10；工程实现范围是本地开发全流程，候选奖表不代表生产发布确认。

## 范围与契约

包含单次抽奖、版本规则展示、余额/缺额、结果动画、历史/详情、账本来源跳转、原键恢复及独立测试工具。没有空奖、奖池、保底、自动连转、购买积分或额外 Pro 门槛。按当前产品用户鉴权，不额外要求当下绑定 Telegram 才能使用已有积分。

接口源为 platform.api：GET /v1/user/draw-state；POST /v1/user/draws；GET /v1/user/draws/by-request/:requestKey；GET /v1/user/draws；GET /v1/user/draws/:idx。对外使用 idx，金额/积分是精确字符串；请求只接受 requestKey 与 versionIdx 作为抽奖语义，不接受前端指定奖项、金额或随机票。

## 存储与计算

business 13 新增 draw_rule_version、draw_control、point_draw。版本名唯一，内容包含金额、万分权重及三个图案；所有七档权重非负、总和 10000，金额正数且精确到美分，图案与奖项唯一匹配，期望金额必须精确匹配配置 RTP。允许权重为 0，避免把文档中的 0.90 调整示例静默裁剪成其他概率。

当前指针初始为空，迁移不发奖、不安装候选表。发布只追加版本，同名同内容可重复调用，同名异内容拒绝；已提交记录保留版本、100 积分投入、奖项、奖励金额、图案、随机票和凭证编号。历史显示取自己的快照与不可变版本名，不套用当前奖表。

## 事务与并发

1. 校验请求并按本人/原键查已提交事实；暂停或版本切换后仍先返回原结果。
2. 开始事务，锁当前产品用户并复查禁用及 auth_version；之后首个快照读取原键，处理并发同键。
3. 共享锁定当前版本指针，复查预览版本；变化返回 DRAW_VERSION_CHANGED，不能自动更换。
4. 后端均匀随机取票，按版本权重确定奖项并插入抽奖单据。调用公共 account.Post，在同一凭证中按 POINT 与 USD 分别平衡：用户 task_points 借方、平台 point_consumption 贷方；平台 reward_expense 借方、用户 reward_usd 贷方。
5. 保存凭证编号并提交。资金不足、任一写入失败都回滚，无“已扣积分待开奖”的持久中间状态。账户余额由公共入口锁定/复查；Pro 与邀请关系不写入。

同用户的任务领奖和抽奖在用户锁上排队；不同用户不共用资金互斥锁，配置指针是共享读锁。只有明确回滚的死锁最多重试一次，同次服务端重试复用随机票；锁等待超时返回繁忙。提交应答丢失先查原键，未找到仍为未知，不换键重抽。

## 前端与恢复

奖励页进入 /draws，显示可消费积分和待提现奖励；不足 100 时显示差额和任务入口。奖表规则列出全部七档与概率，提示 RTP 是长期期望，非个人承诺。

提交前按 API 服务与用户隔离持久化 requestKey/versionIdx，以短时 Web Lock 协调多标签；网络请求不持有 Web Lock。重载只展示查询/重试入口，不自动提交。结果响应需校验金额、100 积分、凭证、图案及原版本，失败不清原请求。确定版本变化或资金不足时，先核对原结果；确认未找到才刷新规则/余额并等待用户再次点击。

收到已结算结果后才播放短展示动画；查询恢复/历史不重播，支持系统减少动态效果设置。历史及详情不会发起 POST，两个账户的恢复信息隔离。

## 验收

用确定随机票穷举 10000 个区间位置验证每档数量及 $0.095 期望，不以随机统计测试代替概率正确性。真实隔离 MySQL 验证同键并发、异键竞争余额、原子回滚、提交未知、版本切换、归属鉴权和任务并发不改 Pro；浏览器验证缺额、确认、原键重载、跨标签及结果展示。实际记录见 [验证](04验证记录.md)。
