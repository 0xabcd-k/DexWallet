# 4.5 奖励事务整合 实施方案

[阶段目录](../README.md) · [全部工作记录](../../README.md) · [工作范围清单](../../../../engineering/工程阶段与工作清单.md)

方案状态：2026-11-14 已细化，尚未实施。当前应用数据库仍要求 business 11，没有新增领奖接口或执行本方案迁移。

## 原子边界

一次成功领奖在同一 MySQL 事务内提交：任务完成事实与资格消耗、首奖状态、首次邀请关系、全部受益人奖励和账本分录、Pro 进度及解锁。任一步失败全部回滚，没有“任务已完成、奖励待补发”的业务中间态。

Telegram 成员查询在事务外；mock 只替换这个不可靠外部边界。MQ、后台任务和通知不承担发奖或补齐部分分录，页面从数据库查询提交结果。当前无消费方需求，不为本轮新增独立奖励投递/重试状态机；后续订阅通知按 3.5 的事务事件方式接入。

## SQL-first 模型

字段名为实施草案，完整 DDL、约束、迁移、生成配置先改源定义。对外新增 TaskCompletion、TaskInvitation 类型的 idx；RewardGrant 复用已有类型。

| 模型 | 职责和必要约束 |
| --- | --- |
| task_completion（扩展已有） | 参与者、稳定 TG 身份、请求键及完整请求语义、任务/身份/绑定版本、本人/助力模式及 invitation、首任务/老用户阶段、验证时间及结果、任务标题/基础积分/规则版本快照；保留 (task_id, telegram_identity_id) 和 (user_id, request_key) 唯一约束 |
| user_reward_state | 产品用户唯一；首次完成编号及时间、累计 Pro 进度、永久解锁时间。缺失行仅在不存在历史完成的情况下等价于从未完成；写入前先锁用户行 |
| task_invitation | 任务、邀请者、创建时间；任务和邀请者组合唯一，不因生成链接占用参与资格 |
| user_referral | 子用户唯一、直接上级、建立关系的首次完成编号及时间；无用户修改入口 |
| reward_grant | 完成编号、实际受益人、原因、现金/积分、当笔权益、进度增量与前后值、解锁结果、凭证编号；(completion_id, user_id, reason) 唯一 |

精度沿用现有账户约束，进度保持非负整数；完成记录的 user_id 始终是参与者，不把邀请者代填为完成者。外部身份引用保留到解绑之后，防止删除/重建绑定刷新次数；奖励则永久归属实际入账的产品用户。

每份非零奖励通过现有 account.Post 和 BusinessReward/rewardGrantID/ActionPost 记账。奖励行、凭证关联及账户更新必须一同提交；不允许留下有奖励行无凭证的已提交结果。无积分收益的老用户助力仍有完成记录，个人结果明确本次资格已用，不伪造零金额流水。

本人没有奖励记录时，完成结果只显示当笔收益及进度增量为零；当前 Pro 状态通过 reward-summary 另查，不把当前状态冒充历史快照。

下一版迁移编号以实施时分支实际版本为准，本方案不预占或直接运行迁移。4.1 正式应用尚未写完成记录；升级前仍检查历史数据。若发现已有完成却无可证明的首奖/账务历史，明确列为迁移异常，不猜测补发或把该用户当新用户；隔离测试夹具需同步更新，不以清空业务库解决。

## 执行顺序和锁

1. 校验当前产品登录态与请求格式，查询本人原请求。已成功且参数一致直接返回；参数不一致报请求键冲突。历史恢复不重新执行成员验证，也不因任务后来到期或换绑丢失结果。
2. 新请求读取当前用户、TG 绑定及版本、任务和邀请上下文，检查有效期及资格。按当前绑定的 TG 数字 ID 调用 mock 验证器，保存本次内存快照。未关注或验证失败直接返回，不开启资金写事务。
3. 预先确定参与者、实际任务积分获得者及其直接上级，去重并按内部用户 ID 升序锁定用户行；再按同序读取/初始化奖励状态。此顺序与既有转账、身份业务的用户行锁一致。新用户本人首任务没有普通积分分成，不预锁假想上级。
4. 在事务中再次查询原请求，然后复查当前 Actor 状态、认证版本、参与阶段、邀请者资格和关系。接着锁定使用的 TG 绑定，复查归属、identity_revision、binding_version；即使解绑后绑回同一 TG，也不能沿用旧验证。
5. 对任务定义取得共享读锁，复查 revision、启用状态、模式与有效期；不把热门任务整行排他锁作为所有领奖的串行入口。任务配置变更路径须与此锁序兼容。以锁后数据库 UTC 时间作为本次结算判定时刻，验证和结算均落在 [starts_at, ends_at) 内。
6. 复查稳定外部身份资格及预先确定的关系。若参与阶段/上下文已变，返回需重新核对的错误；不在锁集合变化后临时逆序追加用户锁。仍有效的关系不会改绑；受锁保护后使用最新 Pro 状态计算。
7. 插入完成记录，必要时建立首次关系、更新首奖状态；调用 4.3 计算，按受益用户固定顺序写奖励、通过现有账本锁顺序记账、更新 Pro。所有外键目标用户已提前锁定，避免各业务在用户与资金行之间反向加锁。
8. 事务提交后返回完成结果。失败释放数据库锁并全部回滚；API 超时本身不证明数据库已回滚。

同一用户涉及多种角色时只锁一次用户/状态行，分别记录奖励原因；同一邀请者的并发助力需要串行更新其 Pro，这是当前金额计算所需的一致性。不同用户且没有共同受益人的任务可并行，不加全局 Redis 资金锁。

## 幂等和未知结果

- 请求键沿用现有互转规范：16–64 位允许字符，作用域为产品用户。保存并比较任务、mode、invitation 及 expected 字段构成的原始请求语义，不只比较键。
- 相同键、相同参数：并发最多一份完成，之后返回相同完成与本人奖励快照；新的实时余额通过余额接口另查，不能用它改写历史结果。
- 相同键、不同参数：明确冲突，不能把请求挪到新任务或新邀请。已成功后即使条件失效，也先恢复原结果，再考虑新操作。
- 不同键、相同 TG/任务：数据库唯一约束拒绝第二次消耗，返回资格已使用；不把旧完成伪装成用新键创建的成功。本人可通过完成列表查询旧结果，其他产品用户不得查询原归属详情。
- 发生提交结果未知时，从主库按原键核验。查到则成功；查询失败或未查到仍保留未知，不换键。后续同键重试即使与原请求仍在执行，也受用户锁和唯一约束保护；执行前仍检查是否已经提交。
- 只有数据库明确回滚的死锁可沿用现有事务策略有限重试（最多重试一次），并重新校验状态与时间。锁等待超时、回滚确认失败、连接中断和未知提交不能作为无限重试理由；保留具体诊断和请求关联信息。

## 验收与故障注入

| 场景 | 必须观察到的结果 |
| --- | --- |
| 四种主路径 | 完成记录、各受益人金额/积分、所有凭证、首奖/关系和 Pro 与 4.3 计算一致 |
| 两个任务并发争首奖 | 同一产品用户最多一份首奖；旧 first 请求不会静默变为 returning 助力 |
| 同 TG 同任务并发、解绑后换用户 | 只消耗一次资格；产品首奖不随绑定重置，原奖励不迁移 |
| 验证时换绑、回换、禁用或任务到期 | 旧快照不能提交，所有完成和奖励写入为空；已先提交的历史事实保持 |
| 在完成、关系、第一份奖励、后续分成或 Pro 更新后注入失败 | 所有新增事实、余额和权益一同回滚，无部分发奖 |
| 提交成功但响应丢失 | 原键返回同一完成；任务后来到期/暂停也能恢复；凭证不增加 |
| 主库恢复查询失败或暂未找到 | 展示未知并保留原参数，不断言失败，不自动换键 |
| 本人、邀请者和上级交叉并发，或与现有互转并发 | 用户锁顺序一致；死锁处理有限且不重复发奖；并发 Pro 以实际序列判定 |
| 其他用户查完成/奖励 idx | 拒绝越权，不返回身份、关系或资金信息 |

纯规则测试不连接外部依赖；事务与约束使用显式独立 MySQL 集成测试，外部查询使用可控 fake/mock；浏览器覆盖领取、助力确认及恢复。实现时执行契约生成检查、Go race/vet、对应集成入口、前端类型/测试/构建及浏览器检查。本轮只有文档检查，不能把这些计划用例写为已经通过。
