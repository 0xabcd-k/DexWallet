## 已验证的业务结果

- 四条奖励主路径：本人首奖、邀请首奖、老用户本人任务、老用户助力；$1 和 1000 进度不被写成 1000 可消费积分。
- 邀请重复创建返回同一条；首任务前禁止邀请；本人历史及奖励归属受鉴权限制。
- 助力者为邀请者上级时只取分成且不增 Pro；禁用上级仍有被动分成，但禁用邀请者不能取得新的助力。
- 精确翻倍、20% 向下取整、零分成不写账；跨 2000 当笔不翻倍。并发助力在进度 1500 时分别按 500、1000 入账，只解锁一次。
- 同键并发仅一笔完成；同键异参拒绝；首次任务竞争仅一份首奖；任务随后暂停仍能恢复原结果。
- 在全部奖励入账后注入状态写入失败，全事务回滚；三受益人的首奖/任务积分/分成及新关系一起回滚，修正故障后原键可成功。
- 绑定版本变化拒绝旧证明；TG 转到其他产品用户仍保留次数消耗；原产品用户不绑定该 TG 也可恢复原完成，其他用户不可读原结果。
- 提交响应丢失后恢复同一完成；未知提交且查询未找到保持未知。前端重载后只查询/重试原请求，不自动生成新键。
- 老用户助力须确认；首任务在其他页面先完成后，旧邀请确认不能静默消耗资格；邀请启动解析不执行外链跳转、不自动领奖。
- 完整 DDL 与逐步迁移一致；空奖励迁移可降级，有业务数据不静默删除；旧只读 /check 保持无资金写入。

## 发现与修正

1. go-zero 的 SQL 映射不能直接将单列时间扫描到 time.Time，改为带明确字段名的结构读取数据库 UTC。
2. 旧完成夹具需显式标记模式/阶段及历史版本；完整 DDL 的索引顺序与增量迁移对齐。
3. 独立测试账号不具备创建触发器所需权限，故障注入改用测试库专用 CHECK 约束，不扩大账号权限。
4. HTTP 组合测试的旧账本夹具先使用了 reward 来源 ID 1，新奖励记录在同一隔离测试内改用不相交的编号段；不修改实际业务分配规则、不对共享库重设自增。
5. goctl TS 不在 body 类型里生成 path 字段，前端显式组合路径 idx 与生成的请求类型，未手改生成文件。
6. 成功页最初混有下一次奖励预估，已去除并补充浏览器断言与复验。
