# 4.3 奖励计算与 Pro 实施方案

[阶段目录](../README.md) · [全部工作记录](../../README.md) · [工作范围清单](../../../../engineering/工程阶段与工作清单.md)

方案状态：2026-11-14 已细化，尚未实施。奖励数值继承 [业务规则 R01–R08](../../../../product/02业务规则.md) 和 [任务与奖励](../../../../product/04任务与奖励.md)，不重新调整首奖、门槛或费率。

## 计算职责

建立无数据库副作用的奖励计算函数。输入为后端已确认的参与者阶段、本人/助力模式、基础积分、实际任务积分获得者的结算前 Pro 状态及直接上级；输出明确的受益人、奖励原因、金额、积分和进度增量。函数不查询 Telegram、不创建邀请关系、不写余额；身份、关系与事务校验归 4.4、4.5。

| 完成场景 | 参与者 | 实际任务积分获得者 |
| --- | --- | --- |
| 新用户本人首任务 | reward_usd 增加 1.00；Pro 进度增加 1000；可消费积分不增加 | 无普通任务积分 |
| 新用户经邀请完成首任务 | 同一份首奖，不叠加普通任务积分 | 邀请者，按邀请者原有 Pro 计算 |
| 老用户本人任务 | 本人取得任务积分，并增加等量 Pro 进度 | 参与者本人 |
| 老用户为他人助力 | 无本人直接任务奖励；消耗本次资格 | 邀请者，按邀请者原有 Pro 计算 |

“无本人直接任务奖励”与直接上级分成的交叉解释见 [4.4](../4.4-邀请与助力/02实施方案.md)，该解释仍单列为建议，不据此改写已确认产品规则。

## 精度与顺序

1. 从受锁保护的状态判断是否首次任务，以及实际任务积分获得者在本次发奖前是否已有 Pro。
2. 普通用户任务积分为基础积分，Pro 为基础积分的 2 倍。只对实际任务积分获得者应用一次翻倍。
3. 其直接上级获得 floor(最终任务积分 × 20%)；没有上级则无分成。上级自身 Pro 不再放大分成，分成不继续向上递归。
4. 首奖给参与者增加 1000 Pro 进度；普通任务或助力所得任务积分给实际获得者增加等量进度。分成、抽奖和积分消费不影响进度。
5. 更新累计进度，达到 2000 永久解锁 Pro。跨过门槛的这一笔使用更新前权益，后续奖励才翻倍；消费积分不降级。

美元按 2 位小数、积分及 Pro 进度按非负整数处理；API 使用字符串，后端使用现有精确金额能力或整数运算，不用 float。累计字段按现有金额容量校验，不能把整数或数据库精度溢出转成负值或静默截断。20% 取整只用于分成，不对本人的任务积分额外取整。

首奖只有一份现金，不产生普通任务积分或现金分成。计算出零分成时不建立零金额账本分录；这不影响主奖励结算。Pro 是累计权益状态，不增加一种可消费资金账户。

## 账本与快照

每个非零奖励对应一个 reward_grant，原因使用具名枚举：首奖、本人任务、助力任务、上级分成。同一用户可能兼具不同角色，记录原因分别保留。

| 奖励 | 借方 | 贷方 | Pro |
| --- | --- | --- | --- |
| 首奖现金 | 现有平台奖励支出 USD | 本人 reward_usd | 本人 +1000 |
| 本人/助力任务积分 | 现有平台积分发行 POINT | 实际受益人 task_points | 受益人 +最终任务积分 |
| 上级分成 | 现有平台积分发行 POINT | 直接上级 task_points | 不增加 |

通过 account.Post 写入，不越过账本改余额；业务来源复用 BusinessReward 与 RewardGrant idx。一份奖励凭证内按单位平衡，不将 USD 与 POINT 相加。各份凭证及 Pro 更新均在同一外层事务，见 4.5。

完成记录保存任务版本、基础积分及规则版本；奖励记录保存当笔权益、实际金额/积分、进度前后值及是否解锁。历史结果读取当时快照，不套用后来的基础积分、关系或 Pro。当前只需保存版本和具名参数，不建立任意公式配置引擎。

## 确定性验收

| 输入 | 预期结果 |
| --- | --- |
| 新用户本人完成 | 待提现奖励 1.00，积分 0，进度 1000 |
| C 是 Pro 用户 A 的上级；新 B 经 A 邀请完成基础 200 的任务 | B 得 1.00 和进度 1000；A 得 400 积分和进度 400；C 得 80 积分且进度不变 |
| 老用户进度 1500，尚非 Pro，完成基础 500 的任务 | 当笔得 500，进度 2000 并解锁；下一笔基础 100 得 200 |
| 普通任务最终 7 积分且有上级 | 上级得 1 积分；最终 4 积分时分成 0，不写零分录 |
| Pro 上级收到 80 分成 | 只得 80，无翻倍、无递归、无进度 |
| 已解锁用户消费积分 | 可用积分减少，累计进度及 Pro 不变 |
| 同一受益人并发取得跨门槛的两份奖励 | 按事务锁串行化的先后判定；恰好一笔触发解锁，后一笔按 Pro 计算 |
| 输入非法或累计超出存储容量 | 明确报错，整笔结算不提交；不裁剪奖励 |

本项纯函数单测与 4.5 的真实账本集成测试分别证明计算和落账；不以只检查内部函数调用次数替代余额、流水和进度结果。
