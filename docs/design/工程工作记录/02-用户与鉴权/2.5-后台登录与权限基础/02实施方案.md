方案状态：2026-10-30 已确认账号开通渠道、独立用户表及 Q03–Q06；Q01 已确认密码与邮箱验证码必须同时通过；Q07 已确认延期。全部退出不在交付中。实现及验证见 [实施记录](03实施记录.md) 和 [验证记录](04验证记录.md)。

## 目标与工作边界

以最少的固定权限接通平台、商户后台登录，管理账户独立于产品用户。交付登录/改密/退出、后台账号管理、产品用户状态管理、操作记录查询和两端页面接入。

依赖已完成的契约生成、数据库事务、idx、统一响应、Redis 和前端基础。企业/商户主体、资金操作、细粒度角色、多级审批、设备会话管理及后台自助注册不在本轮；敏感操作再验证已确认延期；尚无主体的商户账号只能使用本人账户相关功能。

## 设计与实现步骤

### 数据与代码边界

管理端用户与商户端用户分别建表，使用 admin_user、merchant_user，均独立于产品 user；不使用一张后台账户表加类型字段替代。邮箱及密码散列、状态、认证版本、时间等直接平铺，每端邮箱独立唯一；临时密码首登修改按已确认方案执行，字段按实际流程建立。后台验证码独立存入 backoffice_challenge，按所属端及邮箱唯一，绑定认证版本；操作记录独立建表 backoffice_audit，记录执行者及目标所属端，避免两张用户表的内部 id 混淆。商户主体绑定待 6.1 的真实模型确定后增加约束，不创建虚拟商户占位。

操作记录保存明确动作、执行者、目标、允许记录的前后状态、原因、结果和 traceId。密码、token 等材料不进入该表；当前仅覆盖已实现的管理动作，后续业务按需增加动作类型。对外账户使用 idx，并新增具名编码类型，不能混用产品用户编码上下文。

先改 SQL DDL 和 business 增量迁移，再运行现有 model 生成；手写查询、事务和缓存扩展留在保护边界。沿用公共 ServiceContext、transaction.Runner、API 错误语义和 Redis 命名规则，不再建立通用鉴权框架或另一套 HTTP 服务。

### 认证与授权

密码验证使用成熟库，邮箱验证码复用现有发送与校验能力并隔离用途和所属端；密码与邮箱验证码都必须通过，同一次登录的两项验证须绑定同一后台类型和账户；验证码通过前不签发登录 token，不把部分验证成功当作已登录。按后台类型、邮箱和来源限流，失败提示不泄露账号是否存在。全部管理端账户均通过后端服务器上的 super 可执行程序手动创建；源码入口 backend/tools/super，构建为独立二进制，与 API 共用配置和业务用例，不通过新增远程管理接口绕行。商户账户在管理端创建。工具的创建动作同样记录审计，复用事务规则；业务服务不在启动时创建默认账户。

后台 token 与产品 token 的签名配置分开，平台/商户 audience 分开，每次请求核对后台类型、状态和认证版本。复用已有 JWT 和响应头续签所需能力，角色权限从当前管理账户状态判断，客户端传入的账户或商户 ID 不赋予权限。

执行临时密码首登修改；完成密码＋邮箱验证码登录后，若需首次改密，仍只有一种 token，后端只允许当前账户查询、改密和退出。改密成功更新认证版本，当前端获得新 token；其他端旧 token 失效。普通鉴权缓存固定 30 秒，禁用/改密等提交后清缓存；Redis 异常返回暂不可用，不穿透数据库。管理写入在事务内复核最新权限，不能靠过期缓存完成操作。

重复开通由唯一约束拒绝；重复启用/禁用保持版本不变，但记录本次操作。密码重置每次明确提交均产生新认证版本，并要求首登改密；前端不自动重试写入，网络结果未知时先查询账户或重新登录。验证码已消费后不重放 token，须重新发送验证码登录。并发禁用平台管理员时保护最后一个可用管理员，具体锁定顺序在实现中统一。成功业务变更与操作记录同事务；写入记录失败不得伪装管理操作成功。

### API 与页面

在现有 `.api` 中分开 `/v1/admin` 和 `/v1/merchant` 路由域：登录、当前账户、改密；普通退出沿用客户端清理。不开放全部退出按钮或公开接口，已有产品用户内部能力保留，后台不为尚无需求的整体退出增加接口。平台额外提供后台账户列表、商户用户开通、账户状态/重置、产品用户查询/状态、操作记录分页列表及行内详情。按真实字段生成 Go 和 TypeScript，草案路径不视为已实现 API。

管理端页面不提供创建管理端用户入口，创建动作由 super 承接。两端复用现有 Ant Design 桌面布局和请求能力，增加登录页、个人账户与改密入口；平台增加管理账号和记录页面。凭证存储、来源恢复、401/503 和迟到响应处理按端隔离，只提取确有重复的实现，不复制产品用户的邮箱/TG 表单或写一个全局三端会话容器。所有可见文案进入国际化资源。

登录后恢复合法站内页面并重新查权限；必须改密时先完成改密。商户主体尚未接通时明确显示待开通，现有资金和业务页面继续按未开放显示。

## 验收条件

1. super 在后端服务器手动创建管理端用户，管理端创建商户用户；登录不自动注册，网页/API 不提供管理端用户创建入口，两端数据表独立。
2. 密码和邮箱验证码缺少或错误时都不能登录，验证码不能跨端、跨账户或重放；两项通过后才签发登录 token。错误材料和不存在账号行为一致且受限流。首次改密限制按已确认方案执行。
3. 产品 token、平台 token、商户 token 互相不能越权；商户访问平台路由失败，未绑定主体无商户业务权限。
4. token 的 3 天期限、36 小时续签边界、并发响应、普通退出符合 Q04，且无全部退出入口；改密/禁用旧凭证失效，缓存窗口与关键写入实时校验分别验证。
5. 并发禁用不能移除最后一名可用平台管理员；管理状态、认证版本与成功操作记录同事务，失败不留下成功记录。
6. 禁用产品用户后拒绝新登录和业务操作，恢复不重新激活旧 token；既有数据和已受理业务不被删除。
7. 操作记录成功/失败均可追踪，只读查询不泄露凭据；两端直达、刷新、过期、无权限与依赖不可用显示正确状态。
8. 生成漂移、Go race/vet、前端类型/构建及行为测试通过；真实数据库/Redis 独立验证，运行环境凭据不提交。当前 TG 开发环境的数据和配置保持隔离。
