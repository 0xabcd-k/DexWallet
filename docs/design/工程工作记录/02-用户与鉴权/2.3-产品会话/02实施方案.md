# 2.3 产品会话 实施方案

[阶段目录](../README.md) · [全部工作记录](../../README.md) · [工作范围清单](../../../../engineering/工程阶段与工作清单.md)

方案状态：单 token 时效与响应头续签规则已确认，以下为本版工程设计，待实现细化；2.3 未实施。确认依据记录在 [讨论记录](01讨论记录.md)。

## 目标与工作边界

已确认范围调整（2026-10-29）：不实现单次登录的服务端撤销、设备列表或指定设备退出，不为此建立设备会话表。普通退出清理当前端凭证；用户级整体失效沿用 auth_version，保留禁用、退出全部设备以及解绑/换绑后的规则。2.2 认证操作记录继续承担材料单次消费与幂等恢复。

用户确定单 token 有效期 3 天，剩余不足一半时通过响应头更新；因此不采用此前建议的 15 分钟访问凭证与独立刷新凭证。保留最近真实认证起算最长 30 天上限。具体 JWT claims、客户端持久存储和公开接口在实施前细化，不把文档记为已上线能力。

## 设计与实现步骤

1. 采用单 JWT，复用框架及成熟 JWT 库；每次受保护请求校验签名、必要 claims、有效期、用户状态、auth_version 和接口权限。签发/续签不写设备会话表。
2. 登录时固定 auth_time；首次 exp = auth_time + 3 天。有效请求的 exp - now < 36 小时时，可签发新 token，new_exp = min(now + 3 天, auth_time + 30 天)，auth_time 和 auth_version 保持不变。仅 new_exp > exp 时续签，避免临近 30 天上限反复下发无实际延长的 token。now >= exp 或达到绝对上限时拒绝续签、要求重新认证。
3. 建议请求使用 Authorization: Bearer，自动续签响应头使用 X-Access-Token，在响应头写出前设置，含凭证的响应禁止缓存。同源前端直接读取；如启用跨源调用，显式暴露该响应头并限制允许来源。接口与头约定随契约源、生成及前端适配同步维护。
4. 普通续签不撤销旧 token；并发请求可能各自产生有效新 token，不增加服务端轮换锁或逐 token 记录。退出全部设备、解绑/换绑、禁用等改变认证版本的接口由其用例决定是否签发新凭证，通用续签不能覆盖用例结果或给已失效版本续签。
5. 前端在统一请求边界读取响应头，各应用分别保存凭证；在同一用户、同一次认证和同一认证版本内，仅接受到期时间更晚的续签凭证。退出、切换账户、重新认证或身份变更后，先前请求的迟到响应不能更新当前登录。此规则不是客户端替代服务端验签，服务端始终独立校验请求。
6. 没有独立刷新接口，也不新增仅为续签而定时请求的后台心跳；正常受保护请求触发续签。过期时进入认证流程，恢复来源页面后重新检查权限，不自动重放扣款或领奖。2.2 操作恢复沿用原认证时间；换绑/解绑重发保留原 30 天截止时间。

代码职责：2.3 实现签发、校验和响应头行为；2.4 在现有 api-client 的手写扩展边界与各应用接入凭证读取、存储和状态更新。当前 api-client 尚无认证头或续签处理。客户端具体存储方式、完整公开 API 和错误映射继续细化。

## 验收条件

- 首次 token 3 天有效；恰好剩余 36 小时不续签，不足 36 小时且未过期时下发新 token；已过期、版本失效、账户禁用时不能续签。
- 原认证第 29 天的续签最多到第 30 天；到期时间已在绝对上限时不重复下发同期限 token，重试及换绑不改变原认证时间。
- 响应丢失不使仍有效的旧 token 立即失效；前端并发乱序不倒退到期时间，退出或账户切换后的迟到响应不恢复旧登录。
- 自动续签不覆盖退出全部设备或身份变更的结果；跨源场景能按约定读取响应头；新凭证响应不被缓存。
- 无独立刷新凭证、刷新接口、设备会话表或单次登录撤销。验证证据在 [验证记录](04验证记录.md) 中维护，文档检查不等于运行验收。

## 方案确认与变更

2026-10-29 用户先取消单次登录撤销，再指定 3 天 token 与半程响应头续签。本版据此替换此前双凭证或固定 30 天单 token 的建议；用户级认证版本与 30 天重新认证上限保留。本文只补充方案，未修改代码或建立业务接口；后续实际改动记录在 [实施记录](03实施记录.md)。
