# 2.2 用户鉴权（邮箱与 Telegram） 实施记录

[阶段目录](../README.md) · [全部工作记录](../../README.md) · [工作范围清单](../../../../engineering/工程阶段与工作清单.md)

2026-10-29，分支 `feat/user-auth`，起点 `138fe30`。用户要求继续主流程，本轮按已确认规则实现内部鉴权；不提前实现产品会话或接受客户端自报用户的公开接口。

## 交付

| 内容 | 实际实现 |
| --- | --- |
| SQL 与生成 | email_challenge、auth_operation；新增 business/000002，显式登记 auth SQL。13 个纯生成文件、22 个受保护骨架 |
| 邮箱 | 6 位随机码、5 分钟、60 秒、最多 5 次错误；HMAC 保存、用途/Actor 绑定、发送后条件激活、失败状态及重发仅最新有效 |
| Telegram | init-data-golang v1.5.0；附加字段歧义/容量/时间检查、稳定指纹去重、完整可信资料传入用户用例 |
| 邮件与限流 | go-mail v0.8.1 的 TLS SMTP/context/超时，中英文模板；redis_rate v10.0.1 复用现有 Redis，不另建客户端或手写限流 Lua |
| 原子消费 | 挑战消费、用户/身份变更、成功操作记录共用 transaction.Runner。验证码错误计数作为明确拒绝提交；其他业务失败回滚；提交未知不自动重试 |
| 身份变更 | 验证会话版本、身份占用、两种身份换绑、最后身份保护；按用户→同类型 ID 顺序锁定；实际换绑/解绑递增 auth_version；保留身份行和次数归属 |
| 结果恢复 | 同请求同输入返回相同操作 ID 与原事件时间；跨输入拒绝；恢复检查当前用户状态/版本/绑定。供 2.3 衔接同一会话 |
| 共享组装 | 可选 Auth 配置在 ServiceContext 组装，未配置保持关闭；启用必须有 Redis，秘密值由环境注入 |

现有 2.1 事务拥有者入口保留，抽出参与外层 session 的创建/解析方法，不重复用户注册规则。后端 HTTP 生命周期、健康、公共错误契约、idx 格式保持原样。新增库所需的 x/crypto、x/net、x/sys、x/text 版本随 go.mod/go.sum 锁定，原有框架回归通过。

Redis 测试清理增加对 redis_rate 固定 rate: 前缀的识别，但仍要求当前 run 的完整命名空间和有限字符；不会扫描或删除其他 key。真实集成仅使用隔离库和精确登记的 Redis key，没有真实发信、读取其他项目凭据或执行业务生产迁移。

## 后续边界

当前 Result 不是登录令牌。2.3 必须验证会话来源、接入公开 .api、实现同操作会话恢复及版本撤销；绑定恢复不能延长原会话 30 天认证上限。2.4 负责登录/绑定交互。真实 SMTP 配置与送达、TG 设备内材料由独立环境验收，App 原生 TG 接入仍归 8.4。

后续调整（2026-10-29）：30 天上限已由用户取消，2.3 采用 3 天 token 的响应头滑动续签；上段的期限要求已被覆盖。Result 仍保留原操作元数据用于幂等核对，本项没有实现累计期限逻辑；当前规则见 [2.3 讨论记录](../2.3-产品会话/01讨论记录.md)。

路径：`backend/logic/auth/`、`backend/logic/user/binding.go`、`backend/model/auth/`、`backend/manifest/sql/ddl/auth/`。运行说明见 [用户鉴权基础](../../../../engineering/用户鉴权.md)。
