当前状态：讨论中。业务规则已收敛，用户表加按类型划分的身份表、各表 user_id 直接关联及外部字段平铺已按用户要求修订，唯一约束、创建查询及事务边界已同步；技术设计见实施方案，尚未实施。App 仅邮箱、Telegram；换绑条件、任务原子完成、验证码、邮箱规范化、资料、禁用、会话及阶段分工均已确认。直接登录已放弃；首奖仍在首次任务完成后入账，内部解释不面向用户。尚未实现业务。

本项范围与边界以工作范围清单中的 2.1 为准。此处记录具体问题、选择与确认依据。

## 已明确的方向

- 产品用户有独立 idx，通过邮箱或 Telegram 登录；邮箱用户可以不绑定 TG，功能所需外部身份按需绑定，不设置全局 TG 门槛。
- Mini App 提供 Telegram 静默登录：服务端验证授权，首次创建产品用户及 TG 绑定，后续登录对应用户。
- App 仅保留邮箱、Telegram 两种登录入口。已取消直接登录及钱包登录；导入、切换、断开钱包不改变产品用户或会话。
- 邮箱采用验证码认证，注册与登录合一，服务端验证成功后创建或登录对应产品用户；无需设置邮箱登录密码。验证码默认参数已确认，邮件服务在 2.2 实际接入时配置；尚未实现。
- 每个产品用户同时最多绑定一个邮箱和一个 TG，可仅有其中一种；每个邮箱或 TG 同一时刻仅归属一个产品用户。绑定未占用身份保留当前用户 idx 与记录；身份已被其他账户占用时拒绝绑定、不自动合并或转移，明确的登录/切换操作与绑定分开。
- 设备号与设备凭证不作为独立登录入口，直接登录的恢复建议不再实施。邮箱用户除操作必要限制外可使用功能，不因缺少 TG 统一限制为浏览或禁止资金、奖励。
- 当前任务需要 TG；未来可要求其他身份或不需要外部身份。缺少身份时明确引导绑定，返回原任务后重新校验。
- 对依赖外部身份的任务，次数消耗归属外部身份，换绑不重置；首次奖励和奖励账户归属产品用户，外部身份变更不迁移既有奖励或刷新产品首奖资格。
- 用户进一步说明，首奖是预期任务奖励的前置体现，不是任务奖励之外独立赠送的一份补贴；随后明确仍在首次任务完成后入账，解释仅用于内部，不主动让用户意识到。这不新增后续抵扣、欠款或追回规则。

规则归属见 [业务规则](../../../../product/02业务规则.md) 与 [任务与奖励](../../../../product/04任务与奖励.md)，界面及验收已同步设计要求，尚无运行结果。

| 6 | 账户禁用 | 账户禁用后拒绝新登录、使现有会话失效并阻止用户发起业务操作，保留账户及历史数据。后台继续核验、结算和恢复已受理的资金业务，禁用不取消既有交易或抹除资金责任。 |
| 7 | 邮箱验证码 | 验证码默认 6 位数字、有效期 5 分钟、重发间隔 60 秒，每次验证码挑战最多 5 次错误尝试；一次使用后失效，重发后仅最新验证码有效。重发不清空累计限流计数，另按邮箱和请求来源限制发送量，聚合阈值在鉴权实施时配置。 |

### Q02：直接登录与恢复建议（已放弃，仅留历史）

2026-10-28 用户明确“放弃直接登录吧，只要邮箱和tg登录”，本节整体失效，不再是待确认方案或实施要求。以下保留当时提出但未获采纳的建议，便于追溯。

当时的技术参考：[Android 标识最佳实践](https://developer.android.com/identity/user-data-ids)、[Android Keystore](https://developer.android.com/privacy-and-security/keystore)。未据此选定 App 平台、框架或凭证实现。

建议将“设备号”落为本 App 安装范围的随机标识，而非 IMEI、MAC 或其他永久硬件号；它表示这一份客户端安装，不承诺与物理设备或自然人一一对应。再配合本机安全保存、服务端可验证及撤销的登录凭证。标识负责定位，凭证负责证明有权进入账户；不因提供相同设备号就补发旧账户凭证。采用随机令牌或设备密钥的具体形式、时效、轮换及会话衔接留到 2.3 细化，不预先创建独立于会话系统的另一套协议。

| 情形 | 建议行为 |
| --- | --- |
| 首次点击「直接登录」 | 没有可恢复凭证时建立新产品用户及本机登录关联，保存凭证并进入；无需邮箱/TG，不输入密码 |
| 日常重新打开 | 有效本机凭证恢复原产品用户；升级、重启不主动换用户，网络或服务故障不退化为新建用户 |
| 本机有凭证但服务端拒绝或账户禁用 | 说明真实原因，按恢复或限制流程处理；不能自动新建用户掩盖失败 |
| 后续绑定未被占用的邮箱/TG | 在验证成功后为当前产品用户增加登录/恢复入口，保留原 idx、奖励和记录；已被占用的身份交 Q03 处理 |
| 重装、清数据、换机等导致有效凭证不可用 | 使用已绑定邮箱/TG 登录原用户；不承诺同一设备号可找回，也不假设所有系统重装都会清除或保留凭证 |
| 凭证不可用且未绑定恢复入口 | 明确无法凭设备号自动找回旧账户，用户可选择新建直接登录账户；不能静默替换旧账户或迁移其余额；旧账户数据不因本机凭证丢失而删除 |

在账户页提供绑定邮箱/TG 以便恢复的提示，不把提示变为全局使用限制。系统备份、跨设备迁移及共享设备上的退出行为需单独确定；不得把操作系统备份成功等同于已验证的账户恢复。普通退出与“从本机移除此账户”的凭证处理在 2.3 明确，不能让未绑定账户无提示丢失唯一凭证，也不能在退出后自动恢复刚退出的会话。

存储建议是使用客户端系统的安全存储能力。Android 可用 Keystore 保护密钥并加密保存令牌；iOS 可用 [Keychain](https://support.apple.com/guide/security/keychain-data-protection-secb0694df1a/web) 保存凭证，访问条件与是否允许迁移需随客户端方案验证。不在普通配置、日志或设备号字段中保存明文凭证；这不要求每次直接登录都增加生物识别弹窗。

当时待确定的核心为安装范围标识、持有凭证及恢复边界。随直接登录取消，上述问题不再推进；一般产品会话的存储与恢复仍由 2.3 按邮箱/TG 登录范围落实。
