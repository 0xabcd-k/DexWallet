## 目标与工作边界

承接 1.1–1.5，建立独立产品用户、外部身份及绑定的模型，为邮箱、Telegram 两种登录入口提供关联基础。邮箱用户可无 TG 身份；用户 idx 与钱包切换无关。已取消直接登录及钱包登录，不建立设备号注册或设备凭证恢复入口。

本项明确任务资格主体与奖励归属的边界，不提前实现任务、账本或 App 客户端。邮箱与 Telegram 鉴权归 2.2，产品会话归 2.3，前端接入归 2.4，App 客户端仍归 8.4。

## 设计与实现步骤

建议按以下职责细化，不预先承诺最终表名、字段或全部拆表：

| 职责 | 方向与约束 |
| --- | --- |
| 产品用户 | 稳定 idx、状态与产品资料；通过邮箱或 TG 登录，二者均不替代产品 idx；首奖资格及奖励账户归此主体 |
| 外部身份与绑定 | 每用户最多一个邮箱、一个 TG；同一身份同一时刻唯一归属；平台稳定标识、当前归属及必要历史分清，任务资格不随重建绑定重置 |
| 登录身份与凭证 | 仅支持邮箱验证码和 Telegram 入口；邮箱注册登录合一，不要求设置密码；验证码及身份变更规则已确认，凭证存储和会话实现分别在 2.2–2.3 细化 |
| 任务协作边界 | 所需身份由任务声明；身份资格消耗与产品奖励账户分离；只有原子完成记录，固定完成时的外部身份与受益产品用户，提交复查绑定，无进行中业务状态 |

依据已确认业务规则补齐具体设计，再补 DDL、增量迁移、唯一约束、创建/查询用例及必要 API 源定义。沿用现有生成链，不手改生成文件。并发创建、绑定冲突、状态禁用和数据可见范围须有明确失败语义，不能把“查不到”与依赖失败混为一谈。

邮箱或 TG 登录失败时按实际原因处理，不回退为直接登录，也不自动创建设备账户。绑定成功回原业务，重新检查权限和资格，不能自动重发扣款或领奖。Q02 已放弃，原设备登录与恢复建议只保留在讨论记录的历史部分，不纳入本方案。

邮箱验证码方式已确认：先发送验证码，再由服务端验证成功后查找邮箱对应产品用户；已有用户登录原账户，首次使用创建用户及邮箱关联，然后签发产品会话。发送成功不表示邮箱已验证，不提前建立已验证账户；邮箱身份唯一性和并发创建需在模型与事务中保证。验证码和邮箱规范化采用 [业务规则](../../../../product/02业务规则.md) 的已确认参数，邮件服务在 2.2 接入时配置。

绑定数量与冲突处理已确认：允许单独邮箱、单独 TG 或两者各一；数据库约束与事务须同时保证每用户的同类数量上限和身份唯一归属，不能只靠先查后写。目标身份已属于其他用户时返回明确占用结果，双方绑定与当前会话保持，不自动合并、转移或改为登录该账户。未占用身份验证成功后绑定当前用户，不另建产品用户；同类已有不同身份时不得以新增覆盖。换绑前必须已绑定至少两个外部身份；当前即同时有邮箱和 TG，只有一种时先绑定另一种。有效产品登录态即可发起解绑或换绑，不要求验证旧外部身份；目标新身份仍须验证且未被其他账户占用。解绑后至少保留一种登录方式。换绑以原子替换完成，失败保留原绑定；并发操作在提交时重新检查身份数量及唯一归属，不能通过同时解绑或换绑绕过限制。

已解绑身份再次登录时，按当前绑定查找账户；若未被绑定则验证后创建新产品用户，不根据历史绑定恢复旧账户。需要回到旧账户时，通过保留的登录方式进入再绑定；历史奖励不迁移，外部身份的任务消耗不重置。

产品资料、账户禁用与会话遵循业务规则及本轮十项确认，模型需要支持当前绑定版本、资料独立及禁用状态，具体会话撤销在 2.3 实现。

## 验收条件

设计要求见 [身份与任务归属补充验收](../../../../testing/验收与场景追踪.md#身份与任务归属补充验收)。实施前补齐未决策略对应的验证用例，重点覆盖邮箱用户无 TG、重复创建、绑定冲突、未验证身份冒认、身份换绑不重置任务资格、产品首奖唯一性及奖励归属不迁移。

当前仅进行文档检查，不执行业务测试，也不把场景清单视为验收通过。

绑定验收覆盖两类身份各一、单类登录、重复绑定和并发竞争：同一身份不能被两个用户同时绑定，同一用户不能并发增加两个同类身份；占用失败不修改任何账户归属、数据或会话。新增绑定保留原 idx；切换到已有身份所属账户必须是单独明确的登录动作。

邮箱验收覆盖首次验证成功创建、后续返回同一用户、重复/并发不重复建用户、错误/过期/已消费验证码不签发会话，以及发送失败不伪装成功。按已确认参数覆盖时间、重发、限流、并发换绑及恢复边界；不保留设备登录验收。一般产品会话失效、退出及恢复由 2.3 验证。

## 方案确认与变更

2026-10-28 早期讨论：曾记录三种 App 登录入口、直接登录命名及默认开放方案，后续已取消直接登录。任务次数随外部身份、奖励随产品用户、首奖仍在首次任务完成后入账且前置解释仅供内部的规则继续有效。具体依据见讨论记录，没有新增业务实现。

同日后续决定：用户明确“放弃直接登录吧，只要邮箱和tg登录”。Q02 设备标识、凭证与恢复建议整体放弃，当前方案与验收只保留邮箱/TG 登录方向；继续讨论 Q03，不实施登录接口或 App 存储代码。

同日确认邮箱认证：用户“邮箱认证就按你说的验证码”，采纳验证码方式及注册登录合一方向。同步规则、界面与验收要求；验证码参数和绑定规则仍待细化，本轮未实现邮件发送或鉴权接口。

同日确认绑定规则：用户采纳此前关于绑定数量及身份占用处理的建议，落实每用户邮箱/TG 各一个上限、身份唯一归属、占用拒绝且不自动合并/转移。同步设计与拟验收，不将解绑/换绑或任务进行中的策略扩展为已确认，未新增代码或数据库约束。

同日十项统一回复：业务规则按讨论记录全部收敛，修订换绑条件及认证、删除任务在途方案，确认验证码/邮箱规范化/资料/禁用/会话与阶段范围；以上早期未决记录仅供追溯。未新增业务代码或迁移。
