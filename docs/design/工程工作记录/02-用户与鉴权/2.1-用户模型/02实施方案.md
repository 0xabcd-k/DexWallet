## 三张核心表

三个对象分别承担产品账户、外部身份事实、当前关联职责。无需绑定历史就能找回外部身份的原任务消耗；以后身份变更审计由 2.2 保存，但不能将历史绑定用于恢复登录。

```mermaid
erDiagram
    product_user ||--o{ user_identity_binding : "当前绑定"
    external_identity ||--o| user_identity_binding : "当前归属"
```

数据库内部关联使用 `BIGINT` 主键 `id`。产品对外标识仍叫 `idx`，本版使用 UUID v4 的规范小写字符串，数据库 `CHAR(36)`、唯一索引；复用 module 已锁定的 UUID 库，在实际使用时转为直接依赖并处理生成失败。`idx` 不依赖邮箱、TG 或钱包，不能因换绑重新生成。内部主键不成为公开接口的查人授权依据，也不强制将所有内部数字转换成字符串。

### product_user：产品用户

| 字段 | SQL 类型与约束 | 职责 |
| --- | --- | --- |
| id | BIGINT，主键、自增 | 内部用户关联 |
| idx | CHAR(36)，ASCII 精确比较、NOT NULL、唯一 | 对外产品身份 |
| status | VARCHAR(16)，ASCII 精确比较、NOT NULL | 具名状态 active / disabled，创建为 active |
| nickname | VARCHAR(128)，NOT NULL，默认空字符串 | 独立产品昵称；TG 首次注册可初始化，邮箱使用默认资料 |
| avatar_url | VARCHAR(2048)，NOT NULL，默认空字符串 | 产品头像；空值由界面使用默认头像，不在后端抓取任意 URL |
| auth_version | BIGINT，NOT NULL，初始 1 | 全账户会话撤销版本；禁用、解绑/换绑成功和退出全部设备时由相应用例递增 |
| created_at / updated_at | DATETIME(6)，NOT NULL | UTC 时间；创建默认当前时间，修改同步更新时间 |

不存 TG ID、邮箱、钱包私钥、余额、积分或首奖标志。状态禁用保留身份与数据，不以删除绑定代替禁用。模型查询可返回禁用记录用于诊断，登录解析必须明确拒绝；后台资金恢复不能套用用户发起操作的准入检查。

昵称和头像只在创建时接受外部资料初始化，已有用户登录不覆盖；后续产品资料编辑由 2.4 落实。默认文案由客户端国际化资源承接，数据库可用空昵称表示尚未编辑，不能将固定中文文案写成所有用户的资料。

### external_identity：稳定外部身份

| 字段 | SQL 类型与约束 | 职责 |
| --- | --- | --- |
| id | BIGINT，主键、自增 | 任务次数及资格消耗后续引用的稳定主体 |
| identity_type | VARCHAR(16)，ASCII 精确比较、NOT NULL | 具名类型 email / telegram；未来按新类型扩展，非任意输入 |
| subject | VARBINARY(512)，NOT NULL | 规范化后的平台稳定标识，写入后不变 |
| display_value | VARCHAR(512)，NOT NULL | 已验证身份的展示值；邮箱保留原输入，不能用于唯一性判断 |
| created_at | DATETIME(6)，NOT NULL | 首次建立身份事实的 UTC 时间 |

唯一键 `uk_identity_subject(identity_type, subject)` 保证同一平台身份只建一份；`uk_identity_id_type(id, identity_type)` 为绑定表的复合外键提供明确唯一目标。字段长度是本版存储上限，输入超长返回错误，不能截断后匹配其他身份；邮箱具体格式支持范围在 2.2 明确。

邮箱 subject 按已确认规则去首尾空白、仅域名小写、本地部分保留大小写和点号/加号后缀；TG subject 使用经过服务端验证的稳定用户 ID 的规范十进制表示，不能使用 username、昵称或头像。`VARBINARY` 按字节比较，避免默认文本排序规则将不同邮箱本地部分合并，参见 [MySQL BINARY / VARBINARY](https://dev.mysql.com/doc/refman/8.4/en/binary-varbinary.html)。生成字段映射为 Go string 的兼容性已做隔离探测，真实数据库往返仍需实施验收。

解绑只移除当前绑定，绝不删除或重建这条身份记录。身份没有当前归属时，后续验证登录可创建新产品用户并关联原身份 id；因此原任务次数保留，原产品奖励也不会迁移。

### user_identity_binding：当前绑定

| 字段 | SQL 类型与约束 | 职责 |
| --- | --- | --- |
| id | BIGINT，主键、自增 | 当前这一代绑定的标识；新绑定总是新 id，不复用已删除行 |
| user_id | BIGINT，NOT NULL | 当前产品用户 |
| identity_id | BIGINT，NOT NULL | 稳定外部身份 |
| identity_type | VARCHAR(16)，与身份表同类型/排序规则、NOT NULL | 用于每用户同类型数量约束 |
| bound_at | DATETIME(6)，NOT NULL | 本次绑定的 UTC 时间 |

| 约束 | 可观察保证 |
| --- | --- |
| `uk_binding_user_type(user_id, identity_type)` | 每用户同类型最多一个，不能并发新增两个邮箱或两个 TG |
| `uk_binding_identity(identity_id)` | 同一身份同一时刻只能绑定一个产品用户 |
| `fk_binding_user(user_id) → product_user(id)` | 绑定不能指向不存在的产品用户 |
| `fk_binding_identity(identity_id, identity_type) → external_identity(id, identity_type)` | 不能把 TG 身份以 email 类型插入，或指向不存在的身份 |

复合外键列显式建索引；外键采用限制删除/更新，不级联删除用户、身份或奖励。被引用列使用显式唯一索引，参见 [MySQL 外键约束](https://dev.mysql.com/doc/refman/8.4/en/create-table-foreign-keys.html)。

换绑在一笔事务内删除旧绑定、插入新绑定；解绑删除当前绑定。对同一身份的重复新增请求若已绑定当前用户，可返回现有关系，不能无故换代。真正解绑后重新绑定，即使回到同一 TG，也必须产生新的 binding id。任务验证保存 `(user_id, identity_id, binding_id)`，提交时复查整组，不能只比较 TG ID 相同就认可旧验证。

未来任务完成记录长期引用用户及稳定外部身份；保存的 binding id 仅作当时绑定的快照，不对会被删除的当前绑定行建立外键，避免历史完成记录阻止合法解绑。

每用户至少一种登录方式、换绑前至少两种属于跨行条件，由锁定用户后的用例检查，不能声称单靠唯一索引就满足。当前不实现任何按绑定历史找回旧账户的查询入口。

## 创建与查询用例

本项用例放在 `backend/logic/user/`，持久化放在 `backend/model/user/`；以下为拟建路径，不是现有实现。接入方只传业务所需依赖，不传完整 ServiceContext，也不提供可绕过规则的公开 CRUD。

| 内部能力 | 输入与处理 | 输出与失败语义 |
| --- | --- | --- |
| ResolveOrCreateVerifiedIdentity | 可信鉴权调用方给出类型、规范化 subject、展示值及可选初始资料；按当前绑定查找，必要时原子创建用户、身份及绑定 | 原有或新建用户、当前绑定标识；禁用明确拒绝；不签发会话 |
| FindUserByIdx | 供授权过的接入/业务使用产品 idx 查询 | 用户基础资料及状态；不存在与依赖失败分别返回 |
| FindCurrentIdentities | 按明确的产品用户查询当前绑定及身份摘要 | 空缺身份为可观察缺项；不把缺 TG 当成未登录，不返回任何凭据 |
| CheckCurrentBindingInSession | 使用调用方传入的同一 sqlx.Session 检查用户、身份与 binding id | 一致时继续，换代/解绑/禁用分别拒绝；不自行提交或重开事务 |

VerifiedIdentity 仅表示内部接口前置条件，不是“调用方填了 verified=true 就可信”。真实验证、用途绑定、验证码单次消费以及可用会话由 2.2–2.3 实现后才能开放；2.1 的测试仅在内部受控调用构造已验证结果。

规范化逻辑集中一处，创建、查询及未来绑定共用。拒绝未知身份类型、空标识及超过存储上限的值。唯一键冲突按具体约束解释；身份已经归属其他用户不能转换成自动转移或登录切换。领域错误使用具名定义，正式对外错误码在 2.2/2.4 的 `.api` 源加入并生成，不手改 `codes_gen.go`。

## 事务、并发及恢复

### 首次创建与重复登录

1. 根据 `(identity_type, subject)` 读取当前归属作为定位线索；该普通读不代表锁定或最终授权。
2. 有归属时，在事务内先锁定候选用户，再锁定外部身份并重新读取当前绑定。若已换到其他用户或已解绑，结束当前事务后重新解析，不在持锁事务内转去锁另一个用户。确认仍归属后检查用户状态并返回原用户；不覆盖其资料。
3. 无归属时，在事务中建立候选产品用户，查找或创建稳定外部身份并锁定，再确认仍无绑定，最后插入绑定，一起提交。若并发竞争发现已绑定，回滚本次候选用户，再按已有归属处理；不能留下无身份的注册残留。
4. 同身份首次创建冲突、已知回滚后的归属变化，可由该用例在明确的有限次数内重新查询；不向公共事务层添加自动重试。已经提交但响应丢失时，后续有效认证按当前绑定返回原用户，不增加重复用户。

创建时自增号产生间隙不影响业务；不得为填补间隙复用已删除绑定 id。提交阶段失败遵循现有 `transaction.Failure.Unknown()`，不能宣称一定回滚，也不能未经重新核验就再建用户。登录查找遵循当前归属，不承诺将已被解绑的身份恢复到先前的创建结果。

### 统一锁顺序与身份变更交接

已知用户的操作先锁产品用户，再按 identity id 升序锁本次涉及的身份，最后读取/变更绑定；同一用户的所有绑定写入都遵守该入口。查找登录遵循前述重新定位流程，不能持有身份锁后再追着最新归属反向锁用户。需要锁定读取的关键查询使用同一事务的 `FOR UPDATE`，不能以事务外缓存值替代，参见 [MySQL 锁定读取](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)。

2.2 换绑提交时检查有效用户会话、当前绑定 id、至少两个已绑定身份、目标验证结果及目标未占用；不要求旧身份重新验证。删除旧关联、插入新关联、递增 auth_version 及必要操作记录原子提交，失败全部保留原状。解绑按同一用户锁检查操作后至少还剩一种登录方式。身份占用检查不得持锁进入其他用户的变更流程。

2.3 使用提交后的新 auth_version 重发当前会话，其他会话必须因版本不符失效；普通退出只撤销当前会话。新增第二种身份不自动等同于换绑。凭证生成/响应失败时，已提交的绑定不能假装未变更，用户可用保留身份重新登录；具体幂等请求及结果查询由 2.2–2.3 补齐。

阶段 4 在事务外验证外部事实，事务内按兼容顺序锁用户和身份、复查 binding id，再提交完成记录、资格消耗与全部奖励。邀请涉及多个用户时需在阶段 4 确定完整用户集合并按固定顺序锁定，不能在任意已持锁节点追加反向取锁。任务仍无进行中状态，也不因页面停留锁住换绑；真实资金与后台任务继续保留各自必要状态。

### 复用现有事务设施

使用 [transaction.Runner](../../../../../backend/transaction/transaction.go) 的显式 TransactCtx，以及 [现有 WithSession 示例](../../../../../backend/model/example/contract_sample_model.go) 的扩展方式。协作查询和写入全部绑定同一个 session，不混用默认连接；不嵌套事务，不在事务中发邮件、调用 TG、写 Redis 或发送 MQ。

三张表当前事实以 MySQL 为准；2.1 不引入身份查询缓存。未来依赖 Redis 的会话不能在 Redis 故障时绕过鉴权。禁用后的后台资金恢复由原资金用例执行，不能删除既有单据或将用户恢复为可操作状态。

## SQL、生成与实施顺序

隔离探测发现 goctl v1.10.2 拒绝 CREATE TABLE 内的外键声明，移出声明后可生成复合唯一索引及 VARBINARY 字段的 model；探测没有执行数据库 DDL。具体记录见 [验证记录](04验证记录.md#方案阶段生成兼容性探测)。采用显式源清单，不改生成器内部解析器，也不丢弃外键约束。

| 拟新增或扩展位置 | 具体内容 |
| --- | --- |
| `backend/manifest/sql/ddl/user/tables.sql` | 三张表的 CREATE TABLE、主键、唯一索引和普通索引；作为 model 生成输入 |
| `backend/manifest/sql/ddl/user/constraints.sql` | ALTER TABLE 添加外键；完整 DDL 重放按 tables → constraints 顺序执行；不传入 goctl |
| `backend/manifest/sql/diff/business/000001_create_user_model.up.sql` | 独立正式业务迁移序列首项，包含同样的建表和外键定义；不修改 examples 迁移 |
| `scripts/generate.py` 与生成文件清单 | 登记 user model 输入和产物、纳入检查与手写保护；不递归扫描所有 SQL；原示例和 platform API 继续检查 |
| `backend/model/user/` | 生成无缓存基础 model；手写 WithSession、锁定查询、当前绑定聚合及具名枚举 |
| `backend/logic/user/` | 创建/查询用例、规范化、输入检查、状态和归属错误；不注册 HTTP 登录入口 |
| `backend/tools/migrate/`、测试隔离入口 | 增加明确 business 源选择；保持显式目标、凭据和本地测试边界，不自动运行迁移或扩大生产权限 |
| `backend/tests/integration/` | 新建隔离库重放完整 DDL 与 business 迁移，对比结构，并验证约束、并发和回滚 |

先实现源定义及生成兼容，再实现事务用例与测试。正式业务源名称不代表工具获准连接生产库；沿用现有 local 环境、允许地址、受限测试账号和本轮资源归属保护。运行正式环境迁移的配置与发布入口仍归 8.2。

初次建库执行三表及外键；`up` 重复执行保持无变更。失败后保留 dirty/version 和实际诊断，不自动 down/force；MySQL DDL 不能按业务 DML 的整体回滚承诺处理。新库完整 DDL 与迁移对比必须包含外键，不能只比较列名。后续阶段追加新编号迁移，不回改已执行文件。

## 验收条件及证据范围

业务场景沿用 [身份与任务归属补充验收](../../../../testing/验收与场景追踪.md#身份与任务归属补充验收)，本项优先证明模型不变量。

| 检查 | 通过标准 | 验证方式 |
| --- | --- | --- |
| 源与生成 | 反复生成无差异，手写 WithSession 不被覆盖，外键只由完整 DDL/迁移执行 | 既有生成检查加 user 源覆盖 |
| 创建与查找 | 邮箱/TG 分别可首次创建，后续同身份回到同 idx；不修改已有资料，不初始化首奖/余额 | 单元用例；真实 MySQL 持久化验证 |
| 并发首次注册 | 同身份多个请求最终只有一个身份、一条绑定、一个提交成功的产品用户，失败候选用户全部回滚 | 独立 MySQL 并发用例 |
| 约束 | 同身份跨用户、同用户同类型重复、无效用户引用和类型错配均被数据库拒绝 | 真实 MySQL 直接写入反例 |
| 精确身份比较 | 域名大小写归一，本地部分大小写保留；点号/加号不合并；未知类型/超长输入拒绝 | 单元测试及真实数据库唯一索引往返 |
| 事务失败 | 用户、身份与绑定任一写入失败不留下部分注册；提交应答未知保持未知语义 | 真实事务回滚；提交失败在不可靠边界注入 |
| 解绑后建档 | 模拟未来合法解绑后，原外部身份 id 保留；重新登录新建用户，不能恢复原用户 | 内部持久化集成场景，不作为已实现解绑接口 |
| 绑定代际 | 删除后重绑生成新 binding id，旧快照校验失败；同一当前绑定重试不制造换代 | 模型同 session 校验用例 |
| 禁用与缺项 | 禁用用户登录解析被拒绝且不另建用户；无 TG 是缺少身份，不是用户不存在 | 用例及查询测试 |
