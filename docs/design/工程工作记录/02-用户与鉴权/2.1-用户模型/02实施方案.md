方案状态：讨论草案，尚未形成完整实施方案。已明确方向与待讨论技术建议以 [讨论记录](01讨论记录.md) 为准；不得将本页建议视为已实现或整体已确认。

## 目标与工作边界

承接 1.1–1.5，建立独立产品用户、外部身份及绑定的模型，为邮箱、Telegram、直接登录提供关联基础。产品用户可无外部身份；用户 idx 与钱包切换无关。

本项明确任务资格主体与奖励归属的边界，不提前实现任务、账本或 App 客户端。设备凭证、邮箱鉴权的具体实施工作项尚待排定；Telegram 验证、产品会话、前端接入继续与 2.2–2.4 衔接。

## 设计与实现步骤

建议按以下职责细化，不预先承诺最终表名、字段或全部拆表：

| 职责 | 方向与约束 |
| --- | --- |
| 产品用户 | 稳定 idx、状态与产品资料；外部身份非必填；首奖资格及奖励账户归此主体 |
| 外部身份与绑定 | 平台类型、平台稳定主体标识、当前归属及必要历史；任务资格不能因解绑删除或重建映射而重置 |
| 设备关联与登录凭证 | 支持直接登录；设备号用于识别，建议另有持有证明；标识范围、凭证存储、恢复及冲突规则待确定 |
| 任务协作边界 | 所需身份由任务声明；身份资格消耗与产品奖励账户分离；建议任务参与保存外部身份和受益产品用户快照，固定时点待讨论 |

先确定讨论记录中的未决项，再补 DDL、增量迁移、唯一约束、创建/查询用例及必要 API 源定义。沿用现有生成链，不手改生成文件。并发创建、绑定冲突、状态禁用和数据可见范围须有明确失败语义，不能把“查不到”与依赖失败混为一谈。

直接登录的命名与功能范围已明确，凭证实现仍是技术建议；不能仅靠客户端设备号直接获取已有用户会话。绑定成功回原业务，重新检查权限和资格，不能自动重发扣款或领奖。

## 验收条件

设计要求见 [身份与任务归属补充验收](../../../../testing/验收与场景追踪.md#身份与任务归属补充验收)。实施前补齐未决策略对应的验证用例，重点覆盖无外部身份用户、重复创建、绑定冲突、设备冒认、身份换绑不重置任务资格、产品首奖唯一性及奖励归属不迁移。

当前仅进行文档检查，不执行业务测试，也不把场景清单视为验收通过。

## 方案确认与变更

2026-10-28：记录三种 App 登录入口、直接登录命名及默认开放、任务次数随外部身份和奖励随产品用户的方向。追加首奖为任务奖励前置体现的内部解释；用户确认仍在首次任务完成后入账，不主动向用户介绍前置机制。具体确认依据、问题与后续动作统一维护在讨论记录；本轮没有新增业务实现。
