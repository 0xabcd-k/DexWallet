## 两张核心表

产品用户与外部身份为一对多关系，只保留 product_user 和 external_identity。external_identity.user_id 直接指向用户；NULL 表示当前未绑定。不建立单独绑定表，身份及当前归属由同一行维护。以后身份变更审计由 2.2 保存，但不能将历史归属用于恢复登录。

```mermaid
erDiagram
    product_user |o--o{ external_identity : "user_id 当前归属"
```

数据库内部关联使用 `BIGINT` 主键 `id`。产品对外标识仍叫 `idx`，本版使用 UUID v4 的规范小写字符串，数据库 `CHAR(36)`、唯一索引；复用 module 已锁定的 UUID 库，在实际使用时转为直接依赖并处理生成失败。`idx` 不依赖邮箱、TG 或钱包，不能因换绑重新生成。内部主键不成为公开接口的查人授权依据，也不强制将所有内部数字转换成字符串。

### product_user：产品用户

| 字段 | SQL 类型与约束 | 职责 |
| --- | --- | --- |
| id | BIGINT，主键、自增 | 内部用户关联 |
| idx | CHAR(36)，ASCII 精确比较、NOT NULL、唯一 | 对外产品身份 |
| status | VARCHAR(16)，ASCII 精确比较、NOT NULL | 具名状态 active / disabled，创建为 active |
| nickname | VARCHAR(128)，NOT NULL，默认空字符串 | 独立产品昵称；TG 首次注册可初始化，邮箱使用默认资料 |
| avatar_url | VARCHAR(2048)，NOT NULL，默认空字符串 | 产品头像；空值由界面使用默认头像，不在后端抓取任意 URL |
| auth_version | BIGINT，NOT NULL，初始 1 | 全账户会话撤销版本；禁用、解绑/换绑成功和退出全部设备时由相应用例递增 |
| created_at / updated_at | DATETIME(6)，NOT NULL | UTC 时间；创建默认当前时间，修改同步更新时间 |

不存 TG ID、邮箱、钱包私钥、余额、积分或首奖标志。状态禁用保留身份与数据，不以删除绑定代替禁用。模型查询可返回禁用记录用于诊断，登录解析必须明确拒绝；后台资金恢复不能套用用户发起操作的准入检查。

昵称和头像只在创建时接受外部资料初始化，已有用户登录不覆盖；后续产品资料编辑由 2.4 落实。默认文案由客户端国际化资源承接，数据库可用空昵称表示尚未编辑，不能将固定中文文案写成所有用户的资料。

### external_identity：外部身份及当前归属

| 字段 | SQL 类型与约束 | 职责 |
| --- | --- | --- |
| id | BIGINT，主键、自增 | 任务次数及资格消耗后续引用的稳定主体 |
| user_id | BIGINT，NULL，默认 NULL | 当前所属产品用户；解绑清空，不用 0 或虚构用户表示未绑定 |
| identity_type | VARCHAR(16)，ASCII 精确比较、NOT NULL | 具名类型 email / telegram；未来按新类型扩展，非任意输入 |
| subject | VARBINARY(512)，NOT NULL | 规范化后的平台稳定标识，写入后不变 |
| display_value | VARCHAR(512)，NOT NULL | 已验证身份的展示值；邮箱保留原输入，不能用于唯一性判断 |
| binding_version | BIGINT，NOT NULL，默认 0 | 归属版本；每次实际绑定或解绑递增，重新绑定同一用户也不回退 |
| bound_at | DATETIME(6)，NULL，默认 NULL | 当前这次绑定的 UTC 时间；解绑与 user_id 一起清空 |
| created_at / updated_at | DATETIME(6)，NOT NULL | 身份首次建立及最后更新的 UTC 时间 |

| 约束 | 可观察保证 |
| --- | --- |
| `uk_identity_subject(identity_type, subject)` | 同一平台身份只有一条记录；该行只有一个 user_id，不会同时属于两个用户 |
| `uk_identity_user_type(user_id, identity_type)` | 对已绑定用户，每类型最多一个；多个未绑定身份可以同时保留 |
| `fk_identity_user(user_id) → product_user(id)` | 非空归属必须指向真实用户；限制删除/更新，不级联删除外部身份 |

MySQL 唯一索引允许可空列存在多个 NULL，因此 `(user_id, identity_type)` 可以同时满足“同用户同类型唯一”和“多个同类型未绑定身份保留”，参见 [MySQL 唯一索引](https://dev.mysql.com/doc/refman/8.4/en/create-index.html#unique-indexes)。以 user_id 开头的复合索引也用于查询当前用户的全部身份。原绑定表的索引及身份类型复合外键随之移除，类型只在身份行维护。

字段长度是本版存储上限，输入超长返回错误，不能截断后匹配其他身份；邮箱具体格式支持范围在 2.2 明确。邮箱 subject 按已确认规则去首尾空白、仅域名小写、本地部分保留大小写和点号/加号后缀；TG subject 使用经过服务端验证的稳定用户 ID 的规范十进制表示，不能使用 username、昵称或头像。`VARBINARY` 按字节比较，避免默认文本排序规则将不同邮箱本地部分合并，参见 [MySQL BINARY / VARBINARY](https://dev.mysql.com/doc/refman/8.4/en/binary-varbinary.html)。既有探测验证了 subject 的 Go string 生成映射；新增可空字段及实际数据库往返在实施时验证。

归属变更仅更新身份行，不删除或重建外部身份：

- 首次绑定：在锁定并确认未占用后设置 user_id、bound_at，binding_version 递增；新身份首次绑定后的版本为 1。
- 解绑：同一事务内将 user_id、bound_at 设为 NULL，并递增 binding_version；身份 id、类型、subject 及任务次数保持。
- 换绑：在同一事务内先清空旧身份的归属，再给已验证且未占用的新身份设置归属，分别递增两行版本；任一步失败整体回滚。既有“换绑前至少两个身份”规则仍有效。
- 同一当前身份的重复绑定或正常登录：返回原归属，不无故增加版本。真正解绑后再绑定同一用户时，版本仍继续增长，不能复用旧版本。

任务验证保存 `(user_id, identity_id, binding_version)`，提交时复查归属和版本；即使身份解绑后又回到同一用户，也不能使用变更前的验证结果。完成记录长期引用稳定的用户及身份 id，保存当时的版本快照，不要求历史版本等于身份行的最新版本。

一个用户至少保留一种登录方式、换绑前至少两种属于跨行条件，由锁定用户后的用例检查。目标身份已归属其他用户时明确拒绝，不能用 UPDATE 覆盖归属；唯一索引不能代替这项用例校验。

user_id 为 NULL 的身份后续验证登录时，可新建产品用户并关联这条原身份记录；不根据历史恢复旧账户。原任务次数随身份 id 保留，原奖励随原产品用户保留。当前“每用户最多一个邮箱和一个 TG”的已确认数量规则继续适用，一对多不表示开放同类型多个身份。

## 创建与查询用例

本项用例放在 `backend/logic/user/`，持久化放在 `backend/model/user/`；以下为拟建路径，不是现有实现。接入方只传业务所需依赖，不传完整 ServiceContext，也不提供可绕过规则的公开 CRUD。

| 内部能力 | 输入与处理 | 输出与失败语义 |
| --- | --- | --- |
| ResolveOrCreateVerifiedIdentity | 可信鉴权调用方给出类型、规范化 subject、展示值及可选初始资料；按当前绑定查找，必要时原子创建用户、身份并设置归属 | 原有或新建用户、身份 id 及 binding_version；禁用明确拒绝；不签发会话 |
| FindUserByIdx | 供授权过的接入/业务使用产品 idx 查询 | 用户基础资料及状态；不存在与依赖失败分别返回 |
| FindCurrentIdentities | 按 external_identity.user_id 查询当前身份摘要 | 空缺身份为可观察缺项；不把缺 TG 当成未登录，不返回任何凭据 |
| CheckCurrentBindingInSession | 使用调用方传入的同一 sqlx.Session 检查用户、身份归属与 binding_version | 一致时继续，换代/解绑/禁用分别拒绝；不自行提交或重开事务 |

VerifiedIdentity 仅表示内部接口前置条件，不是“调用方填了 verified=true 就可信”。真实验证、用途绑定、验证码单次消费以及可用会话由 2.2–2.3 实现后才能开放；2.1 的测试仅在内部受控调用构造已验证结果。

规范化逻辑集中一处，创建、查询及未来绑定共用。拒绝未知身份类型、空标识及超过存储上限的值。唯一键冲突按具体约束解释；身份已经归属其他用户不能转换成自动转移或登录切换。领域错误使用具名定义，正式对外错误码在 2.2/2.4 的 `.api` 源加入并生成，不手改 `codes_gen.go`。

## 事务、并发及恢复

### 首次创建与重复登录

1. 根据 `(identity_type, subject)` 读取当前归属作为定位线索；该普通读不代表锁定或最终授权。
2. 有归属时，在事务内先锁定候选用户，再锁定外部身份并重新读取 user_id 和 binding_version。若已换到其他用户或已解绑，结束当前事务后重新解析，不在持锁事务内转去锁另一个用户。确认仍归属后检查用户状态并返回原用户；不覆盖其资料。
3. 无归属时，在事务中建立候选产品用户，查找或创建稳定外部身份并锁定，再确认 user_id 仍为 NULL，最后写入当前 user_id、绑定时间并递增版本，一起提交。若并发竞争发现已绑定，回滚本次候选用户，再按已有归属处理；不能留下无身份的注册残留。
4. 同身份首次创建冲突、已知回滚后的归属变化，可由该用例在明确的有限次数内重新查询；不向公共事务层添加自动重试。已经提交但响应丢失时，后续有效认证按当前绑定返回原用户，不增加重复用户。

创建时自增号产生间隙不影响业务；外部身份主键与已使用的归属版本不得重置或复用。提交阶段失败遵循现有 `transaction.Failure.Unknown()`，不能宣称一定回滚，也不能未经重新核验就再建用户。登录查找遵循当前归属，不承诺将已被解绑的身份恢复到先前的创建结果。

### 统一锁顺序与身份变更交接

已知用户的操作先锁产品用户，再按 identity id 升序锁本次涉及的身份，最后检查/更新 user_id、bound_at 与 binding_version；同一用户的所有绑定写入都遵守该入口。查找登录遵循前述重新定位流程，不能持有身份锁后再追着最新归属反向锁用户。需要锁定读取的关键查询使用同一事务的 `FOR UPDATE`，不能以事务外缓存值替代，参见 [MySQL 锁定读取](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)。

2.2 换绑提交时检查有效用户会话、当前身份归属及 binding_version、至少两个已绑定身份、目标验证结果及目标未占用；不要求旧身份重新验证。清空旧身份 user_id、设置新身份 user_id、分别递增 binding_version、递增用户 auth_version 及必要操作记录原子提交，失败全部保留原状。解绑按同一用户锁检查操作后至少还剩一种登录方式。身份占用检查不得持锁进入其他用户的变更流程。

2.3 使用提交后的新 auth_version 重发当前会话，其他会话必须因版本不符失效；普通退出只撤销当前会话。新增第二种身份不自动等同于换绑。凭证生成/响应失败时，已提交的绑定不能假装未变更，用户可用保留身份重新登录；具体幂等请求及结果查询由 2.2–2.3 补齐。

阶段 4 在事务外验证外部事实，事务内按兼容顺序锁用户和身份、复查 user_id 和 binding_version，再提交完成记录、资格消耗与全部奖励。邀请涉及多个用户时需在阶段 4 确定完整用户集合并按固定顺序锁定，不能在任意已持锁节点追加反向取锁。任务仍无进行中状态，也不因页面停留锁住换绑；真实资金与后台任务继续保留各自必要状态。

### 复用现有事务设施

使用 [transaction.Runner](../../../../../backend/transaction/transaction.go) 的显式 TransactCtx，以及 [现有 WithSession 示例](../../../../../backend/model/example/contract_sample_model.go) 的扩展方式。协作查询和写入全部绑定同一个 session，不混用默认连接；不嵌套事务，不在事务中发邮件、调用 TG、写 Redis 或发送 MQ。

两张表当前事实以 MySQL 为准；2.1 不引入身份查询缓存。未来依赖 Redis 的会话不能在 Redis 故障时绕过鉴权。禁用后的后台资金恢复由原资金用例执行，不能删除既有单据或将用户恢复为可操作状态。

## SQL、生成与实施顺序

此前三表方案的隔离探测发现 goctl v1.10.2 拒绝 CREATE TABLE 内的外键声明，移出声明后可生成复合唯一索引及 VARBINARY 字段的 model；探测没有执行数据库 DDL，也未验证本次两表方案的完整字段与约束。具体记录见 [验证记录](04验证记录.md#方案阶段生成兼容性探测)。采用显式源清单，不改生成器内部解析器，也不丢弃外键约束。

| 拟新增或扩展位置 | 具体内容 |
| --- | --- |
| `backend/manifest/sql/ddl/user/tables.sql` | 两张表的 CREATE TABLE、主键、唯一索引和普通索引；作为 model 生成输入 |
| `backend/manifest/sql/ddl/user/constraints.sql` | ALTER TABLE 添加外键；完整 DDL 重放按 tables → constraints 顺序执行；不传入 goctl |
| `backend/manifest/sql/diff/business/000001_create_user_model.up.sql` | 独立正式业务迁移序列首项，包含同样的建表和外键定义；不修改 examples 迁移 |
| `scripts/generate.py` 与生成文件清单 | 登记 user model 输入和产物、纳入检查与手写保护；不递归扫描所有 SQL；原示例和 platform API 继续检查 |
| `backend/model/user/` | 生成无缓存基础 model；手写 WithSession、锁定查询、按 user_id 查询身份及具名枚举 |
| `backend/logic/user/` | 创建/查询用例、规范化、输入检查、状态和归属错误；不注册 HTTP 登录入口 |
| `backend/tools/migrate/`、测试隔离入口 | 增加明确 business 源选择；保持显式目标、凭据和本地测试边界，不自动运行迁移或扩大生产权限 |
| `backend/tests/integration/` | 新建隔离库重放完整 DDL 与 business 迁移，对比结构，并验证约束、并发和回滚 |

先实现源定义及生成兼容，再实现事务用例与测试。正式业务源名称不代表工具获准连接生产库；沿用现有 local 环境、允许地址、受限测试账号和本轮资源归属保护。运行正式环境迁移的配置与发布入口仍归 8.2。

初次建库执行两表及 user_id 外键；`up` 重复执行保持无变更。失败后保留 dirty/version 和实际诊断，不自动 down/force；MySQL DDL 不能按业务 DML 的整体回滚承诺处理。新库完整 DDL 与迁移对比必须包含外键，不能只比较列名。后续阶段追加新编号迁移，不回改已执行文件。

## 验收条件及证据范围

业务场景沿用 [身份与任务归属补充验收](../../../../testing/验收与场景追踪.md#身份与任务归属补充验收)，本项优先证明模型不变量。

| 检查 | 通过标准 | 验证方式 |
| --- | --- | --- |
| 源与生成 | 反复生成无差异，手写 WithSession 不被覆盖，外键只由完整 DDL/迁移执行 | 既有生成检查加 user 源覆盖 |
| 创建与查找 | 邮箱/TG 分别可首次创建，后续同身份回到同 idx；不修改已有资料，不初始化首奖/余额 | 单元用例；真实 MySQL 持久化验证 |
| 并发首次注册 | 同身份多个请求最终只有一条指向唯一产品用户的身份记录、一个提交成功的产品用户，失败候选用户全部回滚 | 独立 MySQL 并发用例 |
| 约束 | 重复身份、同用户同类型重复和无效用户引用被数据库拒绝；多个 user_id 为 NULL 的同类型身份可共存；已占用身份的归属覆盖由用例拒绝 | 真实 MySQL 直接写入反例 |
