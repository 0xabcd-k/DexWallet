## 实际交付

| 内容 | 实现及原因 |
| --- | --- |
| SQL 与生成 | user、email_identity、telegram_identity 三表，身份表可空 user_id 直接关联；明确平台字段、唯一归属和外键。tables.sql 进入 goctl，constraints.sql 独立执行，生成器显式登记业务源；11 个纯生成文件、19 个受保护骨架 |
| model 扩展 | 使用 go-zero 生成 CRUD 与按唯一键查询，手写仅增加 WithSession、主键/身份键锁定查询及具名状态/类型 |
| 创建与查询 | 独立 email/TG 用例、邮箱规范化、TG 完整资料快照、当前身份查询、同 session 绑定检查；沿用 transaction.Runner，不新增通用 ORM/仓储或事务框架 |
| 并发与恢复 | 用户先于身份锁定；缺失身份先 INSERT 再锁定读，避免并发空记录间隙锁升级。竞争、已回滚死锁及归属变更最多重新解析三次；候选用户回滚，提交未知/回滚失败不重试 |
| idx | 复用 FF1 v1.2.1，保持 dexpoker 正数编码格式；用户表无 idx 列。并发调用不共享可变 cipher，非法输入与非正/溢出明确失败 |
| 依赖与配置 | ServiceContext 共用连接组装 model、Users 和 UserIdx；新增必填 DEXWALLET_ID_SECRET，启动校验；数据库连接显式 UTC |
| 迁移 | business/000001 包含三表与外键；CLI 支持显式 business 源，独立 schema_migrations_business。仍限制本地专用测试账号与 contract 库，未增加生产执行权限 |
| 验证 | 输入/idx/失败语义单测、真实 MySQL schema/并发/回滚/dirty/CLI 验证，以及生成和原有依赖/健康 HTTP 回归；详见验证记录 |

## 实施细节与后续边界

Telegram 内部入口明确只接受完整且已验证的资料快照。2.2 处理来源、时效与局部资料合成，不把局部缺省误当作完整快照清空。初始产品昵称按 128 字符容量截取派生值，外部 first_name 保持完整；重复认证不覆盖产品昵称头像。

本机原测试账号缺少 REFERENCES，首次隔离外键测试明确失败并清理临时库。本轮只补充原转义 contract 库范围的 REFERENCES，同时更新 prepare_local 的新环境授权。为已有忽略的 .tools/local.env 单次补齐随机 idx 密钥，保留原凭据；开发库、长期 HTTP 测试库、其他项目与生产数据没有执行业务迁移。HTTP 测试子进程使用公开测试密钥。

公开错误码与 API 留到 2.2/2.4 的 .api 源添加。绑定/解绑/换绑入口、验证码与 TG 验签、会话失效、任务完成和奖励分别由对应后续工作项实现；当前测试中的解绑/再绑是受控数据库场景，不是已开放产品功能。
