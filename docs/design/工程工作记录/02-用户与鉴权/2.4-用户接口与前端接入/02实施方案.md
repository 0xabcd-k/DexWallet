## 目标与边界

接通邮箱验证码、Mini App Telegram 登录、账户资料、身份绑定/换绑/解绑、普通退出与全部退出，并恢复可信来源页。仍使用 React、Ant Design Mobile、React Router、i18next 和已有 fetch 客户端，不增加状态框架或新的认证库。

## 设计与实现步骤

1. `.api` 增加 GET /v1/user/identities 与 PATCH /v1/user/profile，生成 Go 路由/类型与 TS 契约。当前身份在事务内复核 Actor 后读取；昵称去首尾空白、非空且最多 128 个 Unicode 字符，事务锁定用户复核状态/版本后更新，并沿用提交后缓存失效。没有 SQL 迁移。
2. 用户端 session 模块只保存产品 token 与随机认证代次，不保存用户资料或额外 initData。读取 JWT 元数据只用于响应排序，服务端独立验签与授权。新认证开始、完成身份变更或退出都会改变代次；普通续签仅接收同用户、同 issuer、同认证版本且更晚到期的 token。
3. 共享 api-client 增加单次请求 headers 与解码成功后的响应头回调，不持有登录状态。用户端封装注入 Bearer、接收 X-Access-Token、处理 401；较旧 token 的迟到 401 不清除更新后的凭证，503 不伪装成退出。任何请求均不自动重试写操作。
4. localStorage 使用 dexwallet:user:session；原生 Web Locks 保护跨标签页写入，storage 事件通知其他标签页。锁能力或存储不可用时进入内存模式并提示；商户、管理端不共享本端凭证。
5. 页面为 /login、/account、/identities，仍使用 Hash Router。登录、身份变更仅恢复白名单内站内来源，不允许外站或登录循环。账户展示昵称、头像、idx，支持昵称编辑；身份页显示两类当前状态，缺身份提示接收 required=email / telegram，绑定后返回并重新查询，不自动执行来源业务。
6. 验证码表单保留当前挑战和原请求令牌，显示 60 秒重发等待、5 分钟有效期与错误次数规则，重发提示最新验证码。未知结果的显式重试复用相同材料、requestToken 和原 JWT；不持久保存验证码草稿。刷新后需要重新认证时使用仍保留的身份。
7. Telegram 只传 SDK 提供的原始 initData；静默交换失败显示错误与邮箱入口。仅保存指纹与恢复请求令牌，原材料继续由既有 SDK 缓存负责。主动退出会抑制同次启动的自动登录，重新打开同一页面不立即登录回来；新的 Telegram 启动可以再次交换。

## 验收条件

覆盖邮箱登录与错误、Telegram 单次静默交换、刷新恢复、昵称修改、绑定冲突和原账户保留、换绑丢失响应后的恢复、最后一种身份不可移除、503 保留凭证、401 重新登录、站外来源拒绝、跨标签页退出、迟到响应不恢复旧登录、续签乱序不倒退，以及中英文切换保留输入。真实依赖与浏览器 mock 分开记录。

## 实施落点

后端手写扩展在 user/profile.go 和 account logic；前端按 auth、api、view/login、view/account、view/identities 分工。使用浏览器原生并发和存储能力，不另建跨应用会话框架。验证与开放限制见 [验证记录](04验证记录.md)。
