## Telegram 端解绑限制补验（2026-10-29）

按用户要求，仅在 Telegram Mini App 前端阻塞 Telegram 解绑。`pnpm typecheck`、现有认证浏览器回归 14 项及文档检查通过。额外用临时浏览器脚本在 Chromium/WebKit 各核验两种运行端：同时绑定邮箱和 TG 时，Mini App 的 TG 解绑禁用并提示，刷新仍生效；邮箱解绑、TG 换绑以及普通浏览器 TG 解绑按钮仍可用。检查期间没有发送解绑请求。使用合成启动参数与 HTTP mock，未作 Telegram 实机验收。

## TG 开发上下文注入验证（2026-10-29）

`pnpm dev:user:tg` 通过 SDK 的 mockTelegramEnv 注入本地签名的启动信息，不 mock API 响应。使用现有 testenv 工具创建隔离 run `d9b10197e2223256`，应用 business 迁移后启动真实 API/MySQL/Redis，开发前后端使用同一个模拟 Bot token。Chromium/WebKit 均实际通过静默登录（HTTP 200）、账户/身份加载、昵称保存及刷新持久化、TG 解绑提示、退出后刷新不再登录、重新打开重新登录。篡改已签名 TG 用户 ID 返回 HTTP 400 / AUTH_PROOF_INVALID。联调完成已停止服务，并清理该 run 的数据库与 Redis 限流 key。

`pnpm typecheck`、41 项单元测试、三端 `pnpm build`、现有认证浏览器回归 14 项均通过；额外执行 `vite build --mode telegram`，产物及模块边界确认不包含开发注入。普通开发服务与生产 preview 均不提供签名响应；未配置 Bot token 的模拟模式按预期启动失败。检查过程使用临时浏览器脚本；真实 Telegram 客户端与真实 Bot 验收仍未完成。启动方式和后端前提见 [开发与测试环境](../../../../engineering/开发与测试环境.md)。

## 局域网开发访问验证（2026-10-29）

三端 Vite 开发监听改为 `0.0.0.0`，API 仍经同源代理访问本机后端。已确认用户端实际监听 `0.0.0.0:5173`；Chromium/WebKit 使用 `http://192.168.1.107:5173`，确认 `isSecureContext=false`、没有 `crypto.subtle`，仍能通过开发 TG 注入进入账户、刷新恢复、展示 TG 解绑限制及退出后刷新不再登录。此次 LAN 浏览器检查使用 HTTP API mock，未宣称在其他物理设备或跨防火墙验证。

随机认证代次/启动编号复用原生安全随机数，SHA-256 缺失仅在开发环境通过锁定的 `@noble/hashes` 2.0.1 补齐；新增单测验证指纹与原生实现一致、旧启动可恢复。`pnpm typecheck`、42 项单元测试、三端构建及产物隔离检查、全量 40 项 Chromium/WebKit 浏览器回归均通过。该开发依赖未进入生产模块；局域网 HTTP 缺少 Web Locks 时保留既有内存登录提示和行为。

## 开发 TG 永久授权调整（2026-10-29）

用户体验时旧的启动授权超过默认 5 分钟有效期，刷新后重新登录被拒绝。用户明确要求开发环境永久有效、以方便体验为先。已采用显式 `Auth.TelegramDevelopment` 开关：仅 local/dev 环境允许开启，TG 授权可长期重复使用，TG 操作回执无时限；仍校验签名、当前账户及绑定状态。前端开发模式每次新登录生成新请求令牌，网络重试保留原材料，不再增加自动刷新 TG 授权逻辑，隐藏开发模式下无关的授权过期提示。

后端 `go test -race ./...`、`go vet ./...` 通过；真实依赖 run `2db37c450599dcea` 验证十年前的材料、多次登录、过期回执恢复和禁用账户拒绝，默认模式的过期/重放限制及公开 HTTP 流程回归也通过，隔离资源已清理。前端类型检查、42 项单元测试、三端构建与生产模块隔离通过；Chromium/WebKit 在运行中的 `172.16.0.102:5173` 使用同一份十年前签名材料，完成登录、刷新、退出后手动登录，以及响应丢失后原请求恢复，未重新请求授权材料。当前本地 API 已启用该开关并重启；产品 JWT 和邮箱规则保持原值。

## 设置平铺与账户归入设置（2026-10-29）

账户资料、通用语言、绑定身份、账户操作按固定顺序平铺；绑定与换绑表单就地展开。旧账户/身份链接兼容跳转设置，保留业务所需身份及来源；未登录仍可使用语言设置。界面规范记录单块原子功能超过 6 个交互点且复杂时才使用子页面。

类型检查、42 项单元测试、三端构建与产物隔离、文档及差异检查通过。更新现有认证回归后，使用独立 5183 端口运行 Chromium/WebKit 共 14 项通过，覆盖昵称保存、身份冲突、换绑响应丢失重试、来源恢复、跨标签页退出及凭证失效；不停止用户正在使用的 5173 开发服务。后台包保留既有的 >500kB 构建提示。

另在 `http://172.16.0.102:5173` 通过真实开发 API 的模拟 TG 登录，Chromium/WebKit 均验证四组顺序、绑定表单展开/取消不离开设置、语言切换、TG 解绑禁用、退出后设置可登录并保留语言。390px 下无横向溢出，页面截图位于 `frontend/test-results/settings-flat-{chromium,webkit}.png`；没有发送真实邮件或执行身份绑定/解绑写操作，不代表真实 TG 客户端验收。

## Telegram 端隐藏账户操作（2026-10-29）

按当前运行端隐藏 Telegram 换绑、切换账户、退出登录及退出全部设备，同时省略空的账户操作分类；加载失败时也隐藏退出按钮，保留重试。Telegram 解绑沿用禁用规则，邮箱操作与其他端操作保持原条件。此规则替代此前 Telegram 换绑入口可见的界面约定，不修改后端契约。

类型检查、42 项单元测试、三端构建及隔离检查通过（后台包仍有既有 >500kB 提示）；更新现有认证用例后，Chromium/WebKit 共 14 项回归通过，包括已绑定两种身份时仍隐藏 TG 换绑、邮箱换绑可用、刷新不重复登录及 503 不露出退出入口。两种浏览器另通过真实开发 API 检查 `172.16.0.102:5173` 页面及刷新，确认入口隐藏且邮箱绑定可见；未执行真实身份写操作，未作 Telegram 实机验收。
