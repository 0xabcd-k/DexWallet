# 3.6 美元余额互转与账单 实施方案

[阶段目录](../README.md) · [全部工作记录](../../README.md) · [工作范围清单](../../../../engineering/工程阶段与工作清单.md)

方案状态：2026-11-04 完成接口、收款码、限额及付款身份验证的讨论稿；尚未实施。零手续费、既有账户/幂等规则及 App 完整版、Mini App 精简先行版定位已确认；本页新增金额参数、验证方式及身份变更保护均为建议，待用户审核。确认依据记录在 [讨论记录](01讨论记录.md)。

## 目标与工作边界

3.6 以美元余额互转与双方账单为首个可操作资金流程，按已确认的首页、收款页、扫码/手动填写及统一付款框交互组织。两端复用同一 API 与账户，Mini App 不展示链上资产、Tab 或钱包抽屉；App 同样完整提供余额互转。钱包、链上报价、充值、出金与商户订单按所属阶段实现，下载 App 引导不建资金单、不冻结余额。

美元互转手续费已确认固定为 0，付款人扣款与收款人到账等额；付款框及双方账单遵循该规则，不引入互转收费配置。只有涉及链上资金流的业务才可能收费，完整边界见 [业务规则](../../../../product/02业务规则.md#手续费边界)。

现有 [内部转账](../../../../engineering/幂等与事务.md) 已实现 Submit/FindByRequest、双方事务记账与转账事件，尚无公开写入接口；[鉴权](../../../../engineering/用户鉴权.md) 已有 JWT、Redis 验证码和 TG initData 校验，没有付款验证码。方案复用这些边界，不重建账本、通用支付状态机或长期授权会话。

## 建议审核项

| 项目 | 本版建议 | 取舍与状态 |
| --- | --- | --- |
| 收款码 | 默认无金额、可重复使用；另可生成固定金额、24 小时有效、可撤销的重复收款码 | 固定金额不能由付款人修改；这是重复收款请求，不是只能付一次的商户订单；新增细节待确认 |
| 金额边界 | 最低 $0.01、单笔最高 $100、每用户每日累计转出最高 $500 | 试运行起始建议，不是行业标准或已确认运营值；不改变奖励最低转入 $2 |
| 付款验证 | 每笔确认后，用已绑定邮箱或 TG Bot 收取该笔专用验证码，不设支付密码或小额免验证 | 增加一次操作，但避免只泄漏产品 JWT 就直接扣款；待确认 |
| 身份变更 | 已注册账户新增绑定、换绑或解绑后，余额互转转出暂停 24 小时 | 接收、查账及奖励转入不受影响；首次注册建立身份不触发；这是新增业务保护建议，待确认 |

金额、日期规则及身份保护通过具名配置表达；不以原型默认值自动开放生产转账。若调整上述选择，应同步本页、页面和验收，不把讨论稿自动升级成已确认规则。

## 接口与字段草案

以下路径和字段仅供方案审核，尚未写入 `.api`、生成代码或注册路由。所有接口要求产品 JWT；付款人从认证上下文取得，不接受客户端传 senderIdx。沿用 `code/message/data/traceId` 与有语义的 HTTP 状态；金额是正的十进制字符串、最多两位小数，禁止浮点金额和科学计数法，输出统一两位。此组资金接口只处理 USD。

| 方法与建议路径 | 请求要点 | 返回与职责 |
| --- | --- | --- |
| GET /v1/user/receive-code | 无 | 本人 idx、昵称、头像、静态 receiveCode、分享链接；不创建资金单 |
| POST /v1/user/receive-requests | requestKey、amount | 创建本人固定金额收款请求，返回 idx、amount、expiresAt、receiveCode、链接；到期时间由服务端计算 |
| GET /v1/user/receive-requests/:idx | 本人请求 idx | 创建者查看金额、到期、是否撤销及分享信息；他人不能用本接口读取管理详情 |
| POST /v1/user/receive-requests/:idx/revoke | 本人请求 idx | 撤销后停止新付款；重复撤销返回相同结果，已成功转账不撤回 |
| POST /v1/user/transfer-targets/resolve | recipientIdx 或 receiveCode，二选一 | 收款人摘要及金额规则；定额码另返回 receiveRequestIdx、固定 amount 和 expiresAt |
| GET /v1/user/transfer-policy | 无 | 本人适用最小/单笔/日限额、今日已用/剩余、resetAt、restrictedUntil、可选验证渠道及不可用原因 |
| POST /v1/user/transfer-challenges | requestKey、recipientIdx、amount、可选 receiveRequestIdx、channel | 检查目标/金额/当前资格后发送付款验证码，返回 challengeToken、expiresAt、resendAt、脱敏接收目标及服务端确认摘要；不占款 |
| POST /v1/user/transfers | 上述同笔参数、challengeToken、verificationCode | 验证后原子转账；返回原单摘要；同键同参恢复原结果 |
| GET /v1/user/transfers/by-request/:requestKey | 原请求号 | 仅发送方按原请求号恢复；从主库查询 |
| GET /v1/user/transfers/:idx | 转账 idx | 仅双方可读，返回与当前用户相关的方向、对方摘要、金额、费用、时间和结果 |

既有 GET /v1/user/accounts 与 GET /v1/user/account-entries 继续负责本人余额与分页账单；按流水 businessIdx 进入转账详情，不另建一套金额和流水查询。静态 /by-request 路由先于 /:idx 注册，避免把路径片段误当业务 idx。

收款人摘要只包含产品 idx、昵称、头像；不返回内部数值 ID、邮箱、TG 数字 ID、余额、资格或他人验证渠道。只允许精确 idx/收款码解析，不提供前缀枚举。不存在与禁用的目标统一表示不可收款；本人转本人明确拒绝。金额、收款人或定额请求改变后，原验证码失效，前端创建新的操作 requestKey 并重新确认。

转账结果建议字段：idx、direction、counterparty、amount、unit=USD、fee=0.00、status=completed、createdAt、voucherIdx。双方详情只暴露本人凭证/流水访问范围，requestKey 仅发送方恢复接口需要，不向收款人返回。成功响应只能来自已提交且凭证完整的单据；不把验证码已发送或校验成功表示为转账成功。

## 收款码与入口

### 无金额静态码

默认展示本人账户二维码、昵称、idx；付款人扫码后填写 USD 金额。该码可反复收款，不按扫码次数建订单，不保存待支付资金状态，也不嵌入固定金额。服务端生成受保护的 receiveCode，内容限版本、类型、目标 idx 和校验标记。

建议采用 `base64url(JSON([1, type, idx, mac]))`，type 仅 account 或 request；mac 为完整 HMAC-SHA256，输入用固定序列化的版本、类型、idx 及环境命名空间，使用独立用途密钥，常量时间比较。外层无 padding，最长 512 个字符与现有启动参数校验一致；验签前限制大小、字段个数、类型及版本。静态码无需新建逐用户数据库记录；域名和密钥由部署配置注入，不使用示例域名生产发码。更换该密钥会使旧码失效，需重新生成，不引入首版密钥轮换框架。

HMAC 只能校验本平台签发及内容完整，不能证明张贴者身份，也不能阻止别人替换为另一个合法收款码。付款框始终从服务器查询并展示真实收款 idx、昵称；昵称和头像是辨认资料，不作为收款账户主键。receiveCode 是可公开分享的收款定位信息，不能用于登录、查账或扣款。

### 固定金额请求

收款人输入金额后由服务端保存本人、金额、创建/到期时间及撤销标记；金额范围不超过单笔限额。request 类型的码只携带收款请求 idx，不把 URL amount 当权威值。创建使用独立的本人 requestKey 幂等，同键异参冲突；同键重试不刷新 24 小时期限，生成新请求才有新期限。

建议首版固定金额码也允许重复付款，每笔付款使用付款人自己的 requestKey，页面明确「固定金额，可重复收款」。不累计“应收已收”、不自动关闭、不承诺只能支付一次；一次性账单属于另一个业务约束，不能把重复收款码当商户订单。收款人可撤销；撤销与转账以数据库锁定并校验的顺序为准，撤销不影响已提交款项。

固定金额不能在付款框编辑；想付其他金额须明确退出该请求，按 idx 发起一笔普通转账，该笔不关联原定额请求。提交时同时验证请求受益人、金额、有效期和撤销状态；不能省略请求检查仍把付款记为已支付该请求。已成功原单恢复优先于当前请求到期/撤销，不能把到账交易变成失败。

### 链接与扫码

Mini App 分享使用部署配置中的官方 Bot 主应用链接，形如 `https://t.me/<bot>?startapp=<receiveCode>`；普通 H5 路由使用现有 Hash Router，形如 `https://<配置域名>/#/pay?receiveCode=<receiveCode>`。均为格式示意，不是已可访问的地址。App 扫码读取同一 receiveCode；App 系统级链接关联在 8.4 验证，不提前声称已支持 Universal Links/App Links。

扫码、粘贴、相册与启动链接均经过同一解析规则，URL 必须精确匹配配置的 origin、路径或 Bot 标识，拒绝多重同名参数、未知版本和超长输入。不跟随任意跳转、不由后端抓取未知网址。登录后恢复收款意图，重新查当前目标；启动参数和 QR 文本只定位业务，不能替代付款授权。识别为链上地址时，Mini App 仅进入下载 App 引导。

## 限额及并发口径

| 参数 | 建议值 | 口径 |
| --- | --- | --- |
| Transfer.MinAmount | 0.01 USD | 与两位小数的金额模型一致，0、负数或额外小数位直接拒绝 |
| Transfer.MaxAmount | 100.00 USD | 含上限；大额不拆单代付或自动改链上 |
| Transfer.DailyOutgoingLimit | 500.00 USD | 同一产品用户所有端、所有收款人合计的成功 USD 互转转出总额 |
| 日界 | UTC 自然日 | 返回明确 resetAt，界面转换为用户本地时间；不是滚动 24 小时 |
| IdentityChangeTransferCooldown | 24 小时 | 本节身份变更保护，独立于日限额重置 |

日额度按转出毛额统计，收款不抵扣用量，失败/回滚/只发验证码不占额度，同键恢复不重复累计。这里只定义美元互转额度；后续商户支付、链上出金须单独明确资金边界，不能直接把此额度称作全平台每日出款上限。限制接收仅依赖既有账号可用规则，不新增收款手续费或接收额度。

policy 查询和发验证码时的检查只用于及时提示，不预占余额或日额度。真正提交时在既有双方用户行锁内重新查认证版本、账号状态、身份冷却、单笔额度、当日累计及可用余额。先恢复同键已提交原单，再执行新转账限制，避免额度已满、验证码过期或政策降低后无法找回成功结果。

首版直接按 transfer_order 的 sender_id 与创建时间范围汇总，不建 Redis 金额计数器或每日余额影子表。新增 `(sender_id, created_at)` 索引；汇总与新单写入均在付款人行锁之后，同一事务的可见已提交数据上完成，所有转账写入路径共用此检查。计入日期与写单时间使用锁定后的同一个服务端 UTC 时刻，避免跨零点查询一天却记入另一天。原有数据时间语义先核实，不直接重解释历史记录。

复用现有限流组件控制枚举、验证码轰炸和重试流量。建议查询按用户均速 30 次/分钟、验证按用户均速 30 次/小时，另配可信来源 IP 额度；验证码发送按用户跨渠道 60 秒冷却、均速 10 次/小时。GCRA 的均速/突发不是严格自然小时计数，也不替代 MySQL 金额上限；重发或切渠道不能重置用户级错误/发送限制。Redis 故障停止新验证码校验和新付款，已提交原单与账单仍走数据库恢复，不能为了限流失效重复扣款。

## 付款身份验证

### 推荐：每笔专用验证码

建议采用「有效 JWT + 用户核对本笔摘要 + 已绑定身份收取专用验证码」，不新增支付密码、免密额度、可信设备或长时间付款授权。小额也按同一流程，避免拆分金额绕过验证。独立 App 以后可评估设备签名等方式，本次不增加未验证的替代通道。

- 用户已绑定邮箱时可发往该邮箱；已绑定 TG 时可发往该 TG 私聊。两者均有时由用户选一个已可用渠道，不要求为了付款补绑另一种身份。目标地址/数字 ID 由服务端查绑定，客户端只能选择 channel，不能指定收件地址。
- 验证信息明确写「付款验证码」，包含收款人 idx、昵称、USD 金额、手续费 0 和有效期；验证码用途与登录、绑定、换绑隔离，不能拿登录验证码付款。TG 使用纯文本，不让昵称中的格式改变确认内容。
- 建议沿用 6 位随机数字、5 分钟有效、每挑战最多 5 次错误和 60 秒重发间隔。Redis 摘要绑定付款用户、auth_version、选中身份及 binding_version、requestKey、收款人、标准化金额、可选收款请求、验证码用途；金额或目标变化即不匹配。每个用户同一时间只保留一个当前付款挑战，重发成功或切渠道使旧挑战失效，界面说明另一端发起会使旧码不可用。
- 原子核对/错误计数/消费使用既有 Redis 机制；正常 API、日志、URL、本地恢复数据都不保存验证码。只保存摘要和必要的短期上下文，不新增 SQL 验证码回执表。
- TG 静默登录及再次打开 Mini App 不算本笔付款确认；不能把 initData、重新签发的 JWT 或前端 `confirmed=true` 当专用验证码。产品 JWT 与验证码若都依赖同一邮箱/TG，也不宣称是独立双因素认证；同一身份或设备被完全接管仍有风险。

TG 用户需允许 Bot 私聊，Mini App 可通过 requestWriteAccess 请求权限，或提示先打开官方 Bot；无权限、屏蔽 Bot 或渠道故障时显示明确原因，允许改选已有可用绑定渠道，不自动免验证。真实用户接收权及发送结果需要实际联调，前端布尔回调不能证明验证码已送达。

### 身份变更保护

现有身份规则允许只验证新身份完成换绑，不要求验证旧身份。若付款直接接受刚绑定的新邮箱，泄漏的 JWT 可能被用于绑定攻击者邮箱后立即转走资金。因此建议对已存在产品用户的绑定、换绑、解绑，原身份事务内设置 `transfer_restricted_until = 当前 UTC 时间 + 24 小时`，并继续沿用已有认证版本失效机制；首次注册初始身份不触发。

冷却期内暂停所有新余额互转转出，不能通过再登录、切 App、切验证渠道或改请求号绕过；收款、查账和奖励转入照常，已有成功单据仍可恢复。所有已有付款挑战也须因身份版本变化失效。该建议不修改「换绑不用旧身份证明」这一已确认契约，但确实新增了转出限制，必须单独审核。

24 小时只延缓“盗用会话后换绑立即转钱”，不能证明新身份归原用户或解决长期身份失窃；不能以此声称账户盗用风险已消除。若用户不接受冷却期，须明确另选验证身份变更的保护或接受相关风险，不能悄悄去掉后声称强保护不变。

### 与通知预留的关系

付款验证码由用户为本笔付款主动请求，是安全验证，不是订阅后的收款提醒；不因此自动订阅邮箱/TG 业务通知。推荐方案会新增 TG 验证消息发送及邮箱付款模板，现有 initData 验签不具备此能力。当前只细化方案，不发送消息、不索取凭据。

原 8.2–8.3 的通知收尾安排保持。若采纳每笔验证码方案，真实付款验证通道必须在正式开放余额转出前验收；可与收尾联调一并完成。3.6 自动化与隔离环境使用 fake 做行为验证，不能把 fake 通过当真实通道可用，也不在生产设跳过验证码开关。

## 提交、恢复与落库

1. 解析收款对象、取得金额规则及本人 policy，付款框显示服务器确认的收款人、USD 金额与手续费 0。美元到美元无汇兑，不伪造行情报价；持仓余额继续不展示，不足时给出原因并禁用最终提交。
2. 用户确认当前内容后生成随机 requestKey（沿用 16–64 位 ASCII 约束），先按本人产品 idx 持久化目标、金额、可选收款请求和原号，再请求该笔验证码。取消表单不扣款；任何参数改变创建新的操作，旧码不跨操作复用。
3. 提交先验证当前 JWT/账号并查本人已成功原单：同键同参直接返回，异参冲突。未查到不代表此前没执行。新执行需原子消费与本笔完全匹配的验证码；消费不在 SQL 持锁期间进行。随后带服务端内部可信验证结果进入转账事务，客户端不能自填“已验证”。
4. 事务内依现有顺序锁双方用户，复查账号、auth_version；先按原请求号恢复已完成单，再检查身份冷却与限额。定额请求随后锁其行，复核受益人、金额、期限及撤销状态；撤销操作同样先锁请求所有者用户，再锁请求行。完成双边记账、单据和事务事件后一起提交。
5. 验证码已消费而后续余额不足、锁失败或事务回滚时，不恢复验证码；继续同一笔需重新获取绑定原号的新验证码。提交成功但响应丢失，先原号查单，无需重付或重发验证码。并发只有一个验证码消费成功，另一请求先查原单；校验失败本身不能证明另一条已在途请求没有扣款。
6. 已知原单完整才显示成功。超时、数据库提交结果未知或原单暂不可见时显示“结果待确认”，保留原号；按查询/显式原号重试恢复，不自动换新号，不把“未查到”展示成确定失败。不创建永久可见的 processing 资金单或独立通用回执系统。

恢复数据不保存 JWT 的额外副本、验证码或接收身份。提交前本地恢复信息无法可靠保存时禁用提交并解释原因；跨端只能凭已有业务 idx 或原请求号查回，不承诺未提交本地表单自动跨设备同步。当前操作结果未知时不从同一个表单生成新号重付。

### 错误语义草案

| HTTP / code | 含义与界面处理 |
| --- | --- |
| 400 / TRANSFER_TARGET_INVALID、TRANSFER_AMOUNT_INVALID | 格式、版本或金额语法非法；修正输入 |
| 401 / UNAUTHENTICATED；403 / PERMISSION_DENIED | 沿用现有登录失效/禁用规则，保留原操作用于重新登录后查询 |
| 404 / TRANSFER_TARGET_UNAVAILABLE | 目标不可收款；未知与禁用不区分 |
| 404 / TRANSFER_NOT_FOUND | 主库当前无可见原单；已提交请求不得据此认定失败 |
| 409 / TRANSFER_REQUEST_CONFLICT | 同一发送方原号对应不同参数；停止复用该号发送新参数 |
| 409 / RECEIVE_REQUEST_UNAVAILABLE | 定额请求已撤销/到期；不影响已提交原单恢复 |
| 422 / TRANSFER_AMOUNT_LIMIT、TRANSFER_DAILY_LIMIT、INSUFFICIENT_BALANCE | 当前新付款不满足金额或资金条件；不占额度、不写半笔流水 |
| 403 / TRANSFER_TEMPORARILY_RESTRICTED | 身份变更冷却期内，显示 restrictedUntil |
| 400 / TRANSFER_PROOF_INVALID | 付款码错误、过期、耗尽次数或与本笔/当前身份不匹配；原操作若已有在途请求仍先查询 |
| 429 / RATE_LIMITED | 显示 retryAfter，保留原号；不绕过验证或新建付款 |
| 503 / TRANSFER_BUSY、TRANSFER_OUTCOME_UNKNOWN、SERVICE_UNAVAILABLE | 区分锁冲突、结果未知及验证渠道不可用；保留原错误与 traceId，恢复不得重复扣款 |

非参与人访问转账详情与不存在统一 404；验证、限额错误只解释当前请求的结果，不推翻同号其他在途请求。业务码实施时采用具名定义并纳入 `.api`，以上不是已发布的 HTTP 契约。

### 数据与实施顺序

建议新增固定金额收款请求表：数值 id 对外编码 idx、owner_id、request_key、amount、expires_at、revoked_at、created_at，唯一 `(owner_id, request_key)`；请求与历史转账有关联后不删除。向 transfer_order 增加可空 receive_request_id 与双方昵称快照，主键/幂等/凭证唯一约束保留；今日统计索引按前述新增。普通互转的 receive_request_id 为空，存在时属于原号参数一致性的一部分。user 增加可空 transfer_restricted_until，不能用普通资料 updated_at 代替安全身份变更时间。

已有转账迁移不伪造历史昵称，快照可空；旧单仍以产品 idx 定位，展示当前昵称时说明为当前资料。不将长期历史二维码、收款请求或资金单放 Redis；Redis 仅保存短期验证码与反滥用限流。

实施先改 `backend/manifest/api/platform/platform.api` 和 SQL DDL/新增业务迁移，生成类型/model 后在手写边界接入。共享 ServiceContext 组装付款验证和转账依赖；认证证明、支付请求校验、限额/账务各归本身职责。资金写入仍走现有 transfer.Service，不提供绕过新限制的公开入口；消息外发在 SQL 事务之外。

前端依次接首页/余额页、收款码与定额码、扫码/手动输入、付款验证、结果恢复及账单详情；复用现有 hash 路由、登录恢复和国际化。App 基础未建立时先在现有用户端完成共享流程，8.4 仍须真实 App 验收，不能把浏览器测试算 App 完成。

## 外部依据与本项目取舍

2026-11-04 查阅 [OWASP 交易授权建议](https://cheatsheetseries.owasp.org/cheatsheets/Transaction_Authorization_Cheat_Sheet.html)：付款人应识别并确认目标及金额，授权由服务端执行，验证材料应绑定本次交易并限制错误尝试。每笔邮箱/TG 验证码、上述额度与冷却时长是本项目建议，不是 OWASP 给出的默认参数或合规结论。

[Telegram Mini Apps 文档](https://core.telegram.org/bots/webapps#direct-link-mini-apps) 定义 startapp 入口，并要求服务端验证 initData；[requestWriteAccess](https://core.telegram.org/bots/webapps#initializing-mini-apps) 可请求 Bot 发消息权限，[sendMessage](https://core.telegram.org/bots/api#sendmessage) 用于向指定 chat_id 发消息。这些能力支持入口与验证码交互，不等于提供了本项目的付款授权、独立双因素或真实消息送达保证。
