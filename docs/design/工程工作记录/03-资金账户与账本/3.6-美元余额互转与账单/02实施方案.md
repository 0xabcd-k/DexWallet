## 用户通知订阅预留（2026-10-30）

已确认：为用户提供订阅接口，显式订阅后才发送业务通知；渠道支持邮箱和 Telegram Bot。首个业务场景为美元互转的收款提醒，资金成功仍以账本事务提交为准，通知失败不撤销转账。用户现在要求先预留功能，真实配置与收发测试延至项目收尾；本轮不交付可调用订阅接口，不改现有事件或任务实现。

实施时建议提供本人订阅状态查询、订阅与取消能力，以现有鉴权和已验证身份为基础；绑定身份不自动代表同意订阅。具体 API 路径、字段、按渠道独立订阅的方式、发送目标及身份换绑处理在实施时明确，再改 `.api` 和 SQL 源定义，不预先登记虚构路由或迁移。

沿用 3.5 的事务事件与持久任务基础。外部 SMTP/Bot 调用不能放进现有 SQL-only 处理器事务；实施时明确网络发送、状态回写、应答未知及可能重复提醒的处理办法。不得沿用 SQL 事务成功来声称外部通知已送达。

收尾安排：8.2 落实 SMTP 主机/端口/TLS/发件人与认证、Telegram Bot 及指定测试收件人的本地配置；8.3 通过真实邮箱与 Telegram 账号验收订阅及通知，清单见 [8.3 验证记录](../../08-发布与多端扩展/8.3-MiniApp发布验证/04验证记录.md)。届时需要用户协助才索取配置，凭据不入库。真实测试通过与正式生产开放分别记录。

此调整仅针对用户邮箱/TG 业务通知；既有邮箱验证码认证、6.7 商户回调及阶段 5 链上通道安排保持各自范围。
