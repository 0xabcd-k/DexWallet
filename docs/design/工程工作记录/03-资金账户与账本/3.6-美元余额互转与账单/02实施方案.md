## 目标与工作边界

3.6 以美元余额互转与双方账单为首个可操作资金流程，按已确认的首页、收款页、扫码/手动填写及统一付款框交互组织。本人链上充值已补齐入口设计；真实钱包、报价、充值和出金仍在阶段 5 实现，不因共用付款框提前宣称可用。

美元互转手续费已确认固定为 0，付款人扣款与收款人到账等额；付款框及双方账单遵循该规则，不引入互转收费配置。只有涉及链上资金流的业务才可能收费，完整边界见 [业务规则](../../../../product/02业务规则.md#手续费边界)。最低金额、限额和付款再次验证身份策略仍需另行确定。

## 用户通知订阅预留（2026-10-30）

已确认：为用户提供订阅接口，显式订阅后才发送业务通知；渠道支持邮箱和 Telegram Bot。首个业务场景为美元互转的收款提醒，资金成功仍以账本事务提交为准，通知失败不撤销转账。用户现在要求先预留功能，真实配置与收发测试延至项目收尾；本轮不交付可调用订阅接口，不改现有事件或任务实现。

实施时建议提供本人订阅状态查询、订阅与取消能力，以现有鉴权和已验证身份为基础；绑定身份不自动代表同意订阅。具体 API 路径、字段、按渠道独立订阅的方式、发送目标及身份换绑处理在实施时明确，再改 `.api` 和 SQL 源定义，不预先登记虚构路由或迁移。

沿用 3.5 的事务事件与持久任务基础。外部 SMTP/Bot 调用不能放进现有 SQL-only 处理器事务；实施时明确网络发送、状态回写、应答未知及可能重复提醒的处理办法。不得沿用 SQL 事务成功来声称外部通知已送达。

收尾安排：8.2 落实 SMTP 主机/端口/TLS/发件人与认证、Telegram Bot 及指定测试收件人的本地配置；8.3 通过真实邮箱与 Telegram 账号验收订阅及通知，清单见 [8.3 验证记录](../../08-发布与多端扩展/8.3-MiniApp发布验证/04验证记录.md)。届时需要用户协助才索取配置，凭据不入库。真实测试通过与正式生产开放分别记录。

此调整仅针对用户邮箱/TG 业务通知；既有邮箱验证码认证、6.7 商户回调及阶段 5 链上通道安排保持各自范围。

## 已确认交互与待落实边界（2026-10-31）

布局与可观察行为统一引用 [用户端界面 U01–U07](../../../02用户端界面.md)，资金路径引用 [钱包与支付](../../../../product/03钱包与支付.md)。首页任务、收款、付款下方增加余额卡；余额详情上方充值、下方账单；本人充值固定本人受益，资金来源为已开放链上资产。

钱包抽屉的排序、外部连接和搜索已确认。付款框的资产信息仅显示汇率与本次需付数量，点击「选择付款钱包」进入抽屉；选定后校验并展示最终扣款与费用，满足条件再「确认付款」并授权。余额、报价、费用校验与外部签名使用实际所选钱包，不能以合并持仓判断单笔支付能力。纯美元余额来源不打开用户链上钱包抽屉。本轮只确认交互并记录验收目标，API 或页面尚未实现。

下一步技术细化应明确收款码的目标/金额约束、本人账单权限、原请求恢复和各渠道实际可用范围；新增契约先改源定义。通知接口继续预留，真实收发测试仍归 8.2–8.3。
