# 3.6 美元余额互转与账单 实施方案

[阶段目录](../README.md) · [全部工作记录](../../README.md) · [工作范围清单](../../../../engineering/工程阶段与工作清单.md)

更新：2026-11-05。以下为按用户最新指令修订的方案，尚未修改业务代码、接口定义或数据库。覆盖 11 月 4 日草案中的每笔付款验证码、个人定额码、单一全局限额和所有身份变更冻结建议；历史见 [讨论记录](01讨论记录.md)。

## 最新方案摘要

| 范围 | 最新规则与方案 |
| --- | --- |
| 付款授权 | 独立、固定的 6 位数字付款密码，两端共用；日常付款不发验证码 |
| 首次设置 | 第一次拉起付款弹窗且账户未设置时引导；邮箱或 TG 验证码通过后设置，返回原付款框，不自动付款 |
| 修改与忘记 | 修改须邮箱或 TG 验证码；忘记密码建议复用验证身份后的重置流程，不要求记得旧密码 |
| 个人收款码 | 无固定金额、可重复使用，付款人输入金额；删除个人定额码设计 |
| 商户收款码 | 固定为商户创建订单的金额，从服务器查单，付款人不可修改；归阶段 6 |
| 限额 | 可创建多个方案并分配给不同用户，每个用户默认一个；默认最低 $0.01、单笔 $100、每日 $500 |
| 身份冻结 | 只有换绑触发，换绑前提醒；时长沿用上一版 24 小时作为本版方案值；新增绑定、解绑、修改付款密码不触发 |
| 费用 | 中心化流转为 0；链上交易收回平台代付的 Gas，钱包已自行支付的同笔网络费不重复扣取 |

本表业务方向来自用户明确要求；24 小时时长、密码错误阈值和方案管理方式等是沿用或新增的设计值，不声称用户逐项指定。付款密码不作为登录密码；登录方式仍为邮箱/TG。

## 范围与已有基础

3.6 实现美元余额互转、个人收款码、付款密码、本人账单和必要的限额方案后台入口。App 为完整用户端、Mini App 为精简先行版，两端共用身份、资金账户、密码和限额；钱包/链上操作归阶段 5、商户订单归阶段 6。

[内部转账](../../../../engineering/幂等与事务.md) 已有原子记账、请求幂等及原单恢复；[鉴权](../../../../engineering/用户鉴权.md) 已有 JWT、邮箱验证码及 TG initData 验签，没有付款密码或 TG 密码管理验证码。复用已有边界，不重建账本、通用支付状态机或长期免密会话。

## 付款密码流程

### 首次拉起付款弹窗

先解析业务目标并查询本人密码状态。尚未设置时显示设置引导，保留原目标；不在注册或只查看账户时强制设置。“第一次”以账户是否已设置为准，另一端已设置则使用同一密码。

用户选择当前已绑定邮箱或 TG，获取“设置付款密码”验证码，输入验证码、新的 6 位数字密码并再次确认。只有一种绑定身份也能操作，不强制补绑另一种。发送目标由服务端查绑定，客户端不能指定任意收件人。密码按字符串处理，前导零有效；界面区分一次性验证码与固定付款密码。

设置成功返回原付款框，重新查询目标、金额、权限、限额及费用，用户再次明确确认付款；设置和取消都不扣款、不冻结、不建转账单。两端并发首次设置仅一个从未设置状态成功，另一端刷新，不能覆盖已有密码。设置应答未知时查状态；版本变化不能证明某一份新密码一定写入，必要时重新验证后重置，不伪造成功回执。

### 日常付款

个人流程：扫码/填 idx → 输入金额 → 核对收款人与金额 → 输入付款密码 → 确认付款 → 查询结果。商户流程使用服务端订单固定金额，进入相同密码确认。

付款密码只在当前输入过程短暂持有，经认证 HTTPS 提交到本平台，提交或退出即清除；不进 URL、日志、分析事件、剪贴板或持久恢复存储。目标/金额改变后清空密码、重新确认，不能自动将已输入密码用于另一笔付款。

3.6 在转账提交请求中携带付款密码，服务端验证本次请求再执行；不能信任前端 passwordVerified=true，也不产生可任意付款的通用免密 token。同号已完成单据仅查询恢复，不再次扣款或要求重新支付。

App 链上付款仍须选钱包、核对最终费用并由真实钱包签名；付款密码只控制平台内授权，不是私钥，也不能控制用户在外部自托管钱包自主转账。阶段 5/6 把授权绑定对应业务目标、金额及费用，不因设置过密码或打开过付款框而跳过本笔确认。

### 修改与忘记密码

设置页增加“付款密码”管理；未设置提示首次付款时设置，已设置提供修改和忘记密码入口。两者都要求当前登录态及已绑定邮箱/TG 的本次验证码，建议忘记密码复用重置流程，不要求旧密码。用途与登录、绑定、换绑验证码隔离。

成功修改递增独立 payment_password_version，使旧密码或旧版本校验结果不能再创建付款；已成功原单仍可查。设置、修改、重置不产生换绑冻结，不重置日用量，也不解除已经存在的换绑冻结。日常付款不发送验证码。

管理验证码沿用随机 6 位、5 分钟有效、60 秒重发和每挑战最多 5 次错误；绑定用户、auth_version、身份及 binding_version、setup/reset 用途和预期密码版本。Redis 原子消费，重发/切渠道不清累计限流。消费后 SQL 失败不恢复验证码，重新获取即可；不新增跨 Redis/SQL 的长期回执。

邮件或 TG 私聊明确是设置/修改付款密码，不索取现有密码。initData 验签不能代替管理验证码；TG 无私聊权限时引导允许发消息或打开官方 Bot，也可选择已有邮箱。渠道不可用不能降级为只凭 JWT 设置。

### 仍需审核的身份恢复边界

现有绑定/解绑不验证旧身份，而新增绑定、解绑按本轮要求不冻结。若刚新增的身份验证码可立即重置已有付款密码，被盗登录态可能经新增攻击者邮箱后绕过付款密码。不能声称固定密码已消除此路径，也不擅自扩大冻结范围。

建议单独采用“新增身份用于重置已有付款密码前，先以原可信身份验证码或旧付款密码确认”的资格规则，不冻结资金；但可信身份登记、全部失去后的恢复，以及解绑后再绑定是否属于实质换绑，仍需明确。本版不假称已有可信身份名单或人工找回能力；实施密码恢复前应完成这项决定。首次设置同样依赖账户与身份管理的可信性。

## 密码存储与尝试限制

6 位数字空间有限，建议每用户独立随机盐、Argon2id 慢哈希，加与数据库分离保管的服务端 pepper。初始参考 m=19 MiB、t=2、p=1，在目标机器验证成本；记录算法和参数版本，不保存明文或可解密密码。pepper 不入库、不入仓库，不复用 JWT 或验证码密钥。

建议连续错误 5 次后暂停密码校验 15 分钟；到期允许重试，成功校验或身份验证后成功重置清理错误计数。阈值具名配置，跨设备/IP 共享；这是防猜测的验证限制，不是身份换绑冻结，不移动账本余额，不影响收款、查账和密码恢复。

错误计数及 password_locked_until 在数据库安全记录中原子更新，错误计数独立提交，不随转账回滚；并发请求不能各自多获得 5 次机会。Redis/GCRA 额外限制流量，故障明确报错，不跳过数据库密码保护。

慢哈希在资金持锁前校验，取得仅本次调用内部可用的用户、密码版本与请求摘要。事务内再核对密码版本、尝试限制、auth_version 与换绑限制，避免校验后并发改密码仍使用旧授权；版本冲突重新输入，不长期持资金锁计算哈希。

## 个人码与商户订单码

个人码只确定账户/到账类型和版本，不含固定 amount，不建个人定额请求及其创建、期限、撤销管理。展示昵称、idx 和二维码，付款人扫码后填金额；每次付款独立 requestKey，展示/扫描不建资金单。个人码夹带 amount 时提示不支持，不能当定额请求执行。

建议静态格式为 base64url(JSON([1, "account", idx, mac]))，完整 HMAC-SHA256 绑定规范化版本、类型、idx 和环境，独立用途密钥；外层无 padding、最长 512 字符，未知版本/多余字段/超长输入拒绝。更换密钥使旧码失效，账户状态仍由服务端检查。合法码可能被替换为他人的合法码，付款人仍需核对真实 idx/昵称；签名不证明张贴者身份。

商户码定位商户创建的订单 idx，金额、商户、期限和状态从服务器读取。付款人不能用 URL 参数改价；已支付订单展示原结果，不能像个人码一样重复收款。商户订单创建/查询归阶段 6，当前阶段不伪造开单能力。

Mini App 分享使用配置的官方 Bot startapp 入口，H5 继续 Hash Router，App 扫码读取同一目标。严格匹配允许的 origin、路径及 Bot 标识，拒绝重复参数和未知链接，不抓取任意外部网址。登录后恢复目标并重新查询；Mini App 遇链上需求只引导 App。

## 可分配的限额方案

| 默认 USD 互转方案参数 | 初始值 | 口径 |
| --- | --- | --- |
| 最低金额 | 0.01 USD | 正数，最多两位小数 |
| 单笔最高 | 100.00 USD | 含上限 |
| 每日转出最高 | 500.00 USD | 同用户、所有端、所有收款人的成功互转毛额合计 |
| 日界 | UTC 自然日 | 返回 resetAt，界面显示本地重置时间 |

可创建多个具名方案，每个用户分配一个当前方案。现有用户迁移补默认方案，新用户注册写入默认方案 ID；缺失或无效方案报错，不按无限额处理。默认标识由统一部署配置指向已有方案；切换默认只影响之后新用户，既有用户需明确重新分配。

建议方案创建后金额参数不可原地覆盖，要调参则复制新方案并分配目标用户，不增加草稿/审批状态机。校验 0 < min <= perTransferMax <= dailyMax，金额为 USD 两位小数；用户不能自行挑宽松方案，商户管理员不能给用户提额。名称仅展示，对外仍用 idx。

最小后台提供列表/新建方案、查看用户当前方案、给指定用户分配已有方案。展示原/新限额及今日用量，填写原因；分配在用户行锁内检查 expectedPlanIdx 并更新，记录操作者、前后值、时间和原因。先支持单用户明确分配，批量规模及原子性另定，不预建调度系统。

policy 返回实际 planIdx、名称、各限额、今日已用/剩余及 resetAt。用量按用户和日期统计，不按方案分桶：已转出 $400 后改到日限额 $300，剩余为 0；改到 $600，则余 $200。收款、修改密码、重登、换端、换方案均不重置用量。

仅成功互转计入，失败/回滚/查单不占额，同键恢复不重复计数。新提交在既有双方用户行锁下读取最新方案及日累计，校验后同事务写单记账，不建 Redis 金额计数器。新增 (sender_id, created_at) 索引，日界与写单采用锁后的同一 UTC 时刻，先核实历史时间语义。

转账单记录采用的方案 ID，不受后来分配变化影响；查回成功原单先于新限额检查。此批方案明确覆盖 USD 互转；商户支付、链上出金的金额口径及是否共享日预算随所属阶段定义，不能称本项已覆盖全平台出款总额度。

## 换绑冻结与提醒

仅成功把同类型已有身份更换为新身份时，原子设置 payment_restricted_until；本版时长沿用 24 小时。新增另一类型绑定、单纯解绑、注册、设置/修改/重置付款密码不设置或延长它；换绑失败不触发，重复已完成结果不再次延长。仍沿用至少绑定两个身份才能换绑及验证新身份的既有规则。

换绑前从服务端取得提示，在提交前明确显示：“更换绑定后，付款/转出将暂停 24 小时，收款和查账不受影响。”用户确认后才提交，取消不换绑；后端按实际换绑强制执行，不能仅靠前端 confirmed。解冻时刻以成功时间计算并返回 restrictedUntil，普通资料修改不能改变它。

冻结是暂停平台内新付款/转出，不把全部余额搬进一笔账本 Hold；收款、查账、奖励转入正常，已有单据继续核验，不能撤销已广播交易。3.6 执行余额互转限制；阶段 5/6 平台出金/余额付款复用，避免换入口绕过。平台不能冻结用户外部自托管钱包的自主交易。

密码防猜测与换绑冻结分别展示原因/期限；修改密码不解除换绑冻结，冻结不清空日用量，切 App 或登录身份不能解除。

## 费用口径

中心化互转、奖励转入、纯余额商户付款与余额退款费用为 0；限额方案不附带中心化收费选项。

链上交易收回平台代付 Gas，确认前列出金额、Gas、总支出、净到账及费用资产；代付不等于免费补贴。充值及美元链上转出按对应报价结算扣费；固定订单金额不能被改写成扣费后的金额，链上通道须明确另付费用或净结算规则。钱包自己已支付的同笔网络费不重复收取。

本轮确认成本收回原则，不批准额外服务费/加价或所有失败退款费用。预估与实耗差额、费用资产、上限、预留退回及逐场景最终承担人，仍见 [费用逐项审核](../../../链上资金费用逐项审核.md)；3.6 不硬编码 Gas，也不把链上成本变成中心化手续费。

余额和 account-entries 继续复用；删除个人 receive-requests 与每笔 transfer-challenges 草案。换绑提醒补入既有身份契约，不重复实现身份体系。密码相关端点不缓存、不转储请求体；平台管理员不能读取密码或替用户跳过验证码设置。

建议新增 payment_security（user_id 唯一、密码摘要/盐/参数、password_version、failed_attempts、password_locked_until、更新时间）和 transfer_limit_plan（不可变参数、创建者及请求号）。user 增加当前方案 ID 与 payment_restricted_until；transfer_order 增加采用的方案 ID、昵称快照及日统计索引。不新增个人定额请求表。

管理创建请求号按操作者幂等，同号异参冲突；相同方案重复分配不重复产生有效变更。新默认方案和用户回填走显式迁移，保留旧资金历史，不伪造历史昵称；缺失快照时按 idx 识别。先改 SQL DDL/迁移及 .api，再生成 model/类型，手写层接 ServiceContext、认证、资金与既有审计；不搭通用规则引擎。

## 提交与恢复

1. 查询目标、密码状态与当前限额方案，未设置先引导设置；受限或不足则说明原因，仅打开弹窗不占款。
2. 最终确认前按本人持久化原 requestKey、目标和金额，不存密码；恢复信息不能可靠保存时不提交。
3. 认证后先查原号：同键同参成功返回原单，异参冲突；新执行验证密码，慢哈希及失败计数不长期占用双方资金锁。
4. 按既有顺序锁双方用户，复查 actor/auth_version，优先恢复成功原单；新单复查密码版本/尝试限制、换绑限制、当前方案/用量、目标及余额。安全记录锁在用户锁之后，密码/身份修改采用一致顺序。
5. 单据、双边余额、凭证分录及事件同事务提交；密码验证成功不代表转账成功，失败不留半笔账，也不生成长期免密授权。
6. 超时/提交未知先查原号，未找到不证明前次失败，不自动换号重付；需重提时重新输入密码并沿用原号。改密码、换绑、降额后的旧成功单仍可查，新付款按当前规则验证。

错误使用具名业务码，区分未设置、密码错误、尝试受限、版本冲突、换绑受限、金额/日限额、余额不足、原号异参及结果未知。密码错误不伪装退出登录，断网不等于未扣款，非参与人查详情与不存在统一 404。日志保留主体/业务 idx 与 traceId，不记录密码或验证码。

## 通知与外部依据

业务通知订阅仍按原安排在收尾 8.2–8.3 配置与测试。设置/修改付款密码的验证码是用户主动请求的身份验证，不自动订阅业务提醒，也不受提醒订阅开关控制。当前不发消息、不索取凭据；正式开放付款前必须有真实可用的密码设置/修改验证渠道，可与收尾联调一起完成，fake 不替代真实验收。

[OWASP 密码存储建议](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) 支持慢哈希、独立盐和分离保管 pepper；[认证建议](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html) 支持按账户限制猜测；[交易授权建议](https://cheatsheetseries.owasp.org/cheatsheets/Transaction_Authorization_Cheat_Sheet.html) 强调服务端控制本次目标/金额和授权。6 位数字是用户指定产品要求，不宣称静态 PIN 等同硬件签名或独立双因素。

实施前仍需细化新增身份的密码重置资格、解绑再绑定的语义、密码哈希成本/尝试参数、实际验证配置及链上逐项扣费；不把这些取舍冒充已实现能力或擅自新增冻结场景。
