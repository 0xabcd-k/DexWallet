方案状态：用户已确认，按本方案实施。确认依据见 [讨论记录](01讨论记录.md)。

## 数据与源定义

- 保留 user_account；新增 ledger_voucher（来源类型、来源单据 ID、动作、可选原凭证、创建时间）与 ledger_entry（凭证内行号、用户账户或平台科目、单位、借贷方向、正金额、用户变动后余额）。SQL-first，business/000006，新表生成基础 model，约束单独维护。
- 凭证来源三元组唯一，分录凭证/行号唯一，账户与原凭证通过外键约束。用户账户和平台科目互斥；平台分录没有用户余额。金额沿用 DECIMAL(36,18)，美元 2 位、积分 0 位，非零正额，用户余额非负。
- 用户账户采用贷增借减，Credit/Debit 分别表示增加/扣减。平台科目借贷方向按其经济含义记录；按单位借贷合计相等。平台静态科目先提供美元充值清算、奖励费用、积分发行；该定义不开放业务，也不证明平台实际收到资金。
- 业务来源使用稳定具名定义；目前提供转账、充值、奖励来源及其独立 idx 类型，后续业务使用自己的真实单据。没有通用手工调账来源或生产测试资金入口。

## 记账入口与事务

账户服务 Post 接收调用方 session、来源与完整明细。必须在现有 transaction.Runner 事务中调用且使用同一 session，任一错误必须向外传播使事务回滚。无独立提交、外部调用、自动重试、Redis 锁或资金缓存。

先校验输入、账户种类和单位平衡；按 user_id/kind 固定顺序准备并锁定所有涉及账户。只为有入账动作的缺失账户准备零行，扣款缺行视为余额不足；已经存在的余额不覆盖。首次账户准备、余额更新与分录同事务。每条用户分录保存实际方向/金额与对应变动后余额，借记不能消耗 held_balance。完整凭证及分录使用绑定到同一 session 的 model。

来源唯一键只保证同一来源动作不多记；重复返回明确错误，不回放或吞错。参数一致性、权限和用户最新状态由外层业务事务负责，不能拿普通鉴权缓存作为资金写入授权。提交错误沿用 transaction.Failure 的未知语义；查询业务来源后由所属业务决定恢复，不能换单据号盲重试。

写入口只追加凭证和分录。original_voucher_id 保留补记/冲正关联；本项不增加任意冲正 API，也不允许借冲正绕过非负余额或奖励不能通用撤销的规则。

## 查询与页面

.api 新增 GET /v1/user/account-entries，沿用产品 JWT、no-store 和续签。所有者来自已验证身份，kind 可筛选，before 为分录 idx，limit 默认 20、最大 100；按分录 id 倒序，取额外一条决定 nextCursor，不做总条数计数或分页快照承诺。刷新重新读取最新已提交记录。

只输出本人账户分录，包含分录/凭证/业务 idx、来源及动作、账户种类、单位、收支方向、正金额、变动后可用余额及 UTC 时间。不返回同凭证其他主体、对手余额、系统科目或内部数字 ID。金额在 Go/TS/页面保持字符串。

用户端记录页提供账户筛选、分页、刷新、加载、空态、错误重试、登录恢复、退出及筛选后的旧响应取消；中英文文案国际化。3.6 再将多条分录聚合为业务账单，本项不把分录当成所有业务或链上交易记录。

## 验收条件

- 首次入账只建一份账户；纯查询/失败扣款不建账；多个账户、多个种类原子提交，余额和分录精确一致。
- 拒绝零、负、非法精度、越界、不平衡、错误单位或未知账户/平台科目；USD 与 POINT 不相互抵销。
- 同源并发只有一次记账；并发扣款不超支；多账户按稳定顺序锁定；后续分录失败和外层业务失败均无半笔账。
- 新库、5 升 6、完整 DDL 结构一致；约束有效，回滚 6 保留原账户和余额；生成一致、手写边界保留。
- 本人列表按种类/游标查询准确；越权参数不改变所属主体；同凭证只返回本人行；未登录/禁用拒绝，错误不变空列表。
- 前端金额精确、方向/余额/来源可读，支持双语、移动布局、筛选分页、空态与失败重试；迟到响应不恢复已退出页面。
- 必须通过相称的 common、独立 MySQL/Redis HTTP 集成及 Chromium/WebKit 验证。未执行的测试及真实供应商、生产迁移、链上业务不计通过。
