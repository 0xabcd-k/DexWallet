## 已确认方案

2026-10-30 用户要求开始讨论 3.2，随后明确“采纳你的方案，执行吧”。本项沿用 3.1 的分行账户、精确金额、按需建账、统一 Credit/Debit 和业务外层事务。

| 项 | 已采纳内容 |
| --- | --- |
| 结构 | 保留 user_account，新增凭证与分录；本人流水直接从分录查询，不维护重复流水表；业务单据管理业务状态 |
| 平衡 | 完整凭证按单位借贷平衡，用户资金变更和平台对应科目有明确来源；积分与美元分别核对；账面平衡不能证明链上到账 |
| 入口 | 一次提交完整明细，Credit/Debit 接收正数并共用核心；业务、余额、凭证、分录使用同一显式事务 |
| 唯一性 | 业务类型、单据 ID、记账动作唯一；业务层负责请求识别、同键异参和返回原结果，账本防重复落账；重复错误不能被忽略后提交余额 |
| 历史 | 只持久化完整已提交凭证，不维护账本处理中状态；不修改历史分录，补记/冲正关联原凭证且遵循所属业务权限和资金规则 |
| 查询 | 本人按账户种类分页，展示方向、金额、时间、业务编号与变动后余额；不返回对手余额或平台分录；接入最小只读页面 |
| 保护 | 首次建账竞争、精度、平衡、余额不足、并发超支、防重复和整笔回滚随 3.2 完成并验证 |

3.3 负责占用/核销/释放，3.4 负责业务请求层幂等接入与系统性验证，3.5 负责持久任务，3.6 负责真实互转及业务账单聚合。本项不开放充值、发奖、转账或任意调账 HTTP 入口。

## 实施细化

具体字段、内部调用契约、查询权限及验收条件见 [实施方案](02实施方案.md)。平台科目使用静态定义，无共享平台余额热点；只记平台分录，不能据此声称已经完成备付或平台资金对账。测试使用隔离资源与合成业务来源，生产业务来源单据随对应工作项接入。
