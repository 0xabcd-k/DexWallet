## 交付范围

内部美元互转 Submit、按本人请求号查原单 FindByRequest，以及对应 SQL、迁移、生成 model、并发与恢复验证。公共 API、客户端请求号生成/持久化和转账界面归 3.6；通知事务事件归 3.5 与业务接入，不先伪造通知成功。

## 单据及事务

新增 transfer_order：数值主键、发送方、收款方、请求号、精确金额、关联凭证、创建时间。请求号限定 16–64 位 ASCII 字母、数字、下划线或短横线，区分大小写，不裁剪或归一化；客户端使用足够随机的值。发送方与请求号联合唯一，业务种类由转账表限定；无 TTL。金额为正数、最多两位小数，复用账户精度和容量约束。

在一个事务内按用户 ID 升序锁双方用户，查当前状态与发送方 auth_version；随后查原请求。已存在时比较金额与收款人并返回原单，不按收款人后来禁用的状态改写历史结果。新单据才要求当前收款人存在且启用。发送方始终需要有效身份与当前授权。请求号查询仅限本人发送的单据，使用同库主库连接。

新请求插入单据取得业务 ID，调用既有 Post 完成双方扣增与凭证/分录，再补齐 voucher_id，成功后才提交。voucher_id 仅允许在尚未提交的同一事务中为空；不保存持久 processing 状态。任何写入或最终读取失败均向外传播并整笔回滚；查询到缺凭证的异常单据明确报结果未知，不当作成功。

锁顺序为用户 → 转账单据 → 账本内部账户顺序。占用路径保持其已确认规则；不把内部互转改成先冻结后异步结算。事务内没有 Redis、消息或链上调用。

## 重试与恢复

- 最多两次执行：仅 MySQL 1213 且事务未报告提交/清理异常时允许一次重试，每次重新开启完整事务并复核授权；受原 context 截止约束。
- 1205 锁等待超时不自动重试，整笔回滚后返回繁忙，并保留原始数据库错误。
- 业务拒绝不自动重试；已回滚请求不保留失败回执。用户重试仍沿用原键与参数，可能因余额变化而成功。
- 提交结果未知先用原号读主库。找到已完成且参数一致的单据即可恢复；读失败、取消或未查到继续返回未知及原始原因，不开始第二次资金事务。
- 之后可以按原号重提；若原事务仍在执行，数据库锁等待会先让它结束，再读取原单或在确认无单时执行。禁止把一次查询未命中转换成新的请求号。
- 公共 transaction.Runner、客户端自动重试政策保持原样。重试或恢复日志保留主体、单据及原始原因。

## 源定义与迁移

先改 transfer 完整 DDL，再扩展现有 goctl 生成链；model 手写边界提供 WithSession 和仅补齐凭证的 Complete。business/000008 创建新表与约束，不修改已执行历史。回滚有任何单据时拒绝，保护持久请求身份与资金历史；无单据时允许 8 → 7。共享开发库不随生成或启动自动迁移。

## 验收

验证同键并发一次转账、数值等价金额恢复原单、同键异参、不同用户请求号隔离、并发不超支、反向互转、晚期失败无单边账、权限复核、死锁重试上限、真实锁超时与取消、提交应答丢失及原事务尚未完成时的恢复。比较完整 DDL 与迁移、验证历史回滚保护。普通测试使用依赖边界 fake，真实资金/锁语义使用独立 MySQL 隔离库。
