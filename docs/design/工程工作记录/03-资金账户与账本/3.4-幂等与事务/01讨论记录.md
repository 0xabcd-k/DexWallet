## 确认依据

2026-10-30 用户要求下一步方案，在查看 3.4 建议后明确“好，采纳你的建议”。本次采用固定请求号、业务单据持久防重、短事务、按错误语义恢复与有限重试。

| 问题 | 已确认选择 |
| --- | --- |
| 请求身份 | 同一次操作使用固定请求号；重试不换号；业务对外 ID 继续使用 idx |
| 重复与异参 | 已有单据同键同参返回原单，金额或收款人不同返回冲突；精确金额按数值比较 |
| 持久依据 | 由所属业务单据和数据库唯一约束承担；账本保留来源防重，无通用响应缓存表及 Redis TTL 防重 |
| 本步落地 | 建立美元互转单据及内部用例，验证完整行为；3.6 开放接口和页面，3.5 接入通知任务基础 |
| 原子性 | 业务单据、双方余额、凭证和分录在一个短事务内提交或回滚 |
| 重试 | 锁超时整笔回滚后返回繁忙；确认回滚的死锁在请求期限内最多自动重试一次；公共事务层不改 |
| 未知结果 | 按原请求查询；暂时查不到不能认定失败，后续继续原号恢复 |
| 明确失败 | 参数错误、余额不足明确拒绝；已回滚请求不保存永久失败回执，原号重试可重新检查余额 |

客户端不得把同一请求号改作另一意图，即使前次显示失败；没有落库的失败不会永久占号或保存参数快照。资金保护不依赖客户端遵守这一约定：已提交的单据始终唯一且拒绝异参。

## 参考与边界

- [Stripe 幂等请求](https://docs.stripe.com/api/idempotent_requests)：稳定请求号、参数比较；未照搬响应缓存与 24 小时清理策略。
- [MySQL 错误处理](https://dev.mysql.com/doc/refman/8.4/en/innodb-error-handling.html)：死锁整笔回滚；锁超时默认可能只回滚语句，因此业务仍传播错误并由事务入口整笔回滚。

不在本项开放任意余额修改、提现或支付接口，不新增通用状态机、后台重试队列、外部调用或前端资金自动重发。
