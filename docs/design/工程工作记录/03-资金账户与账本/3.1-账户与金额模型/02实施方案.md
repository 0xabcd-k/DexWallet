# 3.1 账户与金额模型 实施方案

方案状态：讨论草案，未确认、未实施。对应建议和确认依据见 [讨论记录](01讨论记录.md)。

## 目标与工作边界

为每个产品用户建立独立、初始为零的美元及奖励账户，并提供本人查询。链上余额不由此表代存；Pro 进度、首次任务资格与账户余额各自归属明确。继承已确认的首奖时机和外部身份换绑规则。

本项不执行充值、扣款、转账、发奖或管理调账。实际非零资金变更依赖 3.2–3.4 的账本、占用和持久幂等；资金结果恢复不沿用本轮已删除的认证回执机制，也不能因认证简化而删除资金业务的持久去重。

## 设计与实现步骤

1. **源定义与迁移。** 新增固定字段 user_account：内部 id、唯一 user_id、美元可用、美元占用、待提现奖励、任务积分、创建/更新时间；金额和积分默认零，约束非负。不保存可推导总额、外部身份、链上钱包余额或可配置账户类型。新增完整 DDL 和后续 business 增量，不修改已发布迁移；迁移补齐原有用户零账户，不覆盖已有记录。金额建议 DECIMAL(20,2)，积分 BIGINT，最终值待讨论确认。
2. **生成和边界。** 用现有 goctl/model 配置生成字段与 CRUD，手写扩展承接事务和按 user_id 查询。Go 复用 shopspring/decimal，金额不经过 float。普通展示与业务输入共用已约定单位，按规模限制和精度明确返回参数错误。
3. **初始化。** 新用户注册的原有 SQL 事务调用账户初始化用例，用户、身份与账户一起提交；回滚不留下孤立账户。已有用户重复登录只读取，不重置。迁移后的账户缺失属于异常，查询返回明确错误，不能把数据库错误或缺失账户伪装成零余额。
4. **本人查询。** 在 .api 中声明账户查询和明确字段，生成 Go/TS；从已验证产品用户身份取 user_id，不接受客户端指定他人账户。美元以固定两位字符串返回，积分以整数字符串返回；美元总额由可用加占用计算。账户余额直接查 MySQL，用户身份认证沿用现有中间件。
5. **前端接入。** 钱包页展示美元可用/占用，奖励页展示任务积分和待提现奖励。登录用户看到数据库中的实际值，未登录展示登录入口。尚未完成的资金动作维持未开放状态；不增加虚构余额、首奖或默认已达成进度。金额格式化保持精度并使用国际化。

此处是本项的建议设计，不表示表、路由、初始化或页面已经实现。只新增业务实际需要的 model/use case；不建立没有使用方的通用账务配置层。

## 验收条件

- 邮箱/TG 首次注册均只创建一个零账户；并发登录不重复创建或重置。
- 旧用户升级后具备零账户；重复迁移不修改用户资料或账户金额，唯一关系和非负约束有效。
- 用户及身份创建失败时，账户初始化一起回滚；数据库失败或意外缺行返回错误。
- 美元可用、占用、奖励与积分保持独立；美元总额准确相加，积分不参与美元加总。
- 金额小数位、整数积分、负数、范围上限及序列化可确定验证；不使用浮点或数据库自动舍入。
- 用户只能查自己的账户；退出、被禁用、换绑后的鉴权继续沿用既有规则，账户归属和金额不因换绑迁移。
- 钱包/奖励页展示实际查询值；金额单位和精度准确，网络错误可重试读取，不引起资金写入。
- 生成检查、必要单元测试、隔离 MySQL 迁移/初始化验证及前端接入验证通过；实际验证事实另记，不以文档检查代替。
