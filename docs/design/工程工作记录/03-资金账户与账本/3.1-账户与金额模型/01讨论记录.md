以下细节需要调整，不能直接复制：

- `wallet` 及 `finance/wallet.go` 表达游戏币容量和容量包，不是链上钱包。游戏币超额转积分、VIP/等级容量不进入 DexWallet 的通用记账入口。
- `creditDexCoin` 的余额按实际 `dexCoin` 增加，流水却写原始 `amount`（`bill.go:88–102`）。例如容量只剩 10、奖励 15，游戏币实际加 10，但该笔流水写 15，另有积分加 5；当前实现时流水必须记录各账户实际变动。
- `bill` 唯一键能阻止同一来源再次落账，但 Credit/Debit 遇到重复会返回错误，不会返回原业务结果。若业务重试每次生成新的 source_id，也不能靠这个键识别重复。当前资金业务仍需稳定的业务单据标识和同键异参检查，按 3.2–3.4 落实。
- 参考代码通过错误文本判断重复键，Debit 要求调用方传负数。建议分别使用 MySQL 类型化错误、Credit/Debit 都收正数并在内部确定方向，减少脆弱判断和符号误用；流水仍保存带正负号的实际变动。
- 首次建账的并发、多账户锁定顺序，以及占用、凭证和按单位平衡，不能从参考代码推定已完整解决。沿用现有阶段边界，在实际资金入口开放前验证这些约束；不以一张 bill 表替换当前账本要求。

## 待讨论问题与建议

以下是参考代码后的修订建议，尚未获得用户确认。原宽表和注册时预建账户的建议由 Q01、Q04 替代；Q03 随统一余额列调整存储类型，业务上积分仍为整数。

| 编号 | 要确定的内容 | 建议及取舍 |
| --- | --- | --- |
| Q01 | 账户结构 | user_account 按“产品用户＋账户种类”分行，唯一键为 user_id、kind，共用 balance、held_balance。种类固定为美元余额、待提现奖励、任务积分，单位和允许精度用具名定义关联；不另设可配置种类表，也不叠加暂时没有独立变化需求的账户类型、资产类型两套维度 |
| Q02 | 美元精度 | 统一余额列继续建议 DECIMAL(20,2)，美元按美分入账，Go 复用 decimal，API 用十进制字符串。dexpoker 的 DECIMAL(19,10) 只有 9 位整数范围，不能只因参考项目使用就照搬。2 位结算精度仍待确认，不将页面展示 2 位自动视为账本精度；换汇中间计算不截到 2 位 |
| Q03 | 积分和 Pro | 积分与美元共用精确十进制余额列，按种类限制非负整数，API 返回整数字符串，不再单独用 BIGINT 余额字段；同一列的范围限制也适用于积分。Pro 进度及首次任务状态归奖励资料，在 4.3 落实，不在积分消费时减少，也不重复保存到资金账户 |
| Q04 | 初始化 | 采用按需建账：注册、登录和查询不写账户；已知种类尚无行表示从未入账，余额为零。3.2 首次入账时同事务创建账户并记录流水；新旧用户规则一致，不做批量补零。已经创建的账户即使余额归零也保留，不删除重建；数据库失败仍返回错误 |
| Q05 | 可用、占用和总额 | 美元可用与占用分字段存储，总额读取时相加，不存第三份可漂移的总额；占用明细和核销/释放在 3.3 实现。奖励申请仍按已确认规则直接扣奖励并记录申请，不机械改成冻结 |
| Q06 | 输入精度与舍入 | 普通输入超过允许小数位、为负数或超字段范围时拒绝，不依赖数据库静默舍入。零值用于初始化/查询；后续正额资金操作拒绝零。汇率/费用先精确计算，再由所属业务明确舍入方向后入账，5.4 再落实换算规则 |
| Q07 | 查询与缓存 | 资金余额先直接查询 MySQL，不增加 Redis 余额缓存；用户身份的 30 秒缓存继续独立存在。写入以后走账本事务和数据库余额检查，不用身份缓存中的状态代替写入校验 |
| Q08 | 本项交付 | 源 DDL、迁移、生成 model、金额约束和本人账户只读 API，前端钱包/奖励页显示按账户规则查询的真实值。3.1 不接入注册建账，也不预先实现没有流水的资金写入；首次建账、统一 Credit/Debit 与账本在 3.2 实现，3.3–3.4 补齐占用和持久幂等，随后贯通互转 |

Q01 的目的主要是让不同种类共用清晰的记账代码。美元余额与待提现奖励虽然都以 USD 计量，使用规则不同，仍是两种账户；积分不参与美元加总。只有美元余额使用 held_balance，其余种类该值保持零。多账户事务按稳定顺序准备并锁定账户，不用 map 的遍历顺序决定加锁次序；具体写入和并发验证归 3.2–3.4。
