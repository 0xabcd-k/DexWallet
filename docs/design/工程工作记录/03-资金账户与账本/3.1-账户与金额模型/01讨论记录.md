## 目标和前置状态

2026-10-30 用户在认证可维护性改造完成后提出“下一步”，依主工作清单进入 3.1。阶段 1、2 的实现和回归已完成；本项先确定美元余额、待提现奖励和任务积分的结构、单位、精度及初始化方式。

已有业务规则继续有效：账户归产品用户，换绑外部身份不转移账户；首奖仍在首次任务完成后入账。链上资产是外部事实，Pro 是业务进度，均不作为可消费的平台余额。商户应付款随商户业务和账本明确，不借后台登录账户自动创建用户资金账户。

## 待讨论问题与建议

以下是本轮建议，尚未获得用户确认。

| 编号 | 要确定的内容 | 建议及取舍 |
| --- | --- | --- |
| Q01 | 账户结构 | 单独建 user_account，每个产品用户一条，平铺美元可用、美元占用、待提现奖励、任务积分；user_id 唯一。按现有固定业务建字段，新增资产时再评估，不先建立可配置账户类型系统 |
| Q02 | 美元精度 | 美元余额与待提现奖励均用 DECIMAL(20,2)，与当前按美分结算的业务例子一致；Go 复用现有 decimal，API 用十进制字符串。选择 2 位为降低结算和展示歧义，属于待确认的新工程决策，不能从示例 DECIMAL(36,18) 推导 |
| Q03 | 积分和 Pro | 任务积分用非负 BIGINT、API 整数字符串，不允许小数。Pro 进度及首次任务状态归奖励资料，在 4.3 落实，不在积分消费时减少，也不重复保存到资金账户 |
| Q04 | 初始化 | 新产品用户与零账户同一事务创建；增量迁移为已有产品用户补齐零账户。登录已有用户不重置账户；初始化不发首奖，不增加进度或积分 |
| Q05 | 可用、占用和总额 | 美元可用与占用分字段存储，总额读取时相加，不存第三份可漂移的总额；占用明细和核销/释放在 3.3 实现。奖励申请仍按已确认规则直接扣奖励并记录申请，不机械改成冻结 |
| Q06 | 输入精度与舍入 | 普通输入超过允许小数位、为负数或超字段范围时拒绝，不依赖数据库静默舍入。零值用于初始化/查询；后续正额资金操作拒绝零。汇率/费用先精确计算，再由所属业务明确舍入方向后入账，5.4 再落实换算规则 |
| Q07 | 查询与缓存 | 资金余额先直接查询 MySQL，不增加 Redis 余额缓存；用户身份的 30 秒缓存继续独立存在。写入以后走账本事务和数据库余额检查，不用身份缓存中的状态代替写入校验 |
| Q08 | 本项交付 | 源 DDL、迁移、生成 model、初始化和本人账户只读 API，前端钱包/奖励页接入已落库的真实零值；不增加任意改余额接口。3.2–3.4 再完成记账、占用和持久幂等，随后贯通互转 |

Q01 的同一用户账户行会串行化该用户不同余额的并发写入；按当前用户量接受这项简单取舍。若未来实际吞吐需要，再按有证据的瓶颈拆分，不提前扩展为通用多资产账务平台。
