# 业务规则

本页维护全项目共用语义与约束。已确认规则来源及本版默认值见 [决议台账](../decisions/决议与待落实事项.md)，具体时序见领域流程。

## 主体与身份

| 对象 | 定义与边界 |
| --- | --- |
| 产品用户 | 独立产品身份与 idx，通过邮箱或 Telegram 登录；首次奖励与奖励账户归属于产品用户 |
| 外部身份 | Telegram 等平台的已验证身份，通过绑定关系关联产品用户；依赖该身份的任务次数随外部身份保留 |
| 用户链上钱包 | 用户控制的内置或外部钱包；可切换多个；后端不保存用户密钥 |
| 付款人 | 发起资金操作的已登录用户，不一定是充值受益人 |
| 受益账户 | 实际增加美元余额的产品账户，提交后保存不可变快照 |
| 企业与商户 | 企业拥有商户；订单、凭据、应付款按商户隔离 |
| 项目资金钱包 | 平台收款、归集和出款地址，按网络和用途管理 |
| 平台操作员 | 操作受权限与业务状态约束，资金处理保留证据与审计 |

钱包地址不替代产品身份。恢复产品登录不保证恢复本机密钥；连接外部钱包无需提交助记词。地址簿记录与可签名会话分开，断开连接不删除历史记录。

Mini App 提供 Telegram 静默登录入口，服务端验证授权后，首次创建产品用户及 TG 身份绑定，已有绑定则登录对应产品用户。App 仅保留邮箱、Telegram 两种登录入口，直接登录、游客登录及钱包登录均不在当前范围；导入、切换或断开钱包不改变产品用户及其登录状态。

邮箱采用验证码认证，注册与登录合一：用户输入邮箱、获取验证码并提交，服务端验证成功后，已有邮箱身份登录对应产品用户；首次使用则创建产品用户及邮箱关联，再签发产品会话。不要求设置邮箱登录密码；发送验证码不等于注册成功或登录成功。验证码默认 6 位数字、有效期 5 分钟、重发间隔 60 秒，每次验证码挑战最多 5 次错误尝试；一次使用后失效，重发后仅最新验证码有效。重发不清空累计限流计数，另按邮箱和请求来源限制发送量，聚合阈值在鉴权实施时配置。

邮箱去除首尾空白，域名转小写，本地部分保留大小写；不自动删除点号、加号后缀或合并推测的别名，保留原输入用于展示。

每个产品用户同时最多绑定一个邮箱和一个 Telegram 身份，可以仅有其中一种，不要求两种同时具备。同一邮箱或同一 TG 身份同一时刻只能归属一个产品用户。新增绑定须验证对应身份；成功后保留当前产品用户 idx、账户和记录，不另建产品用户。

绑定已被其他产品用户占用的邮箱或 TG 时，拒绝本次绑定并提示占用，保留双方原绑定、账户数据和当前会话，不自动合并账户、转移身份或迁移余额与奖励。用户若要进入该身份所属账户，须明确选择登录/切换账户并完成认证；绑定请求不能自动变成切换登录。同一类型已有其他身份时，不能以新增绑定覆盖，须按换绑流程处理。

换绑前必须已绑定至少两个外部身份；当前即同时有邮箱和 TG，只有一种时先绑定另一种。有效产品登录态即可发起解绑或换绑，不要求验证旧外部身份；目标新身份仍须验证且未被其他账户占用。解绑后至少保留一种登录方式。换绑以原子替换完成，失败保留原绑定；并发操作在提交时重新检查身份数量及唯一归属，不能通过同时解绑或换绑绕过限制。

已解绑身份再次登录时，按当前绑定查找账户；若未被绑定则验证后创建新产品用户，不根据历史绑定恢复旧账户。需要回到旧账户时，通过保留的登录方式进入再绑定；历史奖励不迁移，外部身份的任务消耗不重置。

产品昵称和头像独立维护；首次通过 TG 注册可用其资料初始化，邮箱注册使用默认资料。后续登录、换绑或 TG 资料变化不覆盖用户编辑；身份识别使用稳定标识，不使用昵称或头像。

允许多设备同时登录；短期凭证可在登录有效期内自动续期，最长 30 天必须重新认证，自动续期不能顺延该上限。普通退出仅使当前设备会话失效，另提供退出全部设备。解绑或换绑成功后重发当前会话并使其他设备会话失效；失败不变更会话。

产品用户与登录身份保持分离。邮箱用户可以没有 TG 身份，除操作本身存在必要条件外，不因缺少 TG 统一限制为只读、禁止奖励或禁止资金操作；已有权限、资格、风控与通道条件仍然适用。设备标识不作为独立登录入口，登录失败或会话失效不回退为设备登录。

外部身份由具体功能按需要求。目前讨论中的任务需要 TG，未来任务可以需要其他身份或不依赖外部身份。缺少必需身份时，明确说明并引导绑定，绑定后返回原操作、重新校验资格；不把缺少 TG 当作产品会话失效，也不在返回后自动领奖或扣款。

## 四类账户和 Pro 进度

| 对象 | 单位与来源 | 用途与限制 |
| --- | --- | --- |
| 美元余额 | 美元；充值、账户转入、奖励转入、余额退款 | 消费、互转和链上转出；可用与占用分开 |
| 链上资产 | 指定钱包、网络、资产的原币数量 | 用户链上收发或经通道付款；美元估值仅作参考 |
| 任务积分 | 整数积分；本人任务、好友助力及单层分成 | 每 100 积分进行一次抽奖，不直接兑换美元 |
| 待提现奖励 | 美元；首奖与抽奖现金结果 | 满足条件后转入本人美元余额，不能直接支付订单 |
| Pro 进度 | 累计点数；首奖额外 1000 加本人实际获得的任务积分 | 达 2000 自动永久解锁，不是余额，不因消费积分下降 |

美元余额内部冻结不改变总负债。奖励转入申请按已确认规则先扣待提现奖励，记录在途申请；拒绝退回，成功增加美元余额，不能申请时和成功时各扣一次。

## 奖励硬规则

| 标识 | 规则 |
| --- | --- |
| R01 | 新用户指尚未完成首次任务的产品用户，首次本人完成获得 $1 待提现奖励及 1000 Pro 进度，不再额外发 1000 可消费积分 |
| R02 | 任务完成统一由用户主动检查领奖，验证通过后自动入账；依赖外部身份的任务按该身份记录次数与资格消耗，换绑不重置；验证、周期和到期条件按任务类型实现 |
| R03 | 完成首次任务后才能邀请；邀请链接绑定具体任务；本人打开自己的邀请返回任务，不产生助力 |
| R04 | 新用户通过邀请亲自完成首个任务得到同一份首奖；老用户助力无本人奖励，且消耗该任务参与资格 |
| R05 | 每次有效好友助力使邀请者获得一次任务积分；接受助力次数不设总上限，每个参与者仍受各任务资格约束 |
| R06 | 首次任务在有效邀请页完成时绑定直接上级；打开链接或登录不绑定；老用户不能补建关系，用户侧不能改绑解除 |
| R07 | 获得任务积分时，其直接上级同时得到最终任务积分的 20%，向下取整；分成无收益上限、不递归，不因上级 Pro 再翻倍 |
| R08 | Pro 进度包括本人任务和好友助力带来的实际任务积分；不包括分成积分和抽奖现金；触发解锁当笔不翻倍，之后按完成结算时权益计算 |
| R09 | 每次抽奖扣 100 积分，1000 积分对应 $1 仅是计价基准；初始 RTP 为 0.95，现金进入待提现奖励 |
| R10 | 扣积分、确定结果、结果记录和现金入账一起完成；页面离开和动画中断不撤销已完成结算 |
| R11 | 奖励提现固定转入本人美元余额，最低 $2、无手续费；还需 Pro 与当前动态条件，高风险可转人工审核 |
| R12 | 不做通用任务奖励事后撤销；失败事务回滚、提现拒绝退回、资金异常有依据的冲正是不同事项 |

具体任务清单尚未确定，不能把可配置的任务管理误当作所有验证类型已实现。奖励示例与计算见 [任务与奖励](04任务与奖励.md)。

任务资格与奖励归属分开：外部身份变更不迁移产品用户的已得奖励、积分或 Pro，也不重置该产品用户的首次奖励资格。任务资格尚可用不等于可以再领首奖；产品用户尚未领首奖也不能绕过外部身份已耗尽的任务资格。外部身份跨产品用户换绑时仍保留原次数消耗；绑定数量及占用冲突按本页主体规则执行，任务只保存完成事实，不设置“进行中”的参与状态；完成记录、资格消耗、首奖、邀请关系与奖励入账作为一次原子提交，具体并发边界见 [任务与奖励](04任务与奖励.md)。

内部奖励设计将「首奖」理解为预期任务奖励的前置体现，不是任务奖励之外的额外赠送。用户已确认仍在首次任务完成后按 R01 入账，金额、Pro 与可消费积分规则不变，不新增后续抵扣、欠款或追回机制。此为内部解释，不主动向用户介绍；对外继续展示首奖、实际入账与适用转入条件。

## 收付款规则

1. 美元账户转账仅给已注册账户，不允许同一美元账户自转；扣款与入账同一事务完成。
2. 链上资产可给本人或他人美元账户充值；固定受益人，付款人不额外先入账。充值平台代付网络费用并从金额扣除，仅启用已验证通道。
3. 美元余额可以转到本人或他人有效链上地址；系统和用户维度风险判断决定自动处理或人工审核。
4. 普通链上转账默认由付款钱包承担网络费，与充值代付不同。
5. 商户订单按美元计价，平台统一收款，商户收入进入应付款；企业通过人工结算收到链上资金。
6. 组合付款限一个美元账户加一个链上钱包、一个网络、一种链上资产；不跨钱包、跨链凑款，不扩展为个人转账组合付款。
7. 商户订单、充值和内部归集分别识别用途；同一链上事件不能重复生成充值与商户收入。
8. 正常订单采用整单退款、异常多付允许差额退款的本版方案；原资金来源、费用与退币数量政策须在通道开放前落实。

## 金额与报价

平台汇率表决定美元与币量换算，不固定假设稳定币等于 $1。每份报价记录金额模式、来源目标、原币数量、美元价值、费用、精度、有效期、规则版本和锁价条件。

后端使用精确十进制或最小单位整数，API 金额用带明确单位的十进制字符串；用户界面格式化不能代替结算。账本精度、展示精度、舍入方向分别定义，费用、汇差和舍入有专门科目。

未有效提交的报价到期须重新确认；已有效提交的业务保留原报价核验。行情不可用暂停新的换算操作，既有记录和资金处理继续可查。审核后报价过期，展示新旧结果并由原申请人确认，不能静默改变到账量。

## 一致性与资金不变量

- 同一有效请求最多产生一次应有入账或扣款；同键异参返回冲突。
- 同一冻结只能核销或释放一次，两者互斥；不能因页面退出或 RPC 查不到就释放未知出款。
- 分配到订单、超额及退款的总量不能超过同一实收；链上去重精确到资产转移事件，不仅使用交易哈希。
- 用户及商户可用金额不能并发超支，退款和结算不可重复占用同一金额。
- 钱包返回、截图、通知、客户端哈希、人工点击均不能单独证明到账。
- 已收链上款但数据库失败时保存证据并幂等结账，不要求用户再付；已出款但状态未更新时补结账，不重发。
- 结果未知有责任人、处理期限与恢复路径，不能无限无人处理，也不能未经证据冒充失败。
- 通知失败不撤销支付，商品履约失败不改变已收款事实；资金差异用可审计的补记或冲正，不直接改历史分录。

## 权限与诊断

账户禁用后拒绝新登录、使现有会话失效并阻止用户发起业务操作，保留账户及历史数据。后台继续核验、结算和恢复已受理的资金业务，禁用不取消既有交易或抹除资金责任。

用户只能查看本人的业务；代充值付款人可查看自己的付款和对方到账结果，不能因此读取受益人的总余额。商户只能访问所属数据，后台登录与普通用户身份独立。

平台保留业务 idx、交易事件、报价版本、原始通道错误、重试和操作记录。用户界面提供可理解原因，不公开风控绕过参数；凭据、用户私钥和助记词不进入仓库、公开输出或不相关日志。
