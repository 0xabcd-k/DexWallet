## 商户扫码支付

### 原有主流程

1. 商户向项目后端申请创建订单，并在前端展示订单号或二维码。
2. 钱包扫码后向后端获取订单金额、允许币种、收款地址与订单号。
3. 前端向对应地址付款，并使用 memo 记录订单号。
4. 后端轮询检查到账，向商户回调付款信息。

需补充的确认步骤：扫码解析后先展示商户、网络、币种、金额、费用和有效期，再由用户授权付款。此步骤为建议项；扫码跳转支付页和付款授权的交互边界【待填写】。

### 状态与异常

建议分别记录订单状态和商户通知状态：订单可以处于待付款、确认中、已支付、已过期、已取消、异常待处理；通知可以处于待发送、重试中、已送达、需人工处理。退款如纳入范围，另记录退款过程并关联原订单。

| 场景 | 需要确定的用户结果与处理方式 |
| --- | --- |
| 扫码错误、订单失效、商户停用 | 是否可重新获取订单；错误提示与返回入口 |
| 余额或手续费不足、网络不支持 | 如何补充余额、切换网络或取消 |
| 用户拒签、页面关闭、网络断开 | 重进页面如何恢复；如何判断是否已经提交 |
| 转账已提交但暂未确认 | 等待时长、查询入口；不得仅因页面超时默认未付款 |
| 少付、多付、分次付款、重复付款 | 是否合并匹配、差额和多余款处理、支持人员 |
| 错币、错链、缺失或错误 memo | 是否可核实与找回、所需证据、责任及处理时效 |
| 过期后到账或确认结果变化 | 是否继续履约、退款或进入人工处理 |
| 付款成功但商户回调失败 | 用户展示、重试上限、主动查询和商户补偿处理 |

每项补充：最终规则【待填写】；责任人【待填写】；通知文案【待填写】；操作留痕【待填写】。

## 验收场景草案

| 场景 | 可观察的预期结果 |
| --- | --- |
| 余额和 Pro 进度 | 按确认口径展示，提现或奖励撤销后的变化可解释 |
| 提现重复提交、处理超时 | 同一申请的资金处理不重复，未知结果可继续查询 |
| 商户订单正常支付 | 商户、金额、资产及账单一致；满足确认标准后回调 |
| 同一交易被重复扫描 | 不重复记账、不重复结算；回调重复投递按约定处理 |
| 页面中断后恢复 | 能查到实际付款状态，避免引导用户重复付款 |
| 付款成功但通知失败 | 保留真实到账状态，单独展示并处理通知问题 |
| 错误金额、资产或订单标识 | 不错误匹配为正常到账，按已填写异常规则处理 |
| 访问其他用户或商户订单 | 符合已确认的数据权限，不能跨主体操作 |

填写对应测试数据、实际结果、证据、验收人和日期。运营与资金处理见[运营与维护](运营与维护.md)，明细见[账单](账单.md)。
