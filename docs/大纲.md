# DexWallet 产品规划

本规划覆盖产品定位、用户需求、功能范围、奖励与资金规则、版本交付和持续运营。现有方向是以钱包为首页，结合任务奖励、邀请助力、Pro 权益和商户扫码支付；市场、商业模式与首发范围由下表补充。

## 填写方式与文档入口

- **原有设想**：来自原需求，保留原意，不代表已完成评审或开发。
- **建议项**：为规划完整性补充的候选内容，是否纳入版本由你决定。
- **待填写**：补充事实、数值、负责人或日期；暂不适用的内容写“不适用＋原因”。
- **待决策**：存在多种产品选择，需要明确结论。各模块新增的流程、状态、验收项均为建议草案。

建议依次填写：产品定位 → 关键决策 → 首发范围 → 各模块规则 → 运营维护 → 排期与验收。金额、概率、比例及时间阈值以确认后的业务规则为准，示例不作为默认配置。

## 三 原有业务设想与关键决策

### 原有规则清单

以下统一保存原稿中的业务数值。确认或调整后，应同步相关模块与验收案例。

| 编号 | 原有设想 | 待明确的规则 |
| --- | --- | --- |
| R01 | 任务列表初始奖励 1 美元 | 展示余额还是实际发放；触发条件、领取次数、是否可提现 |
| R02 | 继续做任务到 2 美元，解锁 Pro，可提现且奖励积分翻倍 | 按当前余额还是累计收益；是否含邀请奖励；解锁是否扣费；是否永久有效 |
| R03 | 任务奖励采用积分制，1000 积分等于 1 美元 | 是展示折算还是可兑付比例；积分来源、有效期、转换时点与精度 |
| R04 | 每 100 积分转一次，奖励数学期望为 0.1 美元 × RTP，可高可低 | 是否扣除积分；奖励落入哪种余额；RTP 数值、概率表和单次上下限 |
| R05 | 每个任务有“自己做”和“邀请别人做”两种选项 | 两种方式是否互斥；好友完成是否等于本人完成；次数限制 |
| R06 | 邀请时复制链接，请好友完成任务获取奖励 | 链接有效期、归因时点、注册后恢复任务、奖励归属 |
| R07 | 自己做显示任务奖励；帮助别人时，新用户显示 1 美元，老用户显示“一个助力” | 1 美元由谁领取；与 R01 是否同一笔；助力如何换算与兑现 |
| R08 | 邀请的新用户自动成为下级；下级后续任务奖励的 20% 作为邀请人的积分奖励 | 仅直接邀请还是更多层；按基础还是翻倍后奖励；资金承担方、上限和期限 |
| R09 | 页面包含任务列表、邀请弹窗、水果机、任务内容页、分享统计、钱包和账单 | “任务完成页”与“任务详情页”是一个页面的不同状态还是独立页面 |
| R10 | 钱包作为首页，提供商户扫码支付 | 钱包类型、账户关系、支持网络和资产、签名与资产控制方 |
| R11 | 商户创建订单并展示订单号；扫码获取金额、允许币种、收款地址及订单号 | 二维码格式、订单有效期、费用、金额锁定、商户结算方式 |
| R12 | 前端以 memo 记录订单号付款到对应地址，后端轮询到账并回调商户 | 目标链的 memo 能力、订单匹配、确认标准、补扫和回调重试 |

RTP 在本规划中指长期平均返还比例，不代表每次获得固定奖励；具体定义和取值待确认。原稿的 0.1 美元来自 100 积分按 R03 的名义折算，尚不能据此确定实际现金支出。

## 五 奖励经济与资金边界

| 概念 | 待填写的定义 | 必须确认的关系 |

## 九 验收与发布标准

各模块中的验收用例为草案；选入版本的用例应补齐预期值，不能以“流程能点通”替代奖励和资金结果验证。

- [ ] 版本范围、原型、业务规则和不做事项已确认。
- [ ] 选定任务从开始、验证到奖励入账均可追溯。
- [ ] 新老用户、Pro、邀请关系和重复操作等边界结果符合规则。
- [ ] 支付、提现、账单、商户回调和资金对账的相关用例通过。
- [ ] 超时、外部依赖失败、重试及中途退出有明确结果和恢复入口。
- [ ] 语言、设备、权限、性能和数据指标达到填写后的目标。
- [ ] 运营配置、用户告知、客服处理、监控告警和恢复演练已准备。
- [ ] 关键待决事项已关闭；未关闭事项有影响说明与处理人。

验收记录模板：功能编号【待填写】；版本及环境【待填写】；前置条件【待填写】；操作【待填写】；预期【待填写】；实际结果及证据【待填写】；是否通过【待填写】；验收人和日期【待填写】。
