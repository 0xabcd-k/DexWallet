# DexWallet 项目文档

更新日期：2026 年 11 月 21 日。

DexWallet 提供美元账户与链上钱包协同的收付款能力，通过任务、好友助力和积分奖励引导用户使用。用户端以「钱包／奖励／记录」组织，商户端完成收单与结算，平台端负责审核、异常恢复和资金核对。

最新产品定位：App 是完整用户端，提供任务、奖励提现、中心化钱包及全部用户链上功能；Telegram Mini App 是先行发布的精简版，只提供其中的任务与奖励提现、中心化钱包。两端奖励均先转入美元余额，链上提现须在 App 操作；App 首版保留四链九资产组合，两端共享同一产品账户与账单。此为已确认产品方案，客户端裁剪及下载引导尚未实现；详见 [客户端范围](product/01项目总览.md#客户端与资产范围) 与 [本次决议](decisions/决议与待落实事项.md#2026-11-04-mini-app-与-app-客户端分工调整)。

本分支将历史需求与最新交互设计重新整理为一套项目定义。以下文档是本分支的当前入口；已建立产品与工程设计，并完成 1.1 最小工程初始化、1.2 隔离契约示例与生成/迁移工具链、1.3 后端公共基础、1.4 三端前端骨架及 1.5 本地开发与隔离测试环境；2.1 已建立 [用户模型与 idx](engineering/用户模型.md)，2.2 已建立内部鉴权，2.3 已接通 [公开登录与产品 JWT](engineering/用户鉴权.md)、响应头续签及 30 秒用户缓存；2.4 已接通用户端登录、账户资料与身份管理，2.5 已接通 [后台鉴权及 super 工具](engineering/后台鉴权.md)，已完成认证和缓存的可维护性简化（Redis 验证码、取消操作回放、三端复用）；3.1 已接通 [账户模型与余额查询](design/工程工作记录/03-资金账户与账本/3.1-账户与金额模型/03实施记录.md)，3.2 已建立 [内部记账与本人流水](engineering/账本与流水.md)，记录页已接入；3.3 已建立 [占用、核销、释放及本人明细](engineering/占用与释放.md)；3.4 已建立 [内部美元互转单据、请求幂等与失败恢复](engineering/幂等与事务.md)；3.5 已建立 [事务事件与持久化后台任务](engineering/持久化后台任务.md)、有限重试、租约恢复和运维工具，当前代码数据库要求 business 44，真实通知处理器待接入；用户订阅后通过邮箱/TG Bot 通知的需求已预留，按最新决议在收尾 8.2–8.3 配置并验证真实收发，见 [通知预留记录](design/工程工作记录/03-资金账户与账本/3.6-美元余额互转与账单/01讨论记录.md)；3.6 已实现 [美元余额互转、个人收款码与账单](engineering/美元余额互转.md)，含多方案限额和换绑限制。4.1 已实现 [任务基础与 Telegram 频道 mock 样例](engineering/任务基础.md)，包含任务列表、详情、身份资格和只读关注检查；4.2–4.5 已接通 [任务领奖、Pro、邀请与原子结算](engineering/任务领奖与奖励结算.md) 的本地 mock 全流程；4.6 已接通 [积分抽奖](engineering/积分抽奖.md) 的本地单次扣分/奖励结算与恢复。真实频道、公开充值、商户付款和链上通道尚未开放。原有 112 份文件原样保存在 [历史归档](archive/README.md)，旧 Word 和原型不代表新版界面。

## 使用约定

规则分为「已确认」「本版方案」「待落实」：已确认事项继承用户决议；本版方案是本轮选择的设计和默认值；待落实事项需要具体配置、技术证据或产品决策才能开放对应能力。不能将原型值直接作为生产承诺。

业务规则集中在产品文档，页面文档描述如何呈现和操作，工程文档描述如何实现一致性，验收文档描述可观察结果。新增需求先更新归属文档，再同步受影响的引用与场景，不另起一套矛盾口径。
